# AGENTS.md — инструкция для AI-агентов, работающих с этим репозиторием

Это **AI Ops Kit** — переиспользуемый пакет (parent) AI-first операционной системы для
команд: агенты, workflow-контракты, quality gates, маршрутизация, управляемые обновления
child-репозиториев. Здесь разрабатывается сам пакет; в продуктовые репозитории он
устанавливается через `installer/ai_ops.py init`.

## Ключевые инварианты

Валидаторы их проверяют, но знать заранее дешевле:

- **Registry — источник истины.** Файл агента без записи в `registry/agents.yaml` (и наоборот) — ошибка.
- **Capability-декларации честные.** В `registry/runtimes.yaml` и `capability-index.yaml`
  нельзя объявлять возможности, не реализованные в коде; для планов — `status: unsupported` + note "planned".
- **Writer ≠ judge.** В workflow-контрактах стадия с `review_mode: read-only` не может быть writer'ом.
- **Стадии ссылаются только на существующие agent id и gate id.**
- **Никаких новых зависимостей** без явного решения: Python-инструменты работают на stdlib + pyyaml.
- **Язык документации — русский**, идентификаторы и ключи — английские.
- **Импорты внутри пакета — пакетные** (`from ai_ops_kit.<пакет> import <модуль>`). Плоское имя
  соседа связь прячет: её не видит ни человек, ни `validate_layering`. Исключение — валидаторы
  из `ai_ops_kit/validation/` — зона-исключение (v3.34): пакетное имя у них теперь ЕСТЬ и код
  пакета им пользуется, но сами валидаторы двурежимны и потому под общий инвариант не подпадают.
  Границы зоны проверяются: она одна, в ней только точки входа, и список объявленных
  не-валидаторов вправе только сокращаться (`tests/unit/test_package_surface.py`).
- **Слои пакетов.** `foundation` → `primitives` → `capabilities` → `intelligence` → `entrypoints`; зависимость вверх
  запрещена (`packages/layering.yaml`, `validate_layering.py`). Взаимные связи ВНУТРИ ядра пока
  разрешены осознанно — замер 12 пар и 210 циклов длиннее двух; строгий DAG требует разбора, а не
  выключателя. С v3.34 замер — ПОТОЛОК: новая пара или цикл краснеет, ушедшая обязана быть списана
  в `packages/layering.yaml` (ратчет ходит только вниз).
- **Три кольца** (owner-review 2026-07-30, см. `qualification/bootstrap/v3.8.0-plan.yaml` → `architecture_rings`).
  Kernel (Task→Context→Execution→Evidence→Decision→Delivery) НЕ зависит от Intelligence (research/
  product-learning/аналитика); Intelligence зависит от Kernel и ЧИТАЕТ его события. Governance подключается
  ПО РИСКУ, не на каждой задаче. Изменение продукта не должно требовать заполнения исследовательской онтологии.
  С v3.33.2 первая половина — не декларация, а ПРОВЕРКА: аналитика живёт в пакете `intelligence` слоем
  ВЫШЕ ядра, зависимость вверх запрещена (`validate_layering`). Обратное направление разрешено намеренно.
- **Модель продуктового репозитория (v3.35).** Восемь контуров, у каждого свой источник истины
  (`registry/product-operating-model.yaml`); WorkItem объявляет `affects` — какие контуры изменяет.
  Три состояния, и третье НЕ равно второму: `changed` / `not_changed` / `unknown`. Контур без
  сигнальных путей в этом репозитории кит видеть не умеет и говорит `unknown`, а не «не менялось».
  Обратное тоже инвариант: `not_changed` НЕ требует обновления документов — бюрократия «восемь
  документов на каждую задачу» запрещена явно. Гейт `contour_consistency` — advisory до обкатки.
- **Статус не объявляется там, где его можно вывести (v3.35).** В `planning/plan.yaml` человек
  объявляет только факты, которых код не знает (`todo`/`in_progress`/`done`/`dropped`);
  `ready`/`blocked`/`waiting` СЧИТАЮТСЯ из графа зависимостей, статуса WorkItem'а и реестра
  активных работ. Приоритет: факт из гейтов > объявленный факт человека > вывод из графа.
- **План называет РОЛЬ, не исполнителя (v3.35).** Поля `runtime`/`model`/`provider`/`assignee`/
  `agent` в плане запрещены ПРОВЕРКОЙ: иначе смена Claude Code на Codex переписывала бы план
  продукта. Кто соответствует роли сейчас, решает роутер в момент запуска.
- **Наружу — смысл, а не внутреннее состояние (v3.35).** Между состоянием кита и человеком стоит
  Human Communication Layer (`registry/communication-policy.yaml` + `ai_ops_kit/ui/presenter.py`).
  Контракт `UserMessage` живёт в КОДЕ, а не только в скилле: соблюдение не может зависеть от того,
  вспомнила ли модель вызвать скилл. Аудитория по умолчанию — `product`. Простой язык НЕ означает
  сглаживание: `degraded` остаётся `degraded` на всех трёх уровнях.
- **Runtime через адаптер, не замена.** AI Ops управляет исполнителем (Claude Code/Codex/OpenHands SDK/…)
  через адаптер; workflow/approvals/evidence не переписываются при смене runtime. Свой tool-loop не наращиваем,
  если внешний runtime делает это надёжно.
- **Capability_freeze (3.8): СНЯТ — 3.8 stable достигнут.** В 3.9 аддитивно добавлены first-class Claude Code
  executing adapter + complexity-aware routing (доказаны live). Новые концепт-возможности — ПО ДАННЫМ реальных
  прогонов (3.10 Real-Product Qualification), а не по красоте; точечно и аддитивно.

## Публичная граница и breaking change

Перепись поверхностей — [docs/api/public-surface.md](docs/api/public-surface.md); там же
машиночитаемая декларация, которую сверяет с кодом `tests/contracts/test_public_surface.py`.
Здесь — правило.

**Зачем понадобилось.** Границы не было, а канал `stable` уже обещал дочкам совместимость. Без
объявленной границы «breaking change» не определён: любая правка могла оказаться ломающей, и ни
одна не была ломающей наверняка. Обещание без содержания хуже отсутствия обещания.

**Breaking change — это (список закрытый):**

- удаление или переименование интента `./ai-ops` либо команды кита;
- изменение СМЫСЛА существующего кода возврата (`0` — сделано и готово, `1` — исполнено, но не
  готово, `2` — не исполнено). Новый код — аддитивен, но объявляется до первого применения;
- новое **обязательное** поле в `stable`-схеме: существующие документы дочки перестают проходить
  валидацию в тот же день;
- удаление ключа `.ai-ops.yaml` или сужение множества его допустимых значений;
- изменение раскладки `.ai/` — переезд каталога, смена того, что обновление перезаписывает, а что
  оставляет владельцу.

Что breaking change **не** является: новый интент, новое необязательное поле, новый ключ конфига
с рабочим значением по умолчанию, любая правка внутри `ai_ops_kit/*` при неизменной поверхности.

**Окно вывода — один minor.** Уходящее сначала объявляется `deprecated` (запись в
`public-surface.md`, предупреждение в выводе команды), продолжает работать весь следующий minor и
удаляется не раньше того, что за ним. Одновременно объявить и удалить нельзя: дочка обновляется не
в тот же день, и молчаливое удаление она встретит прогоном, а не чтением CHANGELOG.

**Уровень объявляется до первого пользователя, а не после.** Поверхность без записи в декларации
краснеет тестом — именно потому, что незаявленное по умолчанию читалось бы как контракт.

## Перед коммитом — обязательно

Полный контур — **одна команда**, тот же набор, что в CI `.github/workflows/package-quality.yml`:

```bash
./scripts/check-full.sh     # охват full-current-python: весь pytest на ТВОЁМ интерпретаторе
./scripts/check-fast.sh     # быстрый профиль во время работы (~1 мин, без маркера slow)
```

**Называй охват, а не говори «полный».** `check-full.sh` — это `full-current-python`: одна версия
Python, та, что стоит у тебя. Объявленный пол `requires-python` и установку в чистое окружение
даёт только `compatibility-matrix` — джобы CI `pipeline-e2e`, `clean-install`, `upgrade-path`.
Оба охвата объявлены в `registry/release-claims.yaml -> evidence_scopes`; заявление о полноте без
имени охвата отклоняет `validate_release_claims`. Повод: PR #38 написал «полный контур зелёный»,
и compatibility-matrix опроверг это в том же релизе.

Построчного чеклиста больше нет: селфтесты модулей, все 72 валидатора и прогоны на примерах
переехали в pytest — дублировать их значило бы гонять одно и то же дважды. Почему именно так —
в [docs/agent-guides/pre-commit-checklist.md](docs/agent-guides/pre-commit-checklist.md).

**Линтер — часть контура (ревизия 2026-08-11).** `check-full.sh` запускает `ruff check .` ДО тестов,
и то же делает джоба `lint` в CI. Набор объявлен в `pyproject.toml -> [tool.ruff.lint]` и узок
намеренно — `F821`/`F811`/`B023`, класс «поломка», не стиль; по нему ноль, поэтому он блокирующий.
Расширять набор — отдельным решением со своей уборкой (остаток долга: 912 находок, разбор в
[docs/audit-report.md](docs/audit-report.md) §6). Повод: ruff не запускался НИГДЕ, охват хука
(`^(tools|validation|tests)/`) не включал `ai_ops_kit/`, и в пакете жили пять точек входа, падавших
с `NameError` при любом запуске. Если ruff не установлен — `check-full.sh` скажет об этом громко;
молчаливо пропущенная проверка не должна выглядеть пройденной.

**Тест УТВЕРЖДАЕТ, а не возвращает.** `return` со значением из теста pytest проглотит: тест
пройдёт независимо от результата. Так были фактически отключены четыре валидатора и селфтест
инвариантов. Проверяется структурно — `tests/contracts/test_suite_asserts.py`.

**Selftest не живёт в продакшн-модуле.** Модули `ai_ops_kit/` едут в child-репозиторий; тест
модуля — в `tests/unit/test_<module>_selftest.py`.

## Инженерный цикл

Полная версия — в [docs/agent-guides/engineering-cycle.md](docs/agent-guides/engineering-cycle.md).

Кратко:
1. **Change Brief ДО кода** — шаблон в `templates/quality/ChangeBrief.md`.
2. **Три теста на capability** — positive, fail-closed, side-effect proof.
3. **Один свежий review до merge** — AI-сессия без авторского контекста, ≤5 находок.
4. **Не гонять полный цикл после каждой правки** — целевой selftest → core smoke → полный CI один раз.
5. **Рефакторинг — правило третьего изменения.**

## Релизный процесс

**ВОРОТА (с 18.08.2026, работа `release-has-a-gate`).** Три проверки, каждая с кодом возврата:
- **запись для CHANGELOG добавлена в этой ветке** — `towncrier check --compare-with origin/main` в
  обязательной джобе `lint`. Фрагмент — файл `newsfragments/<что-это>.<feat|fix|quality|chore>.md`
  (инструкция — в `newsfragments/README.md`). `towncrier build` НЕ запускается нигде: старый
  `CHANGELOG.md` остаётся как есть;
- **формат новых коммитов** — `cz check` от точки включения
  (`pyproject.toml -> [tool.ai_ops.release_gates] commit_format_enforced_after`). Только НОВЫЕ:
  в истории 72 коммита без conventional-префикса из 594, и переписывать её не будем;
- **выпуск без раздела CHANGELOG для своей версии ОТКАЗЫВАЕТСЯ** (`release.yml`). Прежде он выходил
  «с краткими записками», то есть с пустой историей.

Согласованность версии (`VERSION` ↔ манифест ↔ `registry/release-claims.yaml`) уже проверяют
`validate_ai_first_registry` (п. 7) и `validate_release_claims` (п. 1) — второй механизм на то же
место был бы второй правдой.

1. Обновить `VERSION`, `manifest/ai-ops-manifest.yaml -> ai_ops.package_version`
   и добавить раздел `## [X.Y.Z] — дата` в `CHANGELOG.md`.
2. Коммит `release: AI Ops Kit vX.Y.Z` в `main`.
3. Тег `vX.Y.Z` и GitHub Release создаёт автоматически `.github/workflows/release.yml`
   (по изменению VERSION в main; текст — раздел CHANGELOG). Руками теги не создавать.
