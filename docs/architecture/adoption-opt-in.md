# ADR: добровольный учёт проектов без сетевой телеметрии

Статус: предлагаемое аддитивное решение, независимый срез после состава 4.12.
Источник: запрос владельца знать число всех проектов, использующих Kit, с явным согласием
на прозрачный добровольный учёт. [Issue #1451](https://github.com/aleksandradovgopolova-boop/ai-ops-kit/issues/1451).

## Решение и нормативная граница

Запрет сетевой телеметрии из [ProductMetrics](https://github.com/aleksandradovgopolova-boop/ai-ops-kit/blob/main/context/product/ProductMetrics.md) и
[MetricCatalog](https://github.com/aleksandradovgopolova-boop/ai-ops-kit/blob/main/context/product/MetricCatalog.md) сохраняется. Код не создаёт сервер,
аккаунты, ключи или доступы, не отправляет данные. Поддерживается только локальный учёт и
передача файла самим владельцем вне Kit. Центральный сбор пока не реализован; его нельзя
объявлять работающим или включать на основании этого решения. Для сетевого транспорта
потребуется отдельное решение, согласованная политика получателя, удаления и хранения.

Существующий `reach register` продолжает отдельный экспериментальный контракт, который
включает имя проекта. Его согласие не действует на новый учёт. Новый экспорт имен не несёт;
старый реестр не смешивается с новыми показателями. Главная продуктовая метрика не меняется.

## Единица счёта и согласие

Проект задаёт случайный UUID в `.ai/project/adoption-id.json`, сохранённый в HEAD. Ни root
commit, ни URL, имя или путь репозитория не являются идентификатором проекта. Клоны,
worktree и ветки с этим файлом — один проект. У отдельного продукта, выросшего из шаблона или
форка, владелец создаёт новый UUID до включения учёта. Изменение ID вне HEAD отклоняется.
Невозможно автоматически определить, что два разных UUID обозначают один продукт: сохранение
одного ID во всех его копиях — явная ответственность владельца. Старые ветки без ID не
наблюдаются; мировой total из этого факта не выводится.

Согласие включается отдельной командой владельца конкретного проекта (`--owner`). Это
подтверждение полномочий пользователем, а не механизм аутентификации владельца. Решение
хранится в git-common, общее для worktree этой копии, но не наследуется новым клоном.
По умолчанию решение отсутствует и событийный подписчик ничего не пишет. Новый consent_id
появляется при повторном согласии. Идентификаторы псевдонимные: их можно связать между
выгрузками; абсолютная анонимность не обещается.

## Что подтверждает счёт

Установка наблюдается по локальному `.ai/managed/VERSION` допустимого формата. Это локальный
след установки на дату снимка, не доказательство её исправности или исторического присутствия.
Активность — минимум одно `run_completed` pipeline с положительным числом фактических
вызовов и провайдером, отличным от mock, после согласия внутри явно выбранного периода.
Подписчик использует существующую шину событий, ядро не зависит от новой аналитики.
Локально сохраняются только даты UTC (максимум последние 366 дат), без имён задач и содержимого.
Отсутствие даты означает `unknown`, не «проект не пользовался». Native-сессии, другие пути
выполнения, старые прогоны до включения и утраченные события пока не наблюдаются.

Локальное подтверждение доверяет процессу Kit и файловой системе владельца. Злоумышленник
с возможностью менять локальный код/FS может подделать такие данные: криптографического
доказательства пользовательской активности здесь нет. Сетевых и платных вызовов для проверки нет.

Экспорт строго ограничен: версия формата, тип записи, UUID проекта/согласия, состояние согласия,
дата снимка, состояния установки/активности, период и SHA256. SHA256 ловит повреждение, но
не подтверждает автора. Даже правильно пересчитанная подделка остаётся `self_reported` и
НИКОГДА не увеличивает локально подтверждённый счёт. Неизвестные поля, некорректные UUID,
подмена checksum, даты из будущего, некорректный период и признаки активности после отзыва
отклоняются до записи. Данные принимаются только из обычного JSON ограниченного размера.

## Отзыв и сводка

Отзыв удаляет локальные даты и запрещает дальнейшую запись. Терминальная отметка в git-common
сохраняется и после повторного согласия: выбранная старая копия не оживляет прежнее согласие. Его можно выгрузить как tombstone;
после импорта старое согласие с тем же consent_id не восстанавливается повторной доставкой.
Перед повторным согласием передайте получателю экспорт отзыва прежнего consent_id.
Повторное согласие создаёт новый consent_id. Отзыв одной копии не управляет согласиями других
клонов; владелец отзывает их отдельно. Без доставки tombstone получатель об отзыве не знает;
удалить уже переданные вне Kit копии файла автоматически невозможно. Tombstone хранит только
минимальные идентификаторы и факт отзыва для защиты от replay.

Сводка дедуплицирует по UUID. `owned/external/unknown` задаёт оператор по известному ему
отношению к проекту; конфликтующие оценки дают `unknown`. Непроверенные внешние сообщения
показаны отдельно, в том числе с заявленной принадлежностью `owned`; название внешнего раздела
описывает канал поступления, а не владение. Прямое локальное наблюдение, включая отзыв, вытесняет непроверенную запись
того же проекта из отдельного счёта. Периоды одного consent_id сохраняются раздельно,
а tombstone подавляет все его периоды. Ошибки читаются как неполное наблюдение. При пустом
наборе наблюдений наблюдаемый счёт равен 0, мировой total всегда `null/unknown`, полнота partial.
Stars, forks, downloads, поисковые упоминания в adoption не входят. Подтверждённые наблюдения
дают только нижнюю границу в принятой модели локального доверия; внешние заявления сами по
себе нижней границей подтверждённых пользователей не являются.

CLI-парсер и печать находятся в `ai_ops_kit/cli/adoption.py` (entrypoints), библиотека
`ai_ops_kit/engops/adoption.py` возвращает данные. Библиотека и помощник проверки байтов доставляются вместе с CLI: подписчик и CLI
требуют библиотеку, а владелец запускает процессный вход без системной установки пакета.

## Read-only проверка локальных свидетельств

Аддитивный `adoption evidence` проверяет один явно выбранный проект только после его
действующего согласия. Источник истины остаётся прежним: VERSION, installer provenance,
checksums, итоговый update-report. Installer/актуатор обновлений не меняется. Вывод содержит
только фиксированные состояния, версии, число проверенных файлов и причины; свободный
текст, имена, пути, source URL и сырые документы наружу не отражаются. Это локальная
диагностика, не новый формат export и не центральный сбор.

Полная согласованность локальных байтов называется `locally_consistent`. Это не доказывает
аутентичность manifest/source: произвольная подмена локального кода и FS за пределами модели
доверия. Report update с непустым успешным smoke и совпадающей целевой версией называется
`local_report_consistent`; ни это состояние, ни checksum не повышают внешний self-report
до verified. Недатированный report не подтверждает updated за окно. mtime и дата проверки
не заменяют source_at. Текущие provenance и update-report не имеют надёжной даты перехода.

Legacy state хранит только даты; он не позволяет определить, пришла ли дата из pipeline
или внесена вручную. Поэтому результат `unattributed_local_dates` не является
`verified_product_active`. Доверенный путь проверки описан ниже. Старые state/receipts/агрегаты сохраняют
смысл локальных наблюдений, а не подтверждений.

## Свежесть локального события

В run_completed ядро заполняет существующее необязательное поле KernelEvent.timestamp.
Подписчик использует этот timezone-aware момент в UTC, а не время повторного получения.
Принимается только текущий UTC-день и момент не из будущего; неизвестное/legacy время,
старая копия и доставка через UTC-полночь не пишут активность. Это консервативная потеря
наблюдения, не доказательство отсутствия использования. Дубликат текущего дня не пишет
state повторно. Формат state/receipt не меняется, старые даты не удаляются и не становятся
verified. Тест реального producer→subscriber подтверждает проводку без вызова моделей.

Timestamp — локальное заявление ядра, не криптографическое доказательство. Возможность
подделать новый envelope с новым временем при контроле процесса/FS этим не устраняется.
Повторное чтение JSON и дополнительный checksum не создают проверенного источника.

## Подтверждённая нижняя граница в отчёте

```bash
./ai-ops reach adoption report \
  --external /локальная/копия/проекта \
  --verification /локальная/квитанция.json --verification-sha256 SHA256_ИЗ_ДОВЕРЕННОГО_КАНАЛА
```

`verified_adoption` — аддитивный раздел прежнего отчёта. Без квитанции он показывает охват,
нулевую нижнюю границу проверенных продуктовых проектов и причину отсутствия подтверждения.
Старые `local_observed` и `external_self_reported_unverified` не являются verified.
Первая регистрация в проверенном продуктовом знаменателе требует действующего согласия
и однозначной проверенной идентичности. Parent, fixtures и спорные записи не увеличивают этот
знаменатель. `0` означает «столько подтверждено», а мировой итог остаётся `unknown`.

Квитанцию создаёт проверяющий, которому доверяет владелец сводки, после независимой сверки
источников. Она не принимается обычным `import` и не создаётся обычным `export`. Проверяющий
должен подтвердить, что checkout действительно представляет отдельный продукт, принадлежность
(`owned`, `external`, `unknown`), что источник установки соответствует официальному артефакту,
а выбранный коммит активности — реальная поставленная продуктовая работа с использованием Kit.
Изменение файла само по себе этого не доказывает. Install/doctor/CI, тестовые полигоны и исследования
про Kit не аттестуют как продуктовую работу. Пин SHA256 нужен из канала самого проверяющего,
а не вычисляется для произвольного присланного файла с целью объявить его доверенным.

Формат локальной квитанции: объект `schema_version: 1`, `projects` — объект с ключами UUID
проектов. На проект обязательны `kind` (`product`, `parent`, `fixture`), `relationship`,
`identity_commit` (полный SHA коммита с UUID), `consent_ids` (список явно одобренных текущих
согласий) и `observed_on` (UTC-дата проверки). Необязательные объекты:

- `installation`: `commit`, `version`, `release_commit` и `inventory_sha256`. Digest — SHA256
  канонического JSON только карты `files` из `.checksums.json` независимо проверенной поставки
  (`sort_keys=True`, `separators=(",", ":")`, UTF-8). Сверяются точная версия и Git-якорь,
  provenance релиза, digest карты, реальные байты каждого managed-файла и совпадающий
  полный инвентарь Git-объектов на закреплённом коммите.
- `activity`: `commit` и `path` реально изменённого продуктового файла. Проверяется история
  UUID/установки и непустой diff этого файла к первому родителю; служебные пути не подходят.
- `update`: `commit`, `from_version` и `from_tree_sha256`. Последний — SHA256 канонического
  JSON карты `относительный managed-путь → Git blob OID` независимо проверенной предыдущей
  поставки в формате объектов Git проверяемого проекта. Сверяются полный прежний инвентарь,
  прежняя версия и UUID в первом родителе и полный новый инвентарь в коммите перехода.
  Переход на ту же версию не считается обновлением.

Датой события считается UTC-дата выбранного Git-коммита, рассмотренного проверяющим, а не
mtime, время импорта или запуска отчёта. Проверка истории допускает только локальные объекты
из достижимых коммитов, без догрузки. Нужен checkout с сохранённой историей; shallow/неполный
checkout может дать unknown. Git-даты не подписываются этим механизмом; доверие к проверяющему
и выбранному им источнику остаётся обязательным. Непроверенный внешний receipt сам по себе
не может предоставить checkout, происхождение установки или доказательство реальной работы.
Переименование и перенос не меняют UUID; для независимого форка проверяющий требует собственный
UUID. Противоречащие копии с одинаковым UUID помещаются в карантин. Свежий opt-in после отзыва
требует новой привязки к проверке; tombstone действует на соответствующий consent_id.

Сводка локальна и не отправляется. В ней UUID проектов, но нет путей, Git SHA, текста, названий
или данных владельцев. Перед публикацией можно делиться только `lower_bounds` и `coverage`:
UUID псевдонимны, их не раскрывают для приватного проекта без отдельного согласия.
Публичная индексация не подключена; закрытые/offline/незарегистрированные проекты неизвестны.
