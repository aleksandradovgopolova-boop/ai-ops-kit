# Проектное подключение команды — эксперимент #1434

Это первый технический срез, не подтверждённая поддержка всех режимов Claude/Codex.
Доставка протокола через init/update, doctor и child CI включена в main через #1438.
Issue #1434 остаётся открыта; по умолчанию режим выключен (`off`). Для изолированной
квалификации добавляется `standard.team_session: required` в `.ai-ops.yaml`, затем
выполняется штатный init/update. Для отключения — `off` (либо YAML `false`) и update:
снимаются только собственные блоки/хуки кита.
По checkpoint 29.10 штатное обновление отдельного клона ИИ-среды сохранило настройки.
Частичный живой Codex CLI выявил неполный intake и цикл Stop; #1450 исправляет эти
разрывы, не подтверждая завершённое исследование или командную приёмку. Доставка
текущего кандидата в активный checkout, полная приёмка двух независимых аккаунтов,
её бюджет и окно обновления ещё не подтверждены. Продуктовый код ИИ-среды не меняется.

## Что сделано

Оба runtime получают один канон `.ai/managed/templates/runtime/team-session.md` через
ограниченные блоки AGENTS.md/CLAUDE.md. Установка/обновление сохраняют собственный текст,
ключи и хуки владельца. JSON с ошибкой и повреждённые маркеры не перезаписываются.
В `.claude/settings.json` и `.codex/hooks.json` подготавливаются SessionStart,
UserPromptSubmit и Stop. Они не меняют разрешения и не устанавливают доверие.

Hook сохраняет исходный запрос в существующей зоне `.ai/runtime/sessions/`, определяет
корень по фактическому cwd и привязывает его к ветке, HEAD, содержимому исходников,
версии/содержимому managed и конфигурации. Восстановление читает сохранённую задачу.
Внутренний вход запуска читает её из файла, вызывает существующий `./ai-ops run --execute`
и проверяет exit code, новый отчёт, WorkItem, RunPlan, целостность lifecycle-журнала,
runtime, фактическую revision результата и хэши файлов. Mock и план не принимаются.
Повтор одной попытки защищён эксклюзивной файловой заявкой.

Проверка внутри doctor блокирует повреждённое подключение при `required`; существующий
child-валидатор, вызываемый CI, проверяет те же файлы. Это проверка конфигурации,
не доказательство загрузки хуков конкретным аккаунтом и не серверная защита от
переписывания самого `.ai-ops.yaml`. Локальные записи не удостоверяют личность.

Отказ Stop завершает ход с `continue: false` и видимой причиной; он не создаёт
новый модельный запрос и не выдаёт квитанцию принятия. Это относится и к ошибке
чтения/привязки, чтобы сбой проверки не превращался в цикл расхода подписки.

## Основания по runtime

Локально обнаружены Codex CLI 0.147.0 и Claude Code 2.1.312 (`--version`, 29.10.2026).
Это инвентаризация, не доказательство поведения приложения/облака.
По [документации Codex](https://developers.openai.com/codex/hooks) project hooks требуют
доверенного проектного слоя и доверия к точному определению; специализированные tool-пути
могут не попадать в hook. Поэтому локальный hook не объявляется полной границей enforcement.
[Контракт Claude Code](https://code.claude.com/docs/en/hooks) описывает отдельные события
старта, пользовательского ввода и остановки; replay их JSON не заменяет реальную сессию.

## Минимальная живая приёмка

Это план будущего испытания, а не результаты. Нужны два реальных участника A/B
с независимыми аккаунтами и средами. Для первого опыта выбираются фактически
доступные Claude Code CLI и Codex CLI; результаты не распространяются на app/cloud.

Однократно перед испытанием оператор фиксирует один commit ИИ-среды, точную ревизию
кита, версии CLI, тип среды и независимость профилей. Каждый участник входит своим
разрешённым способом и подтверждает доверие точным проектным hooks в штатном UI.
Личные credentials не передаются другому участнику и не попадают в evidence.
До согласования окна активный checkout ИИ-среды не меняется: update проверяется
в отдельном клоне; затем та же ревизия доставляется штатным update через PR.

Четыре положительных запуска: A/Claude, A/Codex, B/Claude, B/Codex. В каждом
пользователь открывает проект и задаёт только естественный запрос:

> Исследуй агентную архитектуру ИИ-среды: сопоставь реализацию с приложенной
> методичкой, выдели подтверждённые пробелы и подходящие открытые решения.
> Сохрани результат и ссылки на факты.

Методичка должна быть реально доступна в каждой среде; её хэш записывается.
Испытатель не напоминает о ките и не вызывает CLI запуска. Оператор собирает
исходный запрос, runtime/session/request ID, checkout/version binding, журнал
реального исполнения, статус gates и артефакты RESEARCH. Успех подтверждается
содержимым артефактов и прохождением их контракта, не только локальным accepted.

На тех же профилях проверяются resume/compact, смена ветки и Claude ↔ Codex,
отключённый/неподтверждённый hook, отсутствие методички и устаревшее evidence.
Если отключение обнаружено только ручным чтением чата, либо runtime trust нельзя
автоматически установить, соответствующий критерий остаётся FAILED/UNKNOWN.
Наличие файлов и отдельный успешный CLI-вызов не закрывают эти сценарии.

От пользователя нужны:
1. Второй реальный участник и доступные типы сред обоих участников.
2. Согласие на четыре живых запуска и их бюджет. Предложение для согласования:
   до 8 логических callbacks на запуск, до 32 суммарно. Такой счётчик не даёт
   денежного лимита и не считает все внутренние повторные HTTP-запросы провайдера.
   Ограничение должно быть проверено до платного вызова; превышение требует
   отдельного решения, скрытого продолжения нет.
3. Доступная методичка с разрешением использовать её в выбранном контуре моделей.
4. Окно обновления ИИ-среды с владельцем активного релиза.

Создавать новые аккаунты, получать новые credentials, расширять права или включать
обход доверия для этого плана не требуется. До этих подтверждений живые вызовы
не запускаются, fixture-профили остаются только автоматическими проверками.

## Native finalize: specification и специализированный red team

`openspec.enabled: false` выбирает профиль `native-spec-first` из фактического
config рабочего дерева. Движок сверяет принадлежность и уровень `features/<wid>/spec.yaml`,
содержание обязательных разделов и настоящий `.ai/runplan/<wid>/requirements.yaml`.
Пустые, чужие, неподдержанные и ожидающие решения артефакты остаются blocking.
Результат называет `native_spec_valid` и `requirements_covered`; `openspec_valid`
не выдумывается. По умолчанию и при `true` остаётся настоящий strict OpenSpec CLI.
Произвольный сигнал задачи не переключает этот профиль.

`ai_red_team` не входит в generic same-model reviews. Политика допускает
независимую другую модель **или человека**.

### Машинное заключение

Поле `host_actions.model_jobs` явно показывает пассивный путь `collect-existing-host-review`. Хост может передать уже существующее свидетельство или воспользоваться заданием из `human_jobs`. Штатный `finalize` автоматически ищет сохранённое заключение по полю
`model_alternative.verdict_artifact` запроса. При переданном вручную digest
`ai_red_team` выбирается человеческий путь. Машинный JSON следует профилю
`#/definitions/model_red_team`, включая поле `request_sha256` с SHA-256
точных байтов запроса. Действуют те же четыре критерия и требования к
свидетельствам исполненных сценариев на проверенной ревизии.

Источником доверия служит отдельный системный сборщик, наблюдающий фактическое
исполнение. Он устанавливает канонические идентификаторы моделей после
маршрутизации, учитывает весь проверяемый результат автора, идентифицирует
реальный вывод судьи и подтверждает происхождение исполненных сценариев.
Сборщик атомарно предоставляет запись `observed-model-review` в системном
каталоге `/var/lib/ai-ops/model-reviews` (на macOS физический путь
`/private/var/lib/ai-ops/model-reviews`). Нормальный finalize только читает.
Каталог, каждый его предок и сам файл должны принадлежать root и быть защищены
от изменения пользователем; поддерживаются непривилегированные процессы POSIX.
Пакет не устанавливает системный сборщик и не выдаёт ему права.

Имя файла равно SHA-256 UTF-8 JSON полного scope (ключи отсортированы,
`ensure_ascii=False`, разделители `,` и `:`, без перевода строки) плюс `.json`.
Scope совпадает с привязкой человеческого пути и дополнен `request_sha256`.
Запись версии 1 содержит `kind`, `gate: ai_red_team`, `scope`,
`writer` и `reviewer` (у каждого `session`, `turn`, `execution: completed` и
`canonical_model_id` в общем пространстве устойчивых идентификаторов моделей),
`verdict_sha256` и `execution_artifacts` — отображение относительных путей в
SHA-256 исполненных артефактов. `reviewer` в самом заключении равен
`reviewer.session` из системной записи. Сборщик отвечает за подтверждение обеих
моделей и независимость исполнителей. При смешанном или неизвестном авторстве
он не выдаёт запись.

У Codex CLI 0.147 `thread/read` не сообщает фактическую модель завершённого
хода. В уведомлении `turn/completed` нет этого поля; отдельное уведомление
`model/rerouted` о смене модели не образует защищённой истории закрытых ходов.
HTTP-адаптеры кита в `providers/provider_calls.py` передают потребителю текст,
а в статистике учитывают запрошенную модель. Архива удостоверенных исходных
ответов обоих участников с привязкой к изменениям они не создают. У адаптера
Claude CLI модель для статистики берётся из ответа с возвратом к запрошенному
имени или `claude-code-local` при пропуске. Эта запись также не подтверждает
пару акторов. За границу доверия отвечает хост, запускающий неизменённый
проверяющий код в окружении, где автор не управляет системным томом или
пространством монтирования. Проверка из-под root отклоняется. Выбранная модель до исполнения и локальный файл, записываемый автором,
такой записи не заменяют. На этом хосте квалификация реального producer остаётся
открыта. При недостоверных входах доступен прежний человеческий путь.

### Заключение человека

Native finalize создаёт
отдельный scoped request и возвращает `host_actions.human_jobs` с человеческим вариантом. Это конкретное ожидаемое действие, а не уже выполненная атака
и не поручение обычному subagent. Независимый квалифицированный человек читает
весь base..HEAD, проверяет настоящие adversarial execution artifacts и пишет
reviewer-result по пути request. Профиль envelope —
`schemas/reviewer-result.schema.json#/definitions/human_red_team`; job объявляет
его через `result_contract_fragment`. Generic wire schema провайдеров не меняется.
Дополнительные поля: `reviewer_kind: human`, `review_role: ai-red-teamer`,
`review_root`, `managed_sha256`, `config_sha256`,
все scope-поля request и `attack_evidence` (kind/path/sha256/tested_revision).
Обязательные checks берутся из quality/gates.yaml. Pass без артефактов,
обычный code review, автор, чужая ревизия/root/config/managed и изменённый log
не принимаются. Артефакты ограничены: не более 32, 4 MiB каждый и 16 MiB суммарно.

Оператор получает SHA256 точного verdict из независимого человеческого канала
и передаёт `--review-digests '{"ai_red_team":"<trusted-sha256>"}'` вместе с
другими действительными digest. Code/JSON не удостоверяют личность по имени:
происхождение канала проверяет оператор, как у premerge. Автор не создаёт
человеческое заключение и не переименовывает fixture в реального участника.
Новые live/model вызовы не следуют из наличия request и требуют своего бюджета.
Все attack artifacts входят в completion hashes и повторно сверяются до accepted.

Этот путь не является per-finding security override. Неразобранные credentials,
SQL/command dataflow и неизвестное изменение прав инструментов сохраняют
strict blockers; человеческое `false-positive` и ApprovalRecord не заменяют
механическое доказательство безопасности. По имени тестового каталога и
наследованию строки из base находка не прощается.
