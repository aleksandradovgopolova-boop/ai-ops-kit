# Проектное подключение команды — эксперимент #1434

Это первый технический срез, не подтверждённая поддержка всех режимов Claude/Codex.
Протокол и его доставка идут отдельными PR. До принятия PR доставки описанные ниже
init/update, doctor и child CI ещё не подключены; сам протокол не активируется.
Issue #1434 остаётся открыта. По умолчанию прежние установки не меняются.
Для изолированной квалификации добавляется `standard.team_session: required` в
`.ai-ops.yaml`, затем выполняется штатный init/update. Для отключения — `off`
(либо YAML `false`) и update: снимаются только собственные блоки/хуки кита.
В ИИ-среду изменение пока не доставлено; окно обновления согласуется с владельцем
активной работы отдельно. Продуктовый код ИИ-среды не затрагивается.

## Что сделано

Оба runtime получают один канон `.ai/managed/templates/runtime/team-session.md` через
ограниченные блоки AGENTS.md/CLAUDE.md. Установка/обновление сохраняют собственный текст,
ключи и хуки владельца. JSON с ошибкой и повреждённые маркеры не перезаписываются.
В `.claude/settings.json` и `.codex/hooks.json` подготавливаются SessionStart,
UserPromptSubmit и Stop. Они не меняют разрешения и не устанавливают доверие.

Hook сохраняет исходный запрос в существующей зоне `.ai/runtime/sessions/`, определяет
корень по фактическому cwd и привязывает его к ветке, HEAD, содержимому исходников,
версии/содержимому managed и конфигурации. Восстановление читает сохранённую задачу.
Внутренний вход запуска читает её из файла, вызывает существующий `./ai-ops run --execute`
и проверяет exit code, новый отчёт, WorkItem, RunPlan, целостность lifecycle-журнала,
runtime, фактическую revision результата и хэши файлов. Mock и план не принимаются.
Повтор одной попытки защищён эксклюзивной файловой заявкой.

Проверка внутри doctor блокирует повреждённое подключение при `required`; существующий
child-валидатор, вызываемый CI, проверяет те же файлы. Это проверка конфигурации,
не доказательство загрузки хуков конкретным аккаунтом и не серверная защита от
переписывания самого `.ai-ops.yaml`. Локальные записи не удостоверяют личность.

Отказ Stop завершает ход с `continue: false` и видимой причиной; он не создаёт
новый модельный запрос и не выдаёт квитанцию принятия. Это относится и к ошибке
чтения/привязки, чтобы сбой проверки не превращался в цикл расхода подписки.

## Границы приёмки

| Критерий #1434 | Состояние этого среза |
|---|---|
| Старт/восстановление и смена проекта | Протокол проверен отдельными вызовами hook; настоящая сессия runtime не квалифицирована |
| Обычный язык и другой тип задачи | Общий канон передан runtime; естественный запрос → реальный workflow ещё требует живой проверки |
| Реальное исследование и его артефакты | Не подтверждено; controlled fixture доказывает только процессную границу учёта |
| Связь задачи/сессии/checkout/правил/запуска | Автоматические проверки локальной привязки и изменения файлов |
| Конкретная блокировка и сохранение постановки | Проверены пропавшая точка входа, повреждённые настройки, изменённые исходники; недоступная методичка требует живого сценария |
| Ноль ручного надзора | Не подтверждено живой приёмкой |
| Доставка в существующий проект | Штатный update --in-place в изолированной fixture и чистый clone; ИИ-среда ещё не обновлена |
| Два независимых аккаунта | Не проведено; два временных HOME не считаются аккаунтами коллег |
| Версионируемая общая настройка | Доставка правил и project hooks проверена; личные настройки и credentials не создаются |
| Один источник правил для двух runtime | Общий managed-канон, его версия и содержимое входят в привязку |
| Готовность среды | Проверяются файлы/Git/исполняемый вход; авторизация и runtime trust пока неизвестны |
| Пропуск процесса и gates | Stop не принимает отсутствие запуска; существующий движок остаётся судьёй готовности; административный обход вне защиты локальных hooks |
| Отсутствующее/чужое/старое подтверждение | Отрицательные FS/Git/session пробы; локальное evidence не считается required CI |
| Отрицательный командный сценарий | Удаление hook ловится существующим child CI; реальный аккаунт коллеги не проверен |
| Работа без надзора после настройки | Требует живого прогона обоих инструментов на одном commit |

Для закрытия нужны согласованная живая проверка Claude Code и Codex, две реальные
независимые среды/участника, доверие разрешённым механизмом, положительные и отрицательные
исходы, штатное обновление ИИ-среды и применимые CI точного head/base.
Платные вызовы за пределами согласованного бюджета и новые credentials не создаются.

## Основания по runtime

Локально обнаружены Codex CLI 0.147.0 и Claude Code 2.1.312 (`--version`, 29.10.2026).
Это инвентаризация, не доказательство поведения приложения/облака.
По [документации Codex](https://developers.openai.com/codex/hooks) project hooks требуют
доверенного проектного слоя и доверия к точному определению; специализированные tool-пути
могут не попадать в hook. Поэтому локальный hook не объявляется полной границей enforcement.
[Контракт Claude Code](https://code.claude.com/docs/en/hooks) описывает отдельные события
старта, пользовательского ввода и остановки; replay их JSON не заменяет реальную сессию.

## Минимальная живая приёмка

Это план будущего испытания, а не результаты. Нужны два реальных участника A/B
с независимыми аккаунтами и средами. Для первого опыта выбираются фактически
доступные Claude Code CLI и Codex CLI; результаты не распространяются на app/cloud.

Однократно перед испытанием оператор фиксирует один commit ИИ-среды, точную ревизию
кита, версии CLI, тип среды и независимость профилей. Каждый участник входит своим
разрешённым способом и подтверждает доверие точным проектным hooks в штатном UI.
Личные credentials не передаются другому участнику и не попадают в evidence.
До согласования окна активный checkout ИИ-среды не меняется: update проверяется
в отдельном клоне; затем та же ревизия доставляется штатным update через PR.

Четыре положительных запуска: A/Claude, A/Codex, B/Claude, B/Codex. В каждом
пользователь открывает проект и задаёт только естественный запрос:

> Исследуй агентную архитектуру ИИ-среды: сопоставь реализацию с приложенной
> методичкой, выдели подтверждённые пробелы и подходящие открытые решения.
> Сохрани результат и ссылки на факты.

Методичка должна быть реально доступна в каждой среде; её хэш записывается.
Испытатель не напоминает о ките и не вызывает CLI запуска. Оператор собирает
исходный запрос, runtime/session/request ID, checkout/version binding, журнал
реального исполнения, статус gates и артефакты RESEARCH. Успех подтверждается
содержимым артефактов и прохождением их контракта, не только локальным accepted.

На тех же профилях проверяются resume/compact, смена ветки и Claude ↔ Codex,
отключённый/неподтверждённый hook, отсутствие методички и устаревшее evidence.
Если отключение обнаружено только ручным чтением чата, либо runtime trust нельзя
автоматически установить, соответствующий критерий остаётся FAILED/UNKNOWN.
Наличие файлов и отдельный успешный CLI-вызов не закрывают эти сценарии.

От пользователя нужны:
1. Второй реальный участник и доступные типы сред обоих участников.
2. Согласие на четыре живых запуска и их бюджет. Предложение для согласования:
   до 8 логических callbacks на запуск, до 32 суммарно. Такой счётчик не даёт
   денежного лимита и не считает все внутренние повторные HTTP-запросы провайдера.
   Ограничение должно быть проверено до платного вызова; превышение требует
   отдельного решения, скрытого продолжения нет.
3. Доступная методичка с разрешением использовать её в выбранном контуре моделей.
4. Окно обновления ИИ-среды с владельцем активного релиза.

Создавать новые аккаунты, получать новые credentials, расширять права или включать
обход доверия для этого плана не требуется. До этих подтверждений живые вызовы
не запускаются, fixture-профили остаются только автоматическими проверками.
