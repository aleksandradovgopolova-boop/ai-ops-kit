# Автоматическое планирование собственного выпуска

Пульт кита пересчитывает следующий выпуск через существующий workflow
`status-dashboard.yml`: после изменения main, события issue, запуска/завершения
проверок и по ежечасной полной сверке. Выпуск, тег, оплата или обновление дочки
от этого не запускаются. План — read model, не самостоятельный релизный процесс.

## Откуда берётся состав

Один объект `release_plan` попадает в `dashboard/data.json` и встроенный снимок
HTML. Источники — default branch, последний опубликованный stable SemVer release
с разрешённым в commit тегом, полная первая линия Git между ними, связанные
merged PR, канонические closing-связи GitHub с issues, действующий delivery-plan/его история и реестры
проверок. Незавершённые задачи не расширяют ближайший состав; весь уже слитый код
в нём остаётся, включая изменения без подтверждённой связи с PR.

Версия считается существующим `release_assembly`: наличие новой возможности
поднимает minor, прочие записи — patch. Major автоматически не выбирается.
Канал проверяется действующим `validate_release_claims` для целевой версии; обкатка
предыдущего minor не превращает новый minor в stable.
Legacy `assemble.ready` продолжает означать только наличие состава и триггера.
После бампа целевая версия — версия checkout, а не дополнительный bump.

Опциональный корневой блок `release_intent` в `planning/plan.yaml` содержит только
объявляемые параметры, без вычисленного статуса:

```yaml
release_intent:
  id: kit-next-release
  milestone: Проверенный выпуск
  candidate_limit: 0
  deferred:
    cycle_version: 4.12.0
    issues: [1412]
```

Блок необязателен: без него действует текущая веха и состав из уже слитого кода.
Некорректный присутствующий блок — ошибка, а не возврат к широкому составу.
Отложенные issue относятся только к названной версии и не удаляют слитый код.
`candidate_limit` сейчас допускает только 0: автоматического разрастания состава
незавершёнными задачами нет. Зависимости работы `next-kit-release-X-Y-Z`
проверяются транзитивно; declared done без реализации и CI не считается доказанным.

## Что подтверждают состояния

- `composition_available`: состав известен из полной стабильной сверки. В состоянии
  `cycle_state: idle` он пуст и целевой версии ещё нет: это подтверждённое отсутствие
  новой работы после публикации, а не ошибка API или необходимость нового выпуска.
- `plan_ready`: определены состав, проверяемые связи со слитыми изменениями и зависимости.
  Это не утверждение об успешном CI: неизвестность исторического CI сама по себе не
  мешает определить состав. Неизвестная зависимость продолжает блокировать план.
- `release_ready`: дополнительно наблюдались stock release-проверки на точном итоговом SHA,
  включая полный набор, мутации, дренаж очереди и слой владельца. Старый CI этого не заменяет.
- `publication_authorized: null`: read model не предоставляет право выпускать.

В этом срезе существующие CI blockers сохраняются и продолжают запрещать
`release_ready`. План может быть определён при неподтверждённом выпуске; общий
статус такого результата остаётся degraded. Отдельное подтверждение всех 17
проверок release PR и прямой own-medicine не считаются выполненными этим разделением.
- `delivery.observed: unknown`: публикация кита не доказывает update, backup/restore,
  совместимость и живую приёмку конкретной дочки.

Закрытое issue без канонической связи с конкретным merged PR остаётся без подтверждённой
реализации. Само наличие PR также не доказывает все acceptance criteria: поле
`acceptance` остаётся unknown. Наблюдение CI не является независимым review или
разрешением stock `premerge`. Независимые ограничения из #1434 и общий rollback
#1406 не объявляются завершёнными.

## Ограничение исторического CI GitHub

Реальный read-only прогон 30.10 на merged PR #1440 подтвердил: GitHub может
очистить `workflow_run.pull_requests` и `check_suite.pull_requests` после merge,
хотя jobs остаются зелёными. В таком случае состав и версия вычисляются, но
точная историческая связь проверки с base остаётся unknown и не даёт readiness.
Повторный запуск или название CI не восстанавливают недостающий факт.

Идентификаторы в `display_title` — данные автора workflow, не независимая аттестация
использованной версии workflow. Совпадение заявленных Git-объектов само по себе не
доказывает, что именно этот run их исполнял. Такая эвристика не допускается как PASS.
Проверяемое сохранение исходной CI-привязки требует отдельного доверенного producer
или доступного платформенного evidence; новые права и trust policy этим срезом
не добавляются. Это конкретный остаток #1439, не основание закрыть всю issue.

## Неизвестность и повторные события

Read-only клиент проверяет страницы и `total_count`, повторно читает main, release,
issues, последние run/attempt и локальные policy inputs. Неполная страница, API403,
изменившийся источник, skipped/cancelled/rerun и неправильные SHA/base не дают
ложного PASS. Лимит полной сверки — 100 страниц на коллекцию; превышение — unknown.

Для истории переходов читается только вычисленный HTTPS Pages URL данного
репозитория без токена, с ограничением размера и redirects. Предыдущий объект
должен иметь правильный digest и совпасть с последним действительным deploy
trusted workflow/run/attempt/checkout. Проверка ограничена последними 100 run;
неизвестный prior, первый переход со старого пульта, задержка CDN и custom domain
не выдаются за пустую историю. Пересчёт состава продолжится, уведомление о переходе
в таком случае подавляется. Локальный tracked `data.json` доказательством не служит.

Семантический fingerprint исключает часы, идентификаторы publisher и завершение
каждой отдельной job. Повторное событие не создаёт новый переход при тех же фактах.
Сообщение о значимом результате появляется в пульте и summary существующего run
только после успешного deploy; отказ final freshness не оставляет старое зелёное сообщение;
это не доказательство push-доставки человеку. Писем, issue-комментариев и сообщений
в мессенджеры код не отправляет.

Публикации сериализованы существующим concurrency group без отмены deploy.
Job допускается только для ref default branch, в том числе при ручном dispatch.
Checkout — его `github.sha`, а не head внешнего PR.
Перед deploy ещё раз сверяются main, issues, run/attempt и финальные release jobs;
изменившееся evidence останавливает публикацию устаревшего плана.
Между последней проверкой и внешней публикацией остаётся небольшое race-окно:
следующий event/reconcile исправляет проекцию, право выпуска из неё не выводится.

## Проверка эксплуатации

Сборка: `python3 -m dashboard.build_data --repo . --release-plan`.
Она использует существующие read-права GitHub и Pages publisher без новых PAT,
permissions и зависимостей. REST-доступ к PR/close-events с Actions token должен
быть проверен живым запуском после merge; локальный пользовательский token или
fixture этого не доказывает. При отказе доступа не происходит перехода к более
сильным credentials. До живого event/reconcile/deploy evidence #1439 остаётся open.
