# Несколько сессий в одном репозитории

Документ появился по замеру, а не по опасению. **12.08.2026** в этом репозитории одновременно
работали несколько сессий, и за один день они испортили работу друг друга **тремя разными
способами**. Ни один из них не был замечен проверками — при том что у кита есть механизмы для двух
из трёх.

Это тот же класс, что R-21 («кит требует план от дочек, не имея своего») и F-022 («политика
объявлена, обязательна и не исполняется»), только про собственный процесс: **кит умеет
координировать параллельные сессии и не применяет это к себе**.

## Что именно случилось

| Промах | Как проявился | Цена |
|---|---|---|
| **Общее рабочее дерево** | Соседняя сессия сделала `checkout` + `pull` в общем корне — трижды за час. Мои незакоммиченные правки уехали на другую базу | Работа выжила случайно: файлы не пересеклись |
| **`git add -A`** | Коммит `4a231ae` с сообщением `docs(qualification)` унёс, помимо своей обкатки, чужой фикс CI-шаблона с тестами и чужой research-скан | Заявление шире сделанного; у фикса не осталось обоснования в истории |
| **Работа без заявки** | Два исполнителя независимо взяли из `planning/plan.yaml` один и тот же срез `providers` (PR #76 и #77), нашли один и тот же дефект, написали два набора тестов | Двойная работа + конфликт слияния. Обошлось дешево только потому, что выводы совпали |

## Три правила и чем каждое проверяется

Правило без проверки — это вежливость, а не правило. Поэтому у каждого названо, **что именно его
исполняет** и **чего сегодня не хватает**.

### 1. Одна сессия — один worktree

```bash
git worktree add ../kit-<моя-тема> -b engops/<моя-тема>
```

Это устраняет **причину**, а не симптом: чужой `checkout`/`pull` физически не может увести мои
правки, а `git add -A` не может захватить чужие файлы — их в моём дереве нет. Первые два промаха
исчезают вместе, без всякой дисциплины.

Проверять перед началом: `git worktree list` и `git status` — чужие незакоммиченные правки в общем
корне означают, что там кто-то работает **сейчас**.

*Механизма в ките нет.* Правило держится на исполнителе; кандидат на проверку — отказ хука
коммитить из общего корня, когда в реестре есть другие активные работы.

### 2. Заявить область записи ДО взятия работы

У кита для этого есть готовый реестр с межпроцессной блокировкой — `ai_ops_kit/lifecycle/active_work.py`.

**Реестр лежит в рабочем дереве, а заявка из него УЕЗЖАЕТ на носитель — и это две разные вещи.**
Первая редакция этого документа требовала считать особый путь через `git rev-parse --git-common-dir`,
потому что `.ai/runtime/active-work.yaml` лежит ВНУТРИ рабочего дерева: у каждого worktree он свой,
и реестр, созданный в одном, из другого не виден вовсе. Прескрипция была верной по сути и не
сработала дважды: команды кита (`run`, `next`, `status`) всё равно ходили по обычному пути, а
считать особый путь руками никто не стал. Правило, требующее особой команды, исполняется ровно
настолько, насколько о нём помнят.

С 20.08.2026 обычный путь ДОЕЗЖАЕТ сам. Заявка кладётся ещё и на носитель — файл на пару (машина,
работа) в общем каталоге git (`<git-common-dir>/ai-ops/claims/`), и его читают все рабочие копии
репозитория. Ни коммита, ни push для этого не нужно, в историю носитель не попадает и рабочее дерево
не засоряет (`git status` остаётся пустым). Заявка другой МАШИНЕ уезжает вторым транспортом —
опубликованной заявкой в `.ai/claims/`, и только при `team_coordination.publish: true`.

```bash
# ЗАПУСК ЧЕРЕЗ `-m`, а не по пути к файлу. `python3 ai_ops_kit/lifecycle/active_work.py …` падает с
# ModuleNotFoundError: запуск файла внутри пакета не кладёт корень репозитория в sys.path. Первая
# редакция этого документа предлагала именно такую команду — то есть протокол про «проверка обязана
# исполняться» сам содержал неисполнимую строку. Замерено попыткой её выполнить.
export PYTHONPATH=.
REG=.ai/runtime/active-work.yaml     # обычный путь; `--repo .` включает носитель и публикацию

# что уже занято — своим деревом И соседними рабочими копиями
python3 -m ai_ops_kit.lifecycle.active_work list "$REG" --repo .

# пересекается ли моя область записи с активными
python3 -m ai_ops_kit.lifecycle.active_work check "$REG" --repo . \
        --areas "ai_ops_kit/engine,ai_ops_kit/lifecycle"

# заявить. Та же работа или та же ветка у другой сессии — ОТКАЗ (код 1) с именем держателя, его
# рабочей копией и временем начала; перенять можно только словами: `--takeover --takeover-reason`.
python3 -m ai_ops_kit.lifecycle.active_work register "$REG" <work-id> --repo . \
        --branch engops/<моя-тема> --areas "<write_scope пункта плана>" --session <кто я>

# снять по завершении (`done` — только когда работа действительно закончена). Снимает с ОБОИХ
# носителей: оставленная заявка держала бы работу для соседней копии после её закрытия.
python3 -m ai_ops_kit.lifecycle.active_work finish "$REG" <work-id> --repo .
```

`--repo .` — не украшение: без него кит не знает, про какой репозиторий спрашивают, и носитель не
подключается вовсе (молчаливый переход на текущий каталог запрещён — он координировал бы не тот
репозиторий, называя держателя не той работы).

В ДОЧКЕ путь тот же и остаётся контрактом: `.ai/runtime/active-work.yaml` объявлен в манифесте, а
носитель работает поверх него — сессии в дочке обычно делят один checkout, и там реестра хватало и
раньше.

`shared_registry_path()` остаётся как есть — реестр, физически общий для всех копий. Носитель решает
ту же задачу, не переезжая: путь `.ai/runtime/active-work.yaml` объявлен в манифесте, и его переезд
был бы breaking change по раскладке `.ai/` (AGENTS.md).

Реестр атомарен (`durable_write`), берёт межпроцессный лок вокруг read-modify-write и считает
пересечения сам (`classify`, `find_cycle`). `delivery_plan` по этим же данным выводит работе статус
`blocked`, если её `write_scope` пересекается с активной — то есть **план сам скажет**, что работу
брать нельзя.

*Почему это не сработало 12.08:* ни одна сессия реестр не заводила вовсе. Механизм был, его просто
не звали — ровно та ошибка, которую кит ловит у дочек. И заведи его тогда кто-нибудь по
документированному тогда пути (`.ai/runtime/active-work.yaml`), он всё равно не помог бы: в разных
worktree это разные файлы. Обе половины дефекта — и невызванный механизм, и негодный путь —
закрыты здесь.

*Почему этого не хватило 19–20.08:* обе половины были закрыты только в этом документе.
`shared_registry_path` за восемь дней не вызвал никто, кроме тестов — тот же класс, что
«валидатор, не запускавшийся нигде», и цена вышла прямая: две сессии независимо собрали одну и ту же
интеграционную ветку, а один коммит остался вне веток. Замер на двух копиях 20.08.2026 до правки:
`next` во второй копии предлагал работу, которую держала первая, а `register` той же работы
возвращал 0 и не печатал ни одного отказа. Поэтому досягаемость встроена в обычный путь, а не
оставлена особой командой в документе: правило, требующее особого действия, — это пожелание.

### 3. `git add <пути>`, никогда `git add -A`

Перечислять пути — единственный способ гарантировать, что в коммит попало только моё. В общем дереве
`-A` берёт и чужое; в своём worktree он безопаснее, но привычка одна для обоих случаев.

Исполняется хуком `commit-contract` (стадия `commit-msg`): он запускает `commit_policy.check_commit`
на **проиндексированных** файлах и тексте сообщения. На том самом коммите `4a231ae` контракт даёт:

```
broad_scope: затронуто 5 верхнеуровневых каталогов (.research, planning, qualification,
             templates, tests) — похоже на несколько задач в одном коммите
```

То есть проверка **была права** — и не исполнялась нигде. Это замер в поле, которого ждал гейт:
`advisory-gates-obkatka` требует field evidence до ужесточения.

**Сегодня контракт советует, а не блокирует** (`enforce: advise`). Ужесточение до блокировки —
решение владельца, и оно записано в плане как `human_decision`, а не принято молча: правило
репозитория — сначала field evidence, потом ужесточение (`ROADMAP.md` → «Правила движения»).

### 4. Свои процессы — по своему pid, никогда по шаблону команды

ЗАМЕР 20.08.2026, оплачено в тот же день. Осиротевшие прогоны от остановленных задач конкурировали
за CPU, и уборка шла через `pkill -f "m pytest tests/"` — по шаблону КОМАНДЫ. Под него попал pytest
третьей сессии, работавшей в своём worktree: её прогон оборван без предупреждения, и узнала я об
этом только по чужому рабочему каталогу в `lsof`. На машине было три ленты, а не две.

Шаблон команды не различает сессии: у всех он одинаковый. Убивать — только по pid, полученному от
своей же задачи, и проверять рабочий каталог процесса (`lsof -a -p <pid> -d cwd`) прежде, чем
что-то трогать. Реестр заявок на работу здесь не помогает по построению: он координирует РАБОТЫ, а
не процессы, — и это названная граница, не дефект.

## Порядок в двух строках

1. `git worktree add` → `active_work check --repo .` → `active_work register --repo .` → работа.
2. `git add <пути>` → коммит (контракт проверит охват) → `active_work finish --repo .`.

## Чего этот документ НЕ решает

* **Одновременный push в одну ветку** — не наблюдался, механизма нет.
* **Адресация между сессиями.** Подпись коммитов на машине общая, а имена в `ListAgents` не говорят,
  кто в каком каталоге: 12.08 адресат был угадан неверно трижды. Заявка теперь называет рабочую
  копию держателя — но это «где», а не «как позвать». Надёжный канал для координации — комментарий
  в PR, а не сообщение сессии.
* **Живость сессии в соседней копии.** Заявка снимается, когда рабочая копия удалена или процесс
  вида `pid:` мёртв. Измеренная личность рантайма (`session:ab12cd34`) живёт дольше процесса, и «жив
  ли держатель» по ней не проверить — кит не угадывает, а оставляет заявку и предлагает `--takeover`.
* **Ужесточение контракта коммита** до блокирующего — ждёт решения владельца (см. выше).
