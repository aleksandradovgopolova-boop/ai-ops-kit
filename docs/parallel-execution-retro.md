# Разбор параллельного прогона плана (20–21.08.2026) и как сделать его автономным и быстрым

Четыре ленты (+координатор) за одну сессию построили операционный слой AI Ops (PR-1..PR-25):
Фазы 1–3 в main, Фазы 4–5 в хвосте. Прогон дошёл до цели, но с длинным хвостом чистки и с местами,
где требовалось участие владельца. Этот документ — чтобы следующий прогон шёл **без владельца** и
**кратно быстрее**. Он источник истины для параллельных прогонов; читается вместе с
`OS-LANES.md` (в worktrees) и `docs/parallel-work.md`.

## 1. Что реально замедляло — по убыванию цены

1. **DIRTY-беговая дорожка на `plan.yaml`.** Все ленты дописывали работы в один файл. Конфликты
   тривиальны, но каждый мёрж делал соседей DIRTY, и их пересводили. Рост ~N². САМАЯ дорогая статья.
2. **Derived-числа как общие точки.** Счёт валидаторов в `release-claims.yaml`, потолки в
   `delivery-budget.yaml` — одно число на всех. Каждая лента, добавив валидатор/файл, обязана его
   двигать; кто вливался вторым — получал устаревшее и пересчитывал. Тот же класс, что plan.yaml.
3. **Гейты меряют ВЕТКУ PR, а не итоговый main.** coverage и footprint проверяются на ветке. Каждая
   лента проходила порог в одиночку, но их код, сложенный в main, дрейфовал выше — и это всплывало
   на ПЕРВОМ следующем PR, а не на виновнике. main тихо ушёл выше потолка файлов (490→498), и никто
   не поймал.
4. **Мёртвый Python 3.9.** Пол стоял на EOL-версии без потребителей; каждый автор (и ленты, и я)
   спотыкался о 3.10+ синтаксис в CI-джобе, которая никого не защищала.
5. **Капкан обязательных статусов.** Удаление CI-джобы (`python39-compat`) не убрало её из
   ОБЯЗАТЕЛЬНЫХ контекстов защиты ветки — и ВСЕ PR зависли BLOCKED навсегда, пока владелец не
   выполнил одну admin-команду. Единственная точка, где участие владельца было вынужденным.
6. **Хрупкая ручная авто-очередь слияния.** Самодельный цикл-интегратор падал на таймаутах gh,
   один раз отчитался «влито» по факту ЗАПУСКА команды (а мёрж отклонён), один раз сверял SHA с
   пустой строкой. Полурешение вместо родного merge queue.
7. **Крупные недоинтегрированные PR из закрытых лент.** Лента 5 сложила всю Фазу 4 в один PR
   (+2589 строк) с незарегистрированным пакетом, четырьмя модулями на 0% покрытия и пробитыми
   потолками; сессия закрылась — весь долг лёг на координатора серией мелких правок.
8. **Мои собственные ошибки диагностики.** «coverage красный» дважды оказывался НЕ процентом
   (порог проходил), а упавшими тестами — регистрацией валидатора и derived-числами. Время ушло на
   неверную гипотезу до замера.

## 2. Ошибки по классам и durable-fix каждой

| Класс | Что было | Durable-fix | Статус |
|---|---|---|---|
| Общий `plan.yaml` | все ленты правят один файл → DIRTY-N² | координационные файлы — одна рука; работы — **вкладами-фрагментами** (`planning/incoming/*.yaml`), сборка централизованно | протокол+валидатор ✅ (#235/#236); фрагменты — работа `plan-contributions-via-fragments` |
| Derived-числа | счёт валидаторов/потолки — общая точка | считать **автоматически** из факта, а не держать число, которое каждый PR синхронит | новая работа: `derived-counts-are-computed-not-declared` |
| Гейт меряет ветку | coverage/footprint дрейфуют в main незаметно | мерить против **итога слияния** (merge queue) + пер-ленточная ответственность за своё покрытие | merge queue (ниже) + работа `gate-measures-merge-result` |
| Мёртвый Python | 3.9 без потребителей | пол = версия дочек (3.12); версия-совместимость ловится **локально** ruff, не в CI после пуша | ✅ #237 |
| Капкан статусов | удалили джобу, забыли из обязательных | при смене CI-джоб — синхронно править required contexts; **проверка дрейфа** «джоба ↔ обязательный статус» | работа `required-contexts-match-jobs`; описано в `parallel-work.md` |
| Ручная очередь | самодельный цикл, ложные «влито» | **родной GitHub merge queue + auto-merge**, не polling-скрипт | работа `merge-queue-not-handrolled` |
| Крупные PR лент | Фаза одним PR, долг на координатора | лента сдаёт **малыми PR по одной работе**, каждый green сам, code+tests+newsfragment; НИКАКОГО кода в чужой/общей территории | правило в `OS-LANES.md`; проверка размера PR |
| Регистрация нового | валидатор/пакет/модуль не в структурах | **локальный pre-push зеркалит CI**: checklist, layering, public-surface, footprint — красное до пуша, а не после | работа `local-check-mirrors-ci` |

## 3. Целевое состояние: прогон без владельца и кратно быстрее

Рецепт следующего параллельного прогона:

1. **Территории строго непересекающиеся**, объявлены `write_scope`, проверяются
   `validate_parallel_safety`. Общие файлы (план/история/решения/release-claims/budget) — НЕ трогает
   ни одна лента; вклады идут фрагментами, числа считаются автоматически.
2. **Лента сдаёт малыми PR** — одна работа = один PR = код своей территории + тесты + newsfragment.
   Никаких «вся фаза одним PR». Малый PR быстрее зеленеет и не копит долг.
3. **Локальный `./scripts/check-fast` зеркалит блокирующий CI** (ruff+target, checklist, layering,
   public-surface, footprint, быстрые тесты). Красное ловится ДО пуша — не тратится раунд CI.
4. **Слияние — родной merge queue** с auto-merge по green. Координатор не полит вручную; DIRTY не
   возникает (queue батчит и ребейзит сам).
5. **Гейты меряют итог слияния**, а не ветку — дрейф main невозможен.
6. **Ноль admin-точек для владельца:** required contexts синхронны джобам (проверкой), защита ветки
   не завязана на версионные джобы, которые потом удаляют.
7. **Закрытие ленты = её PR влиты ИЛИ переданы координатору с зелёным CI**, а не «сессия закрыта, а
   PR красный и осиротел».

При соблюдении пунктов 1–7 участие владельца не требуется, а хвост чистки исчезает: он весь родился
из нарушения 1, 2, 7.
