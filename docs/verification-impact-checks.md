# Проверки по влиянию изменений

Полный прогон нужен перед merge/release и при неизвестном влиянии. Для итерации небольшой
правки предусмотрен режим по умолчанию: он показывает весь найденный scope, выбранные файлы и
команду. Его зелёный результат означает только названный охват; он не заменяет полный CI,
совместимость Python, ночное покрытие, мутационные пороги и живую квалификацию.

## Локально в Kit

```bash
PYTHON=.venv/bin/python scripts/check-fast.sh
PYTHON=.venv/bin/python scripts/check-fast.sh --impact --plan-only
PYTHON=.venv/bin/python scripts/check-fast.sh --impact --base origin/main
PYTHON=.venv/bin/python scripts/check-fast.sh --impact --intent ready_for_review
PYTHON=.venv/bin/python scripts/check-fast.sh --impact --intent merge_candidate
```

Без аргументов используется impact с базой `origin/main`, включая уже закоммиченные изменения
ветки. `--all` запускает прежний весь набор `not slow`; явные pytest-аргументы сохраняют этот
старый путь. Другую базу можно назвать через `--impact --base REF`.
Режим impact сохраняет проверку окружения
и линтер; `--plan-only` не исполняет проверки. Scope включает staged, unstaged, untracked, удалённые файлы и, при
`--base`, изменения коммитов относительно merge-base. Неизвестный ref — явный отказ, не пустой scope.
Имена до и после rename сохраняются. Не используйте только последний коммит вместо полного diff.

| Изменение / стадия | Проверка продукта |
|---|---|
| Разрешённая проза (`docs/*.md`, newsfragments и перечисленные основные документы) | Product build/test exempt; линтер и подходящие валидаторы остаются |
| Существующие test-файлы, draft | Эти файлы и импортирующие их тесты; при неизвестных зависимостях полный набор |
| Исходники с распознаваемыми статическими зависимостями, draft | Тесты обратного транзитивного графа; каждый изменённый исходник должен иметь известный test impact |
| ready_for_review | Дополнительно тесты соседних исходников в затронутых каталогах |
| Критическая инфраструктура, executable Markdown, конфиги/fixtures, удаление, неизвестный runner, неполный граф | Полная настроенная команда |
| merge_candidate / release_candidate | Полный набор независимо от размера diff |

`explore`, `skip` и принудительный слабый tier не отменяют риск. Python dynamic imports
считаются потенциальными потребителями каждого изменённого исходника: все такие
файлы и импортирующие их тесты добавляются к выборке. Один динамический тест больше не
заставляет исполнять несвязанный корпус. Если загрузчик не имеет известных тестовых
потребителей, дерево не читается, есть ошибки разбора или символьные source-ссылки, остаётся
полный fallback. Динамические зависимости pytest fixtures через conftest, объявления
pytest_plugins, явные pytest plugins, а также JS aliases/re-exports остаются full:
их неявные потребители ещё не описаны статическим графом.
Если консервативная выборка охватывает весь корпус, выбирается полный профиль.
Локальная итерация Kit не включает nightly/release_gate; они остаются в своих маршрутах.

План дополняется сочетающимися классами documents / visual / ui_state_navigation / backend_api /
db_migrations / infra, причинами проверок и отдельными сценариями со статусом NOT_RUN.
Наличие сценария в плане не доказывает его исполнение; его приёмку подтверждает адаптер.

Impact и `evidence_collector` используют `shared/lifecycle_store`. Только полноценный PASS
при совпадении содержимого входов (включая executable mode), dependencies/lockfile, toolchain,
config, flags и среды разрешает reuse. По умолчанию охват входов консервативен: всё дерево,
кроме выделенных runtime/cache/dependency-каталогов; внешние зависимости обязан покрыть адаптер
контекста. Поэтому независимая правка документа может инвалидировать более широкий результат.
Нечитаемые входы/симлинки/неизвестный контекст запрещают reuse. Каждый запуск сообщает причину;
reuse — путь и основание. FAIL/SKIP/BLOCKED/NOT_RUN никогда не становятся PASS от кеширования.
Журнал хранится в runtime общего checkout, вне проверяемого worktree: запись evidence сама не
делает проверенный код грязным. Состояние Git учитывается дополнительно к содержимому файлов.
Python Kit имеет content adapter; произвольный продуктовый runner без адаптера исполняется
заново. Изменение входов во время проверки блокирует пригодность её результата.

Локальные receipts не являются авторитетным CI evidence и не пересекают его доверенную границу.
Документальный build CI Kit запускается на draft и не дублируется при ready_for_review;
package-quality сохраняет событие для ранее пропущенных обязательных проверок. Повторный review
применим только к той же базе, merge-base, точному diff, дереву и политике.

Команда pytest заменяет прежние positional roots на выбранные файлы, сохраняя распознанные
опции. Неизвестные опции, shell-композиции и coverage-команды не переписываются. Vitest получает
позиционные фильтры файлов, а не флаг Jest. `npm test` / `npm run test` сужаются только при точном
локальном script `vitest run`; другие scripts остаются полными. Multi-stack без доказанного
сужения каждого стека тоже остаётся full.

## Перенос в дочерний продукт

Политика общая: `ai_ops_kit/gates/verification_tiers.py` вызывается существующим `evidence_collector`.
Коллектор использует уже подтверждённый профиль продукта и сохраняет build/lint/typecheck.
CLI `python -m ai_ops_kit.devtools.evidence_collect_cli collect ROOT --changed ... --intent draft`
принимает intent; интегратор обязан передать **полный** diff. Прямой CLI коллектора требует
разрешённого Tool Broker и не является способом обходить его политику.

Контроллер отдельной работы передаёт финальный `verification_intent=merge_candidate`
через RunContext и execution pipeline в коллектор. Уровень определяется названной
фазой, а не наличием коммита или `open_pr`: полный настроенный набор выполняется и
без открытия PR. Пакеты последовательности и параллельной работы явно передают `draft`
и сохраняют affected/module-охват даже на immutable package SHA. Их готовность относится
к пакету; JSON-отчёт показывает охват. Итоговый aggregate отдельно требует полный
набор на integration SHA. Прямой draft-коллектор также сохраняет итерационный охват.
Неизвестный intent отказывает до исполнения; отдельного CLI-флага и обязательного
поля WorkItem/RunPlan нет. Подмена ревизии или грязное дерево по-прежнему не дают готовность.

В дочке нужны обновление доставленного runtime и проверка adoption на её реальном профиле.
Шаблоны `templates/ci/ai-ops-validate.yml` / `ai-ops-lint.yml` проверяют здоровье Kit/стандарты,
а не заменяют product CI. Нельзя переименовывать required checks или автоматически выкидывать
полную продуктовую регрессию. В ii-sreda существующий CI с coverage/мутациями и PostgreSQL
остаётся необходимым; этот локальный change его не меняет. Rollout отдельный, после review.

## CI Kit

Контрактные тесты имеют одного владельца в quality matrix: `contracts`. Четыре общих шарда
исключают `tests/contracts`; compatibility jobs сохраняют полный контрактный слой на разных
Python. Это удаляет повторные исполнения, сохраняя объединение node IDs. Coverage, nightly,
release и smoke не ослабляются. Время реального GitHub CI после изменения ещё не измерено.

Замеры 30.09.2026 и точные логи сохранены в локальном отчёте сессии. Полный прогон до оптимизации:
8647 passed, 37 skipped, 1238.87 s, CPython 3.14.7 macOS. Это не результат нового кода.


## Дорогие мутационные пробы

`python -m ai_ops_kit.devtools.mutation_probe ROOT --workers 4` проверяет весь реестр в четырёх
изолированных копиях. `--workers 1` возвращает последовательный режим; библиотечный `run()`
сохраняет последовательный default для существующих интеграторов. Параллелизм ограничен 1–4; CLI тоже сохраняет последовательный default.
Ночная проверка Kit использует четыре копии. Пробы с одинаковой тестовой командой живут в одном
worker и сохраняют общий базовый прогон; кеш существует только внутри этого запуска.

Не изменены набор проб и условия провала: красная база, выживший мутант и непроверенная проба
блокируют результат. Таймаут мутанта теперь считается непроверенной пробой. Цель мутации не
может выйти из своей копии через `..` или символьную ссылку. Исключение worker прерывает прогон,
не превращаясь в частичный зелёный отчёт. Такой режим дочке подключают отдельно, проверив,
что её тесты не разделяют внешнюю базу, порты и изменяемые ресурсы; копия файлов не изолирует
внешние сервисы. В текущей работе дочерние мутационные проверки не запускались.

## Профиль полного локального fallback

Impact CLI явно печатает `full_profile` и исполнимый `full_argv`, в том числе в `--plan-only`. Для `draft`, `ready_for_review` и `merge_candidate` полный fallback вызывает существующий `scripts/check-full.sh --pr`: все обычные fast/slow/contracts без nightly/release_gate. `release_candidate` сохраняет default `check-full.sh` с nightly (`full-current-python`). Это выбор локального профиля, а не изменение графа/подбора тестов или отмена обязательного exact-head CI. Неизвестное влияние по-прежнему требует полного набора своего профиля. Nightly и release gates выполняются своими существующими маршрутами; локальный успех их не заменяет. Ненулевой код проверки возвращается без подмены.

## Собственные outputs проверки

`lifecycle_store.run(..., output_contract=PYTEST_OUTPUTS)` применяется в Kit impact runner
только к pytest/check-full. Это закрытый контракт `pytest-hypothesis-cache-v1`: только
`.hypothesis/.gitignore`, `constants/<16 hex>[_nolimit]` и Unicode `charmap`/`codec-v2-utf-8`
JSON gzip. Tracked-файл даже по такому пути остаётся входом. Неизвестные файлы и конфигурация
под `.hypothesis/` не исключаются; symlink по-прежнему запрещает reuse.

Outputs **входят** в точный fingerprint. Только сравнение семантических входов до/после
свежего исполнения допускает изменение объявленных outputs. При успехе receipt привязан к
фактическому состоянию **после** исполнения: позднейшая подмена/удаление cache требует запуска.
Source, зависимости, lockfile, конфигурация, toolchain, flags, Git и значимая среда остаются
причинами invalidation. `input_observation` сохраняет before/after fingerprints, изменившиеся
компоненты и пути с digest/mode, без содержимого файлов и секретов. Старые BLOCKED не исправляются.

`CODEX_TOOL_CALL_ID`, как thread/session id, считается служебной метаданной вызова, а не входом
проверки. Исполнительская/access identity, `CI`, `PYTHONPATH` и остальные параметры сохраняются
в environment digest. Проверка действующей access policy выполняется независимо от cache.

## Тяжёлый запуск на общем хосте

`check-full.sh` использует `devtools.host_resource_cli` и общий POSIX slot
`/tmp/ai-ops-kit-heavy.lock`, не зависящий от checkout, git-common-dir или TMPDIR.
Унаследованный fd проверяется по inode и flock; одного env-маркера недостаточно.
Lock не удаляется и не снимается по TTL; после смерти держателя ОС закрывает fd.
Наблюдение native `ps` блокирует запуск при видимом стороннем тяжёлом процессе, не останавливая его.

Cooperating self-hosted runner может выполнить тот же wrapper:
`python -m ai_ops_kit.devtools.host_resource_cli --kind self_hosted_ci --owner runner -- COMMAND`.
Это точка подключения, а не уже подключённый product CI. Без wrapper остаётся окно между
наблюдением ps и стартом внешнего CI. Разные OS users требуют заранее доступного общего пути;
ошибка доступа блокирует запуск, права и security settings wrapper не меняет.
