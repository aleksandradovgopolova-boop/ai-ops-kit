# Change Brief — отклонение (снятие) стухших наблюдений-кандидатов (#1386)

## Результат

У наблюдений-кандидатов из прогонов дочек (`./ai-ops candidates`, `inbox`) появляется ОБРАТНЫЙ
глагол к `accept`: `./ai-ops candidates decline <id> [<id>…] --why "<причина>"` (синонимы
`dismiss`/`resolve`). Владелец снимает наблюдение как неактуальное — «уже исправлено в текущей версии
кита» или «протухло» — с ОБЯЗАТЕЛЬНОЙ причиной. Снятый кандидат уходит из активной очереди
`candidates`/`inbox` И НЕ деривируется снова на следующих прогонах, пока источник не изменится. План
работ при этом НЕ трогается: `decline` — не `accept`.

Повод (#1386, разбор хвостов #1321). До этого среза у наблюдений-кандидатов был ЕДИНСТВЕННЫЙ глагол
`accept` (заводит работу). Помеченных «уже исправлено» было нечем: оставался либо `accept` (завёл бы
ненужную работу), либо игнор. Стухшие наблюдения копились в инбоксе. При этом для мёртвых РАБОЧИХ
заявок авто-отпуск у кита уже есть (`work_reconcile` hard-timeout) — для наблюдений не было.
Асимметрия закрыта (ручная половина; авто-протухание — см. «Не входит»).

## Как персистится решение (почему не второй журнал)

Наблюдение-кандидат РЕ-ДЕРИВИРУЕТСЯ на каждом прогоне из своего наблюдения:
`intelligence.child_findings.project_findings` отбирает наблюдения в ОТКРЫТЫХ состояниях
(`delivered`/`accepted`) и строит из них кандидатов `cand-<obs-id>`. Значит, чтобы снятый не воскрес,
подавить надо ИСТОЧНИК, а не кандидата. Двусторонний канал наблюдений уже ведёт журнал решений:
`engops.kit_feedback.set_state` пишет состояние + причину + `decided_at` и в кит
(`findings/from-children/<id>.yaml`), и обратно в дочку (`.ai/kit-feedback/<id>.yaml`), если она на
месте. `decline` добавляет новое закрытое состояние `resolved` и переводит наблюдение в него:

- наблюдение уходит из ОТКРЫТЫХ → кандидат больше НЕ деривируется (подавление регенерации);
- запись честная: решение + причина + когда; история не стирается (не «забыли», а «снято, потому что…»);
- НОВОЕ отличное наблюдение получает НОВЫЙ детерминированный id → всё так же даёт кандидата (снятие
  одного не глушит будущие распознаваемые).

Второй журнал (ключ по id кандидата) стал бы ВТОРОЙ правдой о судьбе наблюдения и разъехался бы с
каналом на первой же правке — поэтому его НЕ заводим (инвариант «один источник истины»).

## Затрагиваемые пути

- `ai_ops_kit/engops/kit_feedback.py` — новое закрытое состояние `resolved` (с человеческим именем
  «снято (неактуально)»), причина для него ОБЯЗАТЕЛЬНА (`check`, зеркало правила `rejected`), и оно
  показывается среди решённых в `status`. `resolved` отличён от `rejected` («кит не согласен») и
  `became_work` («завели работу»): замечание было верным, но действовать по нему больше не нужно.
- `ai_ops_kit/planning/candidate_intake.py` — `decline_candidates(...)`: симметрия к
  `accept_candidates`. Причина обязательна; снимает ТОЛЬКО наблюдения-кандидаты (`source:
  child-finding`); персистит через `kit_feedback.set_state(..., "resolved", reason=…)`. Возврат
  решения в дочку — по `child.path` из доставленной копии; дочки нет → только кит-копия.
- `ai_ops_kit/cli/candidates_cli.py` — глагол `decline`/`dismiss`/`resolve` в диспетче
  `run_candidates`, подсказка «снять:» в листинге наблюдений, причина из повторяемого `--why`.
- `ai_ops_kit/intelligence/child_findings.py` — только комментарии: `resolved` в перечне закрытых.
- Тесты: `tests/unit/test_candidate_intake.py` (decline на уровне приёмки + CLI-обвязка),
  `tests/unit/test_kit_feedback.py` (состояние `resolved`).

## Инварианты

- **Аддитивно.** `accept`, гейты, пороги, floors безопасности, обязательные проверки — не тронуты.
  `decline` ничего не пишет в `plan.yaml`. `candidates`/`inbox` остаются READ-ONLY (запись идёт
  только по явному глаголу владельца `decline`, не на показе очереди).
- **Поверхность.** `candidates` — уже объявленный интент; `decline` — его подкоманда, НЕ новый
  top-level intent. `len(INTENTS)` (39), `HUMAN_ACTIONS`, `docs/api/public-surface.md`,
  `claim:commands-total` — не меняются. Число состояний `kit_feedback` в публичной поверхности не
  объявлено (внутренний домен канала), а CLI `kit_feedback.py decide` принимает `resolved`
  автоматически (`choices=list(STATES)`).
- **Снятый не возвращается.** Доказано тестом: после `decline` следующая деривация кандидата не даёт.
- **Новое наблюдение не заглушено.** Доказано тестом: снятие `obs-old` не мешает `obs-new` всплыть.
- **Причина обязательна.** На уровне CLI (отказ без `--why`) и на уровне данных (`check` отвергает
  `resolved` без причины) — две линии, как у улики дефекта.
- **Слои.** `planning` → `engops` — импорт в пределах слоя `capabilities` (уже используется
  `planning/drift.py`), не вверх.

## Failure modes

1. **`--why` не задан** → `decline_candidates` отвергает (CLI код 1), источник не тронут.
2. **id не среди актуальных кандидатов** → `skipped_unknown`, названо явно (не молчим).
3. **Кандидат не наблюдение** (роадмап-направление / недобравший исход — ре-деривируются из живого
   состояния, устойчивого ключа нет) → `skipped_unsupported` с честной причиной, НЕ подавляется
   наполовину.
4. **Дочка-источник недоступна** (исправлено в более новой версии кита / продукт закрыт) → решение
   ложится только в кит-копию; стража от записи `.ai/kit-feedback/` ВНУТРЬ кита — путь-страж в
   `_child_root_for`.
5. **Наблюдение не читается в ките** → `set_state` возвращает ошибку, она попадает в `errors`,
   остальные id обрабатываются.

## Доказательство

- `tests/unit/test_candidate_intake.py` — decline записывает `resolved`+причину+`decided_at` и
  убирает кандидата из деривации; без причины — отказ, источник цел; неизвестный id назван; новое
  отличное наблюдение всплывает; не-находка — honest skip; план байт-в-байт не тронут; CLI-обвязка
  (`run_candidates`): глагол доходит до операции и подавляет, без `--why` отказ, без id — запрос id,
  `accept` по-прежнему работает.
- `tests/unit/test_kit_feedback.py` — `resolved` записывает решение и закрывает наблюдение (и в кит,
  и в дочку, виден среди decided); `resolved` без причины невозможен.
- Регрессия поверхности зелёная: `test_ai_ops_cli`, `test_human_actions_facade`,
  `test_public_surface(_truth)`.

## Не входит (честная граница)

**Авто-протухание по времени ОТЛОЖЕНО.** `work_reconcile` hard-timeout — отдельный
РЕКОНСИЛ-шаг, а не часть показа очереди. Сделать авто-протухание наблюдений «правильно» значит либо
писать во время READ-ONLY деривации `candidates`/`inbox` (прямо запрещено инвариантом «inbox ничего
не пишет»), либо завести отдельный реконсил-проход/команду — это НЕ тесный срез. Поэтому ручной
`decline` реализован полностью, а авто-протухание (наблюдения старше порога / чей источник исчез
стареют сами, как мёртвые заявки) — явный follow-up: отдельный шаг `candidates reconcile`
(или ветка в существующем реконсиле), который переводит стухшие в `resolved` с машинной причиной.
`decline` реализован так, что этот шаг просто переиспользует тот же переход состояния.
