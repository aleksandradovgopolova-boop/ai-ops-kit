# Поставка восстановления runtime без повторного исполнения — #1434

**Результат.** Один независимый PR доставляет ограниченное восстановление процесса, автоматическую сверку завершённой проверки и deadline read-only CLI resume. Это подготовка поставки уже проверенного runtime-кода, не новый native-контракт и не подтверждение общей автономности.

**База и происхождение.** Локальная delivery-ветка создаётся от main `16c40a6a800ba17fa062b2edc19c510fd184b416`. Runtime-изменения происходят из `1875b177` и `4d0706fc`; семь production/test файлов переносятся byte-for-byte из последнего checkpoint. Исходная ветка `codex/1434-readiness-bounds-20261105` остаётся на `4d0706fc10e4508ee1516ea671b8cedaadb1ea94`, её предок `bc6ac056` и все старые receipts сохраняются. ACK/sessionId, readiness timeout, неактивные preflight producer/trace и их fixtures в delivery не переносятся. #1468 уже слит в main; #1469 остаётся отдельным design-only draft.

**Затрагиваемые пути.** `lifecycle/project_session.run_process` — одна повторная попытка только после EAGAIN/ETXTBSY до старта, общий deadline и cleanup. `execute` проверяет timeout до readiness/claim. `cli/project_session_completion.reconcile(finished_only=True)` и Stop-hook — сверка только durable finished outcome по прежним request/attempt/binding/hash/revision/gates. Подготовленная CLI run-resume ветка — отдельный read-only worker с deadline30 секунд, общим inline checker и scoped import path. Callback hooks остаются inline: их timeout15 секунд не расширяется новым worker. Подробности — [resume Change Brief](1434-resume-read-deadline.md).

**Инварианты и failure modes.** Не повторять исполнение после старта, неизвестного исхода, отмены, ненулевого exit или отказа доступа; не удалять execution claim. Не принимать чужой/изменённый/неполный отчёт, пустую квитанцию или неподтверждённый результат. Worker не меняет state/claim и не захватывает locks родителя; последнее относительное чтение фиксируется до I/O. Границы sandbox/runtime policy и approvals неизменны; это не новая security isolation. Нет моделей, новых credentials, trust, активации, публикации или merge на этапе подготовки.

**Доказательство.** Сначала сверить семь перенесённых blobs с `4d0706fc`; затем новый focused профиль process recovery + completion + bounded resume и core contracts/validators на delivery-базе. Positive: фактический marker ровно один раз; fail-closed: отказ после старта не повторяется, чужие receipts не принимаются; side effects: реальный OS FIFO read завершается, worker отсутствует, state/claim и locks сохранены. Старые 240 PASS/1 FAIL и успешный повтор48 не являются полным suite/compatibility matrix. Для новой delta нужны независимый entire-delta review, а после разрешённой публикации — CI точного head; локальные проверки его не заменяют.

**Delivery budget, до изменения реестра.** Независимое review выявило strict file breach:699 не меньше ceiling699. Две реальные stock init в synthetic `/tmp` fixtures с полной сверкой checksums/provenance дали main698 файлов/6334537Б, кандидат699/6341256Б; единственный новый asset — `ai_ops_kit/cli/project_session_resume.py`. Он вызывается установленным CLI и остаётся в поставке. По штатному `quality/delivery-budget.yaml` добавляется датированная запись только substantive_files699→700, measured698→699, с именем и child wiring этого модуля. Строгий `<` и тесты не меняются. Volume ceiling7063000 и reserve fraction0.10 сохраняются: остаток721744Б ≈10.22%. Сам budget registry не едет в child; stock after measurement повторяется на окончательном commit. В delivery добавляется четырнадцатый файл реестра, а не исключение worker из подсчёта.

**Недублирующая интеграция.** Открытый #1508 решает native-agent review handoff, а recovery — зависание/сбои. Обе работы меняют `cli/project_session.py` и completion, поэтому рекомендуемый порядок — #1508, затем recovery. До публикации сверяется actual main; если #1508 уже вошёл, нужны локальная интеграция его изменений, affected regressions и независимое review новой delta. Нельзя перезаписать его agent response или pending review requests восстановлением старых blobs. Публикация draft сама по себе не подтверждает merge admission или готовность child rollout.

**Новая база, до интеграционного кода.** Перед push main продвинулся в `a7c6723681c42c4bb7a6706dfb4e98910058b394` (#1508); прежний delivery92c47235 сохранён отдельной локальной веткой, исходный4d0706fc не менялся. Agent response сохраняется, но в prepared CLI resume формируется внутри того же worker: `response` из #1508 повторно вызывает binding и читает report/request files. Оставить этот вызов у parent означало бы вновь неограниченное I/O после bounded проверки. Observer передаётся в response/binding/scope/artifact reads. Полный ответ передаётся через приватный IPC-файл (до4MiB), stdout содержит только snapshot/request/response hashes. Parent проверяет квитанцию и неизменность всех исходных полей task; допускается только добавление host_actions, не изменение status/приёмки. Проверки: existing native-agent handoff suite, большой ответ >4KiB, блокировка второго managed read именно в host response, подмена ответа и прежние timeout/cancel/claim сценарии. Это перенос существующей read-only подготовки ответа, не новый dispatch/native-контракт.

Повторный stock-замер этой проекции на a7c67236:698 файлов/6345462Б →699/6353936Б; все checksums/provenance проверены. Предыдущие10.22% относятся только к исходной проекции16c40a6a, а не к новой базе. Текущий запас около10.04%; пороги7063000Б/0.10 не изменяются. После окончания rebase stock init повторяется на окончательном SHA: provenance включает имя ветки, поэтому точные итоговые bytes фиксируются отдельной квитанцией, не подменяются этим промежуточным замером.

**Поставка после merge — отдельный этап.** Выпуск по штатным gates, затем update-PR в каждый согласованный child с сохранением настроек и сверкой install footprint; не копирование файлов вручную. Toast checkout и исходная зависшая operation не используются для приёмки и не меняются этим этапом. Сначала disposable synthetic clone и проверки start/resume/timeout/Stop; рабочие child checkouts обновляются только в согласованное окно. Любая live/native приёмка требует отдельного конкретного лимита и разрешения. #1434 остаётся открытой.
