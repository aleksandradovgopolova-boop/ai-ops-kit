# R7: проверка команд после обновления сохраняет код возврата

Результат: `check-upgrade-path.sh` отказывает при сбое команды, даже если ошибка
не содержит Traceback; диагностический вывод и настоящий код доступны в логе.

Затрагиваемые пути: `answers()` и его четыре вызова (`next`, `status`, `model`,
installer `doctor`), отдельные unit-регрессии shell-helper. База — `073d1bfb`.

Инварианты: каждый вызов требует код 0, непустой ответ и отсутствие Traceback.
`next` возвращает 1 при отсутствующем/ошибочном плане или ошибках roadmap;
`status` — при повреждённом реестре; `model` — при ошибке модели;
`doctor` — при проблемах проверки установки. Это диагностические отказы, а не
успешные ответы для upgrade-гейта. Общий контракт 0/1/2 —
`docs/api/public-surface.md`; конкретные ветви — `_intent_next`, `_intent_status`,
`_intent_model`, `installer/doctor.py:cmd_doctor`. Других успешных кодов у этих
четырёх вызовов нет. Ненулевые коды не разрешаются ради зелёного результата.

Failure modes: ошибка без Traceback; пустой/пробельный ответ; Traceback при rc=0;
потеря argv с пробелами; игнорирование отказа одного из четырёх реальных вызовов.

Доказательство: извлечённая из скрипта функция и реальные строки её вызовов
исполняются в Bash с `set -euo pipefail`, команда `python3` подменена stub-функцией.
Проверяем успешный ответ, отказ, факт исполнения и точные argv через отдельный
журнал, все четыре команды и отсутствие OK после отказа. Ни моделей, ни сети,
ни установки в реальный проект. Целевые регрессии, core smoke, Ruff,
Bash syntax, ShellCheck и shfmt; локальный успех не заменяет compatibility CI.

Не входит: installer/rollback (R5), clean-install (#1397 уже исправлен), изменение
fixture/допусков ради успеха, issue/план (координатор — единственный writer),
push/PR/merge/tag/release.
