# Конечное ожидание read-only resume — #1434

**Результат.** `project_session run` для подготовленной current-session задачи не зависает бесконечно при проверке binding или артефактов. Весь существующий read-only validator переносится в собственный завершаемый worker с общим timeout 30 секунд. Deadline включает запуск, binding (обход managed, конфигурацию, source digest, Git) и чтение подготовленных артефактов; проверка времени между файлами не заменяет остановку заблокированного `read()`.

**Источник.** Сохранённые R4 trace/state toast-сессии `01a1a0b8-5cc5-77df-98f3-e4e0b2c630c4`: более шести минут, собственный SIGINT/130, traceback в managed `read_bytes()`, запись prepared/running сохранена, принятия нет. Точный файл и причина задержки неизвестны. Incident не повторяем и toast checkout не используем для тестов. Исходный инкремент `4d0706fc` сохраняется вместе с родителем `bc6ac05628705586972c8d528b6e6cf45f700480`; delivery переносит тот же runtime-код отдельно от неактивных preflight/trace helpers, на базу main `16c40a6a`.

**Затрагиваемые пути.** Только прямая CLI-ветка `project_session run` с уже prepared current-session задачей вызывает `cli/project_session_resume.validate`, без нового публичного интента. Worker исполняет прежние binding/hash проверки через `lifecycle/project_session`, получает неизменный snapshot задачи через приватный временный файл, возвращает только проверяемую квитанцию. Общий `resume_current` и worker используют один inline checker `project_session_resume.check`, но callbacks completion/continuation не запускают worker. Опциональный observer в binding/configuration/source hashing фиксирует относительный путь до resolve/stat/read. Observer по умолчанию отсутствует; значения хешей и правила соответствия остаются прежними. Повторная подготовка, отдельный provider и завершение задачи не запускаются.

**Процесс и locks.** Используется существующий `run_process`: собственная группа процесса, единый deadline и cleanup при timeout/SIGINT/SIGTERM. Worker не приобретает preparation/migration/request locks; их держит родитель CLI, поэтому повторного захвата и взаимного ожидания нет. Исключение выходит через прежние context managers и освобождает locks родителя. IPC/logs находятся только в приватном временном каталоге, не в checkout; при ошибке последняя диагностика выводится до его удаления. Timeout относится к worker validation, не ко всему CLI bootstrap: первоначальные `project_root`, load и приобретение locks до ветки resume не переносятся этим срезом. Нет новой гарантии real-time завершения при неисправности ядра/незавершаемом процессе ОС.

**Происхождение worker.** Минимальная версия проекта Python3.12 поддерживает `-P`. Worker запускается с `-P -m` и единственным PYTHONPATH — корнем той копии Kit, из которой импортирован parent `project_session`. Cwd продукта и унаследованный PYTHONPATH не используются для поиска модулей worker; остальные переменные окружения сохраняются. Отдельная отрицательная fixture содержит продуктовые `ai_ops_kit`, `yaml.py` и `sitecustomize.py` с marker side effect: worker должен успешно сверить snapshot без исполнения этих файлов. Глобальные настройки Python и права не меняются.

**Уточнение по независимому review ДО исправления.** Изначальное подключение worker внутри общего `resume_current` было неверным: этот API вызывается также из hooks с timeout15 секунд. Отдельная группа worker с deadline30 секунд могла пережить уничтоженный внешним runtime hook-supervisor. Worker переносится только в прямую CLI-ветку. Внутренние callbacks остаются inline, их существующий timeout/процессный контракт не меняется. Отдельная регрессия запрещает запуск worker из `resume_current`/completion callback. Это не устраняет оставшиеся неограниченные чтения внутри hooks — они требуют отдельного budget-aware решения, не скрытого расширения этого патча.

**Уточнение тестового scope.** Existing completion regression сохраняет полный запрет процессов во время `reconcile`. После восстановления handoff последующий прямой CLI `run` теперь обязан запустить ровно один read-only resume worker; тест проверяет точный тип команды и не разрешает повтор controller/verifier. Это уточнение ожидания теста, не изменение production-контракта reconcile.

**Инварианты.** Результат возвращается только после успешного кода worker и квитанции, привязанной к snapshot/request. Timeout, отмена, неверная квитанция и несовпадение binding/artifact не принимают результат, не изменяют задачу/claim и не повторяют исполнение. Проверки предыдущего resume сохраняются полностью. Изоляция прав не добавляется: границы sandbox и approvals runtime не меняются; worker является read-only по выполняемому коду, не новой security boundary. Нет моделей, trust/runtime changes, новых credentials, доставки или публикации.

**Failure modes.** (1) Заблокированное чтение managed; (2) заблокированное чтение подготовленного артефакта; (3) timeout/отмена при удерживаемых родителем locks; (4) чужой binding/изменённый артефакт; (5) ошибочная/отсутствующая квитанция worker.

**Доказательство.** Synthetic fixtures, не toast: положительный реальный worker и та же prepared запись; реально блокирующий FIFO `read` внутри инъекции чтения обычного managed/artifact файла (не доказательство причины incident); bounded завершение при сокращённом тестовом timeout; SIGINT/SIGTERM supervisor; отсутствие живого worker после возврата; неизменность state/claim и возможность заново приобрести locks. Проверки mismatch и malformed receipt не дают зелёного результата. Дополнительно targeted существующих session/continuation/completion путей, core smoke, Ruff, применимые валидаторы и независимое review точной delta.

**Не входит.** Исправление причины конкретного файлового I/O toast, изменение активного native-контракта, внешнее возобновление модели или полная автономность Codex. Worker запускается только для уже выбранной ветки read-only resume. Первичные проверки и остальные вызовы binding вне неё остаются отдельными путями.
