# #1439: автоматическое планирование выпуска по проверяемым фактам

## Change Brief до кода

**Результат.** После событий GitHub и полного reconcile существующий пульт получает
один машинный план следующего выпуска: целевая версия, слитый состав, связи
issue→PR→commit→release, зависимости, отсутствующее evidence и следующий шаг.
Владелец не собирает состав и не запускает обычный пересчёт вручную.

**Исходная база.** main `a2defae3880ee767b8e5943c3862d4948d54ceec` после #1440;
код #1442 уже включён. #1441 и работа #1403 над hybrid-политикой принадлежат другим
сессиям. #1434 не закрыт: отдельный clone update не равен живой приёмке двух аккаунтов.

**Пути.** Продолжить `devtools/release_assembly`, read-only `integrations/github`,
существующие модель/валидацию delivery-plan и dashboard. Состояние писать существующим
durable I/O, а не новым storage. Параметры optional `release_intent` в существующем
плане не содержат вычисленных статусов. Legacy `assemble.ready` не меняет значения.
Новые модули остаются в существующих доменах и имеют настоящий вызывающий путь.

**Инварианты.** Полный API snapshot, точные SHA/base/attempt и проверяемая ancestry;
closed issue не означает реализацию. Уже слитый код не вычёркивается из сборки.
План, готовность выпуска, разрешение публикации и подтверждённая доставка дочке —
разные факты. Недоступный API/неполная страница/битый prior state дают unknown,
а не пустой успешный набор. Каналы и SemVer — из действующих механизмов.

**Failure modes (5).**

1. Неверная связь issue/PR/merge или неполная пагинация превращают отсутствие evidence в PASS.
2. Старые CI, изменившаяся база/политика или начавшийся rerun сохраняют прежнюю готовность.
3. Повтор/перестановка событий и interruption создают разные планы или дубли уведомлений.
4. Privileged workflow исполняет PR head либо устаревшая публикация вытесняет свежий план.
5. Pages/summary объявляются доставленным человеку уведомлением; общий план выдаёт права
   на update/rollback дочек, оплату, release или изменение настроек.

**Доказательство.** Positive, fail-closed и side-effect тесты на реальные временные
Git-репозитории, state I/O и подменённый transport; no-write proof для GitHub/release/
дочек. Дубликаты/конкуренция/reordered/reconnect, closed-only issue, wrong SHA/base,
skipped/cancelled/rerun, API403/truncation, corrupt prior state и смена источников.
Независимый review, core и применимый CI точного final head/base. Для workflow/API/
publisher нужны прямые own-medicine наблюдения: fixture не заменяет Actions token
или действительный deploy. До такого доказательства соответствующий критерий
#1439 остаётся незакрытым, а проблема не уходит в молчаливый fallback.

**Публикация плана.** Использовать существующий status-dashboard workflow/Pages с
его текущими правами. Доверенный checkout default branch; metadata событий не
исполняется. Существующие workflow completion + issues и полный периодический
reconcile дают eventual обновление, не мгновенную реакцию на любой PR edit.
Previous published snapshot требует source/digest/publisher/deploy proof; unknown
history не равна пустому прошлому. Семантический transition исключает timestamps
и run-id; UI/summary не обещают push receipt человеком.

**Не входит.** Новый scheduler/пакет/зависимость/PAT/permissions; автоматический
merge, bump, tag, Release, оплаты или изменение protection/credentials; применение
к дочкам или общий fleet rollback #1406; чужие ветки и закрытие #1434.

## Разделение поставки

Координационный срез сначала уточняет write_scope и собственный evidence в
delivery-plan. Производственная реализация ещё todo; ветка текущей подготовки
отражена в реестре активных работ, а не выдаётся за уже начатый код. Производственный код идёт отдельным PR: существующий parallel-safety
контракт не смешивает plan/ROADMAP с изменением движка. Этот документ фиксирует
требуемое поведение и границы, а не объявляет автоматизацию реализованной.
