# #1446 — проверка сообщения о готовности выпуска на пульте

## Результат

Перед тегом workflow сообщает, что пульт показал готовность, только после чтения
опубликованного машинного плана и проверки его происхождения, версии, готовности
и SHA. Сейчас достаточно успешного запуска status-dashboard после начала ожидания:
такая сборка способна опубликовать план с blockers или уже другую main.

## Границы

Используем штатную проверку последней публикации Pages и её digest. Подтверждение
пишется в журнал существующего выпуска. Оно содержит версию, SHA и идентификатор
публикации. Ошибка сети, устаревшая проекция или незавершённая проверка сохраняют
advisory timeout. Запрет обхода release gates, права workflow и создание тега
остаются в штатных точках. Факты по конкретным дочерним проектам сюда не поступают.

## Проверки

Положительный сценарий — подтверждённая свежая публикация на SHA выпуска.
Отрицательные — чужая версия или SHA, более ранняя публикация, release_ready=false,
неподтверждённый deploy либо API. На искусственных входах проверяем отсутствие
записей и внешних действий. Включение в workflow проверяем по месту вызова между
прошедшими проверками и созданием тега. Проверка на живом выпуске требует самого
выпуска по обычному процессу.

## Квитанция для проверки после выпуска

Сохранить проверенный JSON, который уже выдаёт штатный наблюдатель перед тегом, в артефакте конкретной попытки release workflow. Сейчас единственная копия этого вывода находится в логе. Для прошлого выпуска состояние готовности страницы подтвердить задним числом не удалось.

Область — шаг ready_window, загрузка одной квитанции в GitHub Actions, инструкция и проверки. Сначала завершаются существующие проверки и наблюдение Pages, затем штатный выпуск может создать тег. Загрузка файла происходит после шага создания тега. Квитанция подтверждает только наблюдавшуюся готовность. Таймаут, сбой наблюдения и незавершённая запись не должны открывать загрузку. Имена различают повторные попытки. Проверим исполнение shell-шага на локальных примерах успеха и отказа, точность сохранённых байтов, условия и порядок загрузки. Ошибка архивации не меняет исход выпуска.

### Повторяемый сбой браузерной проверки при доставке

В обязательном CI #1610 и #1612 первый запрос Chrome о создании пустой вкладки превысил 15 секунд. Загрузка страницы ещё не начиналась. Для этого первого запроса выделяем до 60 секунд. На каждую последующую команду остаётся 15 секунд, отсчитываемых по монотонным часам; промежуточные события Chrome срок не продлевают. Существующие проверки страницы и разделение CI сохраняются. Проверяем обычное открытие на всех размерах и ограничение времени на потоке сообщений.
