# #1434 — отказ доступа до учёта запуска сессии

В режиме workspace-write Codex на macOS разрешил создать .ai/runtime и вернул EPERM при создании .git/ai-ops в том же новом клоне. Проверяем доступность носителя заявок до необратимой отметки execution-claim при запуске контроллера открытой сессии.

Контур: current_session после проверки подготовленной задачи, затем прежние claim_execution и регистрация контроллером. Проверка создаёт и закрывает временный файл в каталоге канонического реестра, определённом Git. Она не занимает работу, не открывает сам реестр для записи и не заменяет проверки под блокировкой при регистрации. Все рабочие копии используют прежний общий путь.

При отказе до запуска обычная команда сообщает причину и сохраняет возможность продолжить тот же запрос. После старта действуют прежние запреты на повтор. Проверки: доступная и недоступная директории, доступ изменился после успешной пробы, один запуск после устранения первичной ошибки, сохранение чужого реестра и claims. Режимы доступа Codex, реальные проекты и незавершённые прежние попытки не меняются.

## Проверка на macOS

Codex CLI 0.147.0, штатный sandbox в режиме workspace-write. В одноразовом Git-проекте создание .ai/runtime прошло, а mkdir .git/ai-ops вернул EPERM. После stock init и настройки fixture-проекта установленные intake и run были вызваны в той же песочнице. Run вернул 1, сохранил pending и точную причину. Каталог общего реестра отсутствовал, execution-claim и журналы процесса отсутствовали. Это проверка установленного CLI без модели. Сам доступ к общему реестру в данной песочнице остаётся ограничен.
