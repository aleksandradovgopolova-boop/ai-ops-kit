# Change Brief — дубль обязательного набора PR↔merge: безопасного среза нет без решения владельца (#1376)

## Результат

Это **design-only бриф**: ни один workflow, гейт, обязательный status-контекст и branch protection
**не тронуты**, issue #1376 **не закрыта**. Он отвечает на вопрос среза: можно ли убрать дубль
обязательного набора между `pull_request` (голова PR) и `push` (merge-коммит) безопасной правкой из
PR писателя — и показывает по данным репозитория, что **нельзя**: безопасный лёгкий рычаг уже
выбран, а оставшийся дубль структурный и снимается только решением владельца (merge queue). Вывод,
подкреплённый замером #1372 (`qualification/CI-END-TO-END-BASELINE-2026-10-26.md`).

## Что доказано (факты из репозитория, не предположения)

**Обязательных контекстов десять** (branch protection `main`, `strict: false` — «ветка обязана быть
свежей» ВЫКЛЮЧЕНА):
`smoke`, `lint`, `clean-install`, `pipeline-e2e (3.12)`, `upgrade-path`,
`quality (fast-1, …)`, `quality (fast-2, …)`, `quality (selftests-a, …)`,
`quality (selftests-m, …)`, `quality (contracts, …)`.

**Откуда они приходят.** Девять — из `.github/workflows/package-quality.yml` (матрица `quality`,
плюс jobs `lint`, `clean-install`, `upgrade-path`, `pipeline-e2e`). Контекст `smoke` — из
`pr-smoke.yml`, который идёт **только на `pull_request`** (на `push` в main его нет вовсе).

**Триггеры `package-quality`.** `pull_request: [opened, ready_for_review, synchronize]` **и**
`push: branches: [main]` **и** `workflow_dispatch`. То есть обязательный набор исполняется и на
голове PR, и на merge-коммите.

**Модель слияния — squash** (`allow_squash_merge: true`, вершины `main` имеют вид `… (#NNNN)`).
Merge-коммит — это **новый SHA**, которого до слияния не существует. Прогон на `push` в main —
**единственный** прогон на этом точном итоговом SHA (это и есть гейт направления #1321).

**Замер #1372.** Единственный доказуемый из `gh`-метаданных повтор — именно этот дубль PR↔merge:
обязательный набор `package-quality` идёт ~2× на одно влитое изменение (критический путь
`selftests-m` — 285…519 с каждый раз). Прочие категории повторов из метаданных не выводятся и за
ноль не выдаются.

## Что УЖЕ оптимально (рычаги, которые выбирать нечего)

- **Отмена устаревших прогонов PR уже включена.** В `package-quality.yml`, `pr-smoke.yml`,
  `docs.yml` стоит `concurrency` с `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`.
  Новый коммит того же PR отменяет прежний незавершённый прогон; прогоны `push` в main и разные PR
  независимы (ключ группы включает `github.event_name` и номер PR / `run_id`). Это и есть
  «безопасный чистый срез waste» из плана — он **уже сделан**, дополнительной экономии здесь нет.
- **`strict: false`** означает, что PR на устаревшей базе **не** форсируется к повторному прогону
  перед merge — лишнего обязательного прогона из-за требования свежести тоже нет.

## Почему наивный срез триггеров небезопасен

- **Убрать прогон на `pull_request`** ⇒ девять обязательных контекстов никогда не отчитаются на PR
  ⇒ branch protection не даст слить (отсутствующий required-контекст висит «pending» вечно).
- **Убрать прогон на `push` в main** ⇒ точный итоговый merge-SHA перестаёт полностью проходить
  обязательный набор ⇒ прямое нарушение #1321 («полный набор на точном итоговом SHA»).
- **`paths-ignore` / docs-only пропуск тяжёлого набора.** Пропуск всего workflow по путям оставляет
  required-контексты «pending» на docs-only PR ⇒ merge заблокирован. Вариант «скипнуть job, но
  отчитаться контекстом» (skipped считается за success) технически возможен, но требует
  детектора изменённых файлов внутри job; его ошибка классификации **тихо пропустит обязательный
  набор на коде** — ровно антипаттерн «объявлено, но не исполняется», против которого построены
  гейты кита. Это не минимальная и не безопасная правка без осознанного решения.

## Рекомендация (нужно решение владельца): merge queue

Единственный способ прогнать обязательный набор **один раз именно на итоговом коммите** — GitHub
**merge queue** (триггер `merge_group`). Очередь строит коммит-кандидат предполагаемого слияния на
временной ветке `gh-readonly-queue/main/…`, гонит на нём обязательный набор **один раз**, и при
зелёном переводит `main` ровно на этот коммит. Тогда:

1. **Владелец** включает merge queue в настройке branch protection ветки `main` и делает те же
   обязательные контексты обязательными на событии `merge_group`. *(Правка branch protection —
   только владелец; из PR писателя это недоступно и не делается.)*
2. В `package-quality.yml` добавляется триггер `merge_group:`; при желании `smoke` тоже начинает
   гонять на `merge_group` — это **усилит** #1321, т.к. сейчас `smoke` на итоговом SHA не идёт
   вообще (на `push` его нет).
3. Прогон на `push: branches: [main]` снимается как избыточный (коммит очереди уже прошёл), а
   прогон на `pull_request` остаётся лёгким предварительным сигналом (или сужается).

Итог: обязательный полный набор исполняется **один раз на точном итоговом коммите**; обязательные
контексты сохранены; branch protection не ослаблен; дубль PR↔merge устранён по существу, а не
отключением проверок.

## Решение, которое нужно принять (явно)

Нужно решение **владельца**: включить merge queue на `main` и перенести/добавить обязательные
контексты на событие `merge_group`. До этого решения дубль PR↔merge — это **корректная и безопасная
цена** сочетания «required-контексты обязаны быть на PR» + «полный гейт на точном итоговом SHA» при
squash-слиянии. Ни одна правка workflow на уровне писателя не снимает его безопасно.

## Что НЕ тронуто (граница честности)

Ни один `.github/workflows/*.yml` не изменён. Ни один гейт, обязательный контекст, порог покрытия,
security/mutation-пол и branch protection не ослаблены. Финальный полный прогон на точном итоговом
SHA и список required-контекстов — **в точности прежние**. Issue #1376 оставлена открытой: это
анализ и рекомендация к решению, а не его реализация.
