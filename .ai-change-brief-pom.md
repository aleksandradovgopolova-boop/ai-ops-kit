# Change Brief — 3.35 Product Operating Model

Источник: аудит владельца 2026-08-10 (два сообщения подряд, второе расширило первое). Первое
сообщение просило контур PLANNING & EXECUTION. Второе сняло сужение: обязателен не «набор
документов», а **модель продуктового репозитория из восьми связанных контуров**, у каждого свой
источник истины, и WorkItem связывает те контуры, которые изменяет.

Срез идёт после 3.34 (её релизный коммит лежит в рабочем дереве незакоммиченным — этот срез его
не касается и версию не двигает; запись идёт в `## [Unreleased]`).

## Что сегодня есть и чего нет

Замерено, а не предположено.

**Есть.** `context/` (product/system/team, 14 документов), `rules/meta/repo-onboarding.yaml`
(13 пунктов черновиков), WorkItem с ДЕТЕРМИНИРОВАННЫМ статусом из гейтов
(`lifecycle/workitem.py`), реестр активных работ с conflict forecast по зонам/контрактам/
зависимостям (`lifecycle/active_work.py`), RunPlan + atomic_planner (разбор ОДНОЙ задачи на
work packages), `work-graph.yaml` + PSD + IntegrationPlan (**внутризадачный** параллелизм,
`validate_work_graph.py`), Product Health, usage ledger, engops (commit/branch/env/deploy/cost).

**Нет трёх вещей.**

1. **Репозиторий не знает, куда он идёт.** `ROADMAP.md` есть у кита, у продуктового репозитория —
   нет ни файла, ни контракта. Направление не является артефактом.
2. **Нет уровня между направлением и прогоном.** WorkItem создаётся из фразы пользователя
   (`_wid_for`), а не выбирается из объявленной работы. Вопрос «что брать следующим» не имеет
   входных данных: `atomic_planner` разбирает задачу, которая уже выбрана человеком.
   `active_work.py` знает, что идёт СЕЙЧАС, но не знает, что должно идти после.
3. **Контуры не связаны.** WorkItem может закрыться, изменив React-компонент, при этом
   `context/system/DataMap.md` и API-контракт останутся прежними, и никто не покраснеет.
   Единственное исключение — architecture-сигналы из diff (3.15), то есть один контур из восьми.

## Результат

**A. Модель репозитория объявлена машиночитаемо.** `registry/product-operating-model.yaml` —
восемь контуров, у каждого: класс вопросов, на который он отвечает, источник истины (пути),
сигналы изменения (globs), роль-владелец. Модель — реестр, а не проза, потому что по ней работает
код: детект, гейт, doctor, onboarding. Роли работы отделены от исполнителей: план называет
`owner_role`, конкретный runtime выбирает роутер в момент запуска — вендорское имя в плане
запрещено ПРОВЕРКОЙ, а не соглашением.

**B. Planning & Execution стал артефактом.** `ROADMAP.md` (четыре горизонта: Сейчас / Следующий
результат / Дальше / Later) + `planning/plan.yaml` (`kind: delivery-plan`: цели по приоритету,
WorkItem'ы с `depends_on`, `type`, `owner_role`, `write_scope`, `affects`). Кит отвечает на четыре
вопроса в любой момент — `ai-ops next`: где мы, что идёт сейчас, что заблокировано и ЧЕМ, какую
работу имеет смысл взять следующей и почему, что можно вести одновременно и какими ролями.

**C. Статус работы не объявляется там, где его можно вывести.** `ready`/`blocked`/`waiting` —
ВЫВОД из графа зависимостей, статуса WorkItem'а (гейты) и реестра активных работ, а не запись в
файле. Объявленный `ready` при незакрытой зависимости — расхождение, и его видно. Человек
объявляет только факты, которых код не знает: `todo`, `in_progress`, `done`, `dropped`.

**D. Связность контуров проверяется.** WorkItem объявляет `affects` по контурам; кит выводит
затронутые контуры из diff и сверяет с объявленным. Три состояния, и `unknown` НЕ равен
`not_changed`: если у контура в этом репозитории нет ни одного сигнального пути, кит не умеет
его видеть и говорит `unknown`, а не «не менялось». Гейт `contour_consistency` вводится
**advisory** (правило roadmap: blocking — только после обкатки на child-репозиториях).

**Что НЕ входит в срез (объявлено, не сделано).** Back-fill модели в уже подключённые
child-репозитории (`ai-ops update`); перевод `contour_consistency` в blocking; вывод `affects` из
спеки до старта работы (сейчас — из diff после); связь плана с knowledge graph (кольцо
Intelligence, отдельный слой).

## Коллизия имён — решение №1

В ките УЖЕ есть `work-graph.yaml` (`validate_work_graph.py`, `schemas/work-graph.schema.json`):
разбор ОДНОЙ задачи на параллельные пакеты + ParallelSafetyDecision + IntegrationPlan. Это
уровень RunPlan, а не уровень продукта. Второй сущности с тем же именем в одном репозитории быть
не должно — «WorkGraph» из запроса владельца называется здесь **delivery-plan**
(`planning/plan.yaml`), а элемент плана — **WorkItem**, ровно та же сущность, что и
`features/<id>/workitem.yaml`. Это не переименование ради вкуса: совпадение id даёт настоящую
связь уровней — статус элемента плана выводится из WorkItem'а, когда работа началась.

## Три теста на capability

Для каждой новой возможности — positive, fail-closed, side-effect proof:
- **plan** — валидный план разбирается; битый/циклический план даёт ненулевой код (не «пусто, всё
  хорошо»); порча `registry/product-operating-model.yaml` краснеет в `validate_product_model`.
- **next_work** — READY считается по зависимостям; элемент с незакрытым human-решением НЕ
  попадает в READY; пересечение `write_scope` с активной работой исключает параллельность.
- **contours** — diff по пути сигнала даёт `changed`; отсутствие сигнальных путей даёт `unknown`,
  а не `not_changed`; заявленный `changed` без обновления источника истины даёт находку.
