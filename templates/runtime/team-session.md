# Проектный запуск AI Ops

Один канон для Claude Code и Codex. Используй фактический cwd и текущий checkout.
Начни с проектного контекста по `commands/task/ai-session-start.md` managed-слоя.
Обычный проектный запрос — поручение исполнить подходящий процесс по
`commands/task/ai-run.md`, а не показать команду пользователю.

Проектные hooks сохраняют исходную постановку. Когда hook сообщил идентификатор
сессии, классифицируй задачу по `registry/routing-policy.yaml` и запусти:

```sh
PYTHONPATH=.ai/managed python3 -m ai_ops_kit.cli.project_session run --runtime <runtime> --session <session_id> --signals '<JSON сигналов>'
```

Значения аргументов передавай безопасно, без интерполяции пользовательского текста в shell.
Постановку команда читает из сохранённого файла. Research — `task_type: research`:
«проведи ресерч», «исследуй архитектуру» и явный `ai-ops research` используют тот же
RESEARCH-контракт. Для другой задачи выбери применимый процесс, не по одному слову.
Размер/риск определяй по фактам; не понижай обязательные проверки ради запуска.
Права, approvals и бюджет остаются обязательными. Hook не запускает платные модели.
По умолчанию run готовит существующий controller-план для **тебя, уже открытого агента**.
Отдельный провайдер не нужен. Статус running с execution.mode=current-session означает
передачу стадий текущему агенту: прочитай WorkItem/RunPlan и исполни применимый workflow.
Это не accepted и не подтверждение пройденных проверок. Самоотчёт автора не заменяет
независимое review. Автономный pipeline с отдельной моделью выбирается только явным
`--autonomous` при наличии соответствующего разрешения и бюджета.

Вход `run` сначала проверяет обязательную спецификацию штатным Spec-First.
Ответ `status: pending` с `preparation` означает подготовку, а не исполнение:
заполни названную спецификацию из сохранённого запроса, устрани названные ошибки
и продолжи тот же `project_session run --runtime <runtime> --session <session_id>`.
Сигналы уже сохранены; передавать их повторно и просить пользователя повторить
постановку не нужно. До готовности спецификации не создавай результат задачи.
После resume сначала прочитай сохранённую задачу и её `preparation`/`next_step`.
Для prepared current-session повтор run читает ту же передачу без нового процесса:
это штатное восстановление после compact, в том числе после правок продукта.
Если уже существует claim автономного или незавершённого запуска, это другой исход:
автоматически повторять его, удалять claim, отчёт или создавать новый запрос нельзя.
При тайм-ауте исход остаётся неизвестным; проверь сохранённые process.*.log и артефакты.
Занятую блокировку команда диагностирует сразу. Повтор hook с тем же надёжным turn_id
не создаёт постановку; без turn_id нельзя склеивать разные запросы по их тексту.

Если нет checkout, методички, разрешения или доступного runtime, проверь причину
доступными средствами. Сохрани задачу, назови конкретное ограничение и минимальный
следующий шаг. Нельзя заявлять сопоставление с непрочитанным источником.

План, текст «готово», наличие этих правил и старый отчёт не подтверждают исполнение.
Локальная проверка запуска не заменяет контракт артефактов, независимое review и CI.
После смены проекта/ветки/кита используй новую привязку текущего checkout; после
resume/compact прочитай сохранённую постановку и проверь её актуальность.
