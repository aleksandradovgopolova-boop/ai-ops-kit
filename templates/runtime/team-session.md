# Проектный запуск AI Ops

Один канон для Claude Code и Codex. Используй фактический cwd и текущий checkout.
Начни с проектного контекста по `commands/task/ai-session-start.md` managed-слоя.
Обычный проектный запрос — поручение исполнить подходящий процесс по
`commands/task/ai-run.md`, а не показать команду пользователю.

Проектные hooks сохраняют исходную постановку. Когда hook сообщил идентификатор
сессии, классифицируй задачу по `registry/routing-policy.yaml` и запусти:

```sh
PYTHONPATH=.ai/managed python3 -m ai_ops_kit.cli.project_session run --runtime <runtime> --session <session_id> --signals '<JSON сигналов>'
```

Значения аргументов передавай безопасно, без интерполяции пользовательского текста в shell.
Постановку команда читает из сохранённого файла. Research — `task_type: research`:
«проведи ресерч», «исследуй архитектуру» и явный `ai-ops research` используют тот же
RESEARCH-контракт. Для другой задачи выбери применимый процесс, не по одному слову.
Размер/риск определяй по фактам; не понижай обязательные проверки ради запуска.
Права, approvals и бюджет остаются обязательными. Hook не запускает платные модели.
По умолчанию run готовит существующий controller-план для **тебя, уже открытого агента**.
Отдельный провайдер не нужен. Статус running с execution.mode=current-session означает
передачу стадий текущему агенту: прочитай WorkItem/RunPlan и исполни применимый workflow.
Это не accepted и не подтверждение пройденных проверок. Самоотчёт автора не заменяет
независимое review. Автономный pipeline с отдельной моделью выбирается только явным
`--autonomous` при наличии соответствующего разрешения и бюджета.

После исполнения стадий зафиксируй результат и выполни тем же агентом:

```sh
PYTHONPATH=.ai/managed python3 -m ai_ops_kit.cli.project_session finalize --runtime <runtime> --session <session_id>
```

Finalize запускает штатные проверки на committed HEAD, без моделей, установки зависимостей
и доставки. Не достраивай заключения судьи за него: команда создаёт scoped reviewer requests.
Передай их вместе с полным диапазоном base..HEAD реальному независимому read-only агенту/
оператору. Он записывает существующий reviewer-result/acceptance-result по указанному пути
и возвращает SHA256 через независимый канал. Затем повтори finalize с
`--review-digests '<JSON gate-id: trusted-sha256>'`. Не вычисляй хэш собственного вердикта
и не называй его независимым evidence. Результат read-only агента/tool в текущем ходе
не создаёт новый пользовательский ввод. Если оператор прислал digest новым UserPromptSubmit,
это уже новое input-событие: прежний verdict устарел, требуется review обновлённого scope.
Это та же доверительная граница, что у premerge:
форма и digest проверяемы, происхождение подтверждает вызывающий runtime.
Реальные approvals и обязательные gates сохраняются; их нельзя закрыть чужим review.
`accepted` здесь означает локальную готовность к ревью, не merge/release и не успех CI.
После него следующий настоящий запрос получает новый WorkItem, прежний claim остаётся.

Вход `run` сначала проверяет обязательную спецификацию штатным Spec-First.
Ответ `status: pending` с `preparation` означает подготовку, а не исполнение:
заполни названную спецификацию из сохранённого запроса, устрани названные ошибки
и продолжи тот же `project_session run --runtime <runtime> --session <session_id>`.
Сигналы уже сохранены; передавать их повторно и просить пользователя повторить
постановку не нужно. До готовности спецификации не создавай результат задачи.
После resume сначала прочитай сохранённую задачу и её `preparation`/`next_step`.
После подтверждённого prepared current-session handoff следующий пользовательский ход
продолжает ту же активную задачу. Hook сохраняет отдельную immutable квитанцию ввода
в ignored `.ai/runtime/sessions/…/<request>.inputs/`; прочитай её по пути из additionalContext,
затем продолжи `project_session run`. Исходные prompt, WorkItem, RunPlan и claim сохраняются.
Новые уточнения учитываются при последующем независимом review и finalize: старые verdicts
и отчёты относятся к прежнему составу ввода. Не публикуй payload квитанций в Git и не считай
слова «approved» или «согласовано» машинным ApprovalRecord.


Сохранение нового ввода не пересчитывает автоматически risk/size/workflow или критерии
приёмки уже prepared RunPlan. `run --signals` после handoff остаётся resume того же плана.
Если уточнение меняет классификацию или объём работы, требуется отдельное штатное
перепланирование; этот путь не предоставляет нового API перепланирования и не подтверждает
безопасность произвольного расширения scope по тексту. Фактический security diff и approvals
всё равно проверяются существующими gates. До подходящего плана и проверки изменённых
обязательств не объявляй задачу выполненной.

Надёжный turn_id задаёт идентичность события: текущий повтор идемпотентен, конфликтующий
или поздний повтор исходного/предыдущего хода закрыт. Если runtime не передал turn_id,
сохраняется новая delivery-only квитанция с `identity_scope: unreliable`; это не новая задача.
Для таких доставок нельзя гарантировать идемпотентность или обнаружить поздний повтор:
одинаковый текст не служит ключом. После accepted новый реальный ход создаёт новую задачу.
Продолжение также возможно до claim, если CLI уже фактически запросил недостающие
intake-поля или создал ожидающую заполнения spec для текущего агента. Сохранённый marker
содержит уже заданные signals; прочитай ответ пользователя и передай недостающие значения
явным JSON через `--signals` (он дополняет сохранённые signals). Hook не извлекает значения
или approval из текста. Fresh pending без такого запроса данных остаётся границей отдельных
задач: нельзя угадывать продолжение по смыслу prompt. Unknown/autonomous claim или
подготовку автономного запуска нельзя продолжить таким способом. При занятой блокировке hook явно отказывает;
не обходи отказ созданием замещающей задачи или удалением claim.

Для prepared current-session повтор run читает ту же передачу без нового процесса:
это штатное восстановление после compact, в том числе после правок продукта.
Если уже существует claim автономного или незавершённого запуска, это другой исход:
автоматически повторять его, удалять claim, отчёт или создавать новый запрос нельзя.
При тайм-ауте исход остаётся неизвестным; проверь сохранённые process.*.log и артефакты.
Выполни `project_session reconcile --runtime <runtime> --session <session_id>`: команда
перечитывает durable исход своей попытки без повторного процесса. Готовый controller-план
можно восстановить как prepared; приёмка результата требует отдельного finalize.
Если подтверждённого отчёта проверки нет, повтор не разрешается автоматически. Известный
неуспех можно исправить и снова проверить той же finalize, сохранив историю попыток.
Занятую блокировку команда диагностирует сразу. Повтор hook с тем же надёжным turn_id
не создаёт постановку; без turn_id нельзя склеивать разные запросы по их тексту.

Если нет checkout, методички, разрешения или доступного runtime, проверь причину
доступными средствами. Сохрани задачу, назови конкретное ограничение и минимальный
следующий шаг. Нельзя заявлять сопоставление с непрочитанным источником.

План, текст «готово», наличие этих правил и старый отчёт не подтверждают исполнение.
Локальная проверка запуска не заменяет контракт артефактов, независимое review и CI.
После смены проекта/ветки/кита используй новую привязку текущего checkout; после
resume/compact прочитай сохранённую постановку и проверь её актуальность.
