# Architecture

Единственный источник правды об архитектуре **AI Ops Kit**: что построено, что осознанно не
построено и почему, куда идём и какие решения в основе. Дополняющие документы (не дублируют):
инструкция для агентов — [AGENTS.md](AGENTS.md); карта файлов — `FILE_INDEX.md`; инженерный
стандарт как продукт кита — `docs/engineering-standard-requirements.md`; решения-исследования —
`.research/decisions/`; границы пакетов и слои — `packages/layering.yaml`.

## 1. Context

AI Ops Kit — переиспользуемый пакет (parent) AI-first операционной системы для команд: агенты,
workflow-контракты, quality gates, маршрутизация моделей, управляемые обновления дочерних
репозиториев. Здесь разрабатывается сам пакет; в продуктовые репозитории он ставится через
`installer/ai_ops.py init` и ведёт продуктовую задачу процессом `specify → plan → run`.

Пользователи: владельцы продуктовых репозиториев (часто не разработчики) и AI-агенты-runtime
(Claude Code, Codex, Qwen). Оператор пакета — его сопровождающие. Кит фордж-нейтрален: не зависит
ни от GitHub/GitLab, ни от типа репозитория (личный/организация).

## 2. Goals

- **Registry — источник истины.** Поведение объявлено данными в `registry/`, а не зашито в код;
  расхождение объявленного и реализованного краснеет тестом.
- **Честность вместо ложной зрелости.** «Готово, но проверено не всё» называется так; недоказанное
  не выдаётся за доказанное (writer ≠ judge, capability-декларации честные, built ≠ wired).
- **Управляемая доставка в дочку.** Обновление приходит как PR, managed-слой цел и версионирован,
  дрейф детектируется.
- **Низкая цена инструментов.** Python-инструменты — на stdlib + pyyaml; новых зависимостей нет без
  явного решения.

## 3. Non-goals

- **Новые рантайм-зависимости** у инструментов — отклонено (stdlib + pyyaml).
- **Автогенерация человеческих документов из машинных** — отклонено: проверяется отсутствие
  противоречия yaml↔текст, а не происхождение одного из другого.
- **Кит не выдумывает продуктовую правду дочки** (направление, архитектуру, приоритеты) —
  `reconstruction`-модель помечает `unknown`/`needs_human`, а не правдоподобный текст.
- **Блокирующих quality-гейтов MVP > 8** — бюджет не растёт молча.
- **Пятое дерево `standards/` рядом с `registry/`/`rules/`/`templates/`** — стандарт ссылается на
  существующие реестры, а не заводит вторую правду.

## 4. System Overview

Кит — пакет `ai_ops_kit/` (код движка) плюс прозаический слой (`registry/`, `agents/`, `workflows/`,
`rules/`, `templates/`, `context/`) и установщик `installer/ai_ops.py`. Движок разложен по пакетам
со слоями `foundation → primitives → capabilities → intelligence → entrypoints`; зависимость вверх
запрещена (`validate_layering.py`, замер как потолок-ратчет). Запуск модулей —
`python3 -m ai_ops_kit.<пакет>.<модуль>` (плоский слой `tools/` снят в 4.0).

## 5. Components

- `ai_ops_kit/` — код движка по пакетам: `shared`/`context`/`engine`/`gates`/`providers`/
  `lifecycle`/`planning`/`intelligence`/`delivery`/`engops`/`security`/`ui`/`cli`/`devtools`.
- `ai_ops_kit/planning/` — контур Planning & Execution: модель контуров продукта, delivery-plan,
  ROADMAP-контракт, отбор следующей работы, понимание репозитория при онбординге.
- `ai_ops_kit/validation/` — валидаторы (Python, только pyyaml); единственная зона, из которой
  скрипты запускают напрямую (`import _bootstrap`, двурежимный).
- `installer/ai_ops.py` — CLI `ai-ops`: init/update/doctor/status и доставка managed-слоя в дочку.
- `registry/` — машиночитаемые реестры (агенты, workflow-контракты, провайдеры, модели, среды,
  capability-index, routing-policy, product-operating-model, artifact-registry).
- `quality/gates.yaml` — реестр quality gates (blocking ≤ 8).

### Концептуальные слои (роль пакета)

Пять слоёв выше (`foundation → … → entrypoints`) — по направлению **зависимостей**. Поверх них —
четыре концептуальных слоя по **роли** пакета в продукте: чтобы 19 top-level пакетов читались как
доменная модель, а не как история разработки, и чтобы не утонуть в собственных абстракциях. Слои
ортогональны (роль-слой пакета не равен его dependency-слою), маппинг документарен — **без переезда
файлов**; он объявлен данными в `packages/layering.yaml` (`conceptual_layers`) и там же проверяется
ратчетом: каждый пакет отнесён ровно к одному роль-слою, новый — обязан быть классифицирован.

- **DOMAIN** — продуктовые сущности и доменные контракты (Work / Run / Outcome / Decision, порты,
  общий фундамент): `kernel`, `lifecycle`, `shared`.
- **APPLICATION** — как ведётся работа (Workflow / Planning / Execution / Learning): `context`,
  `engine`, `planning`, `delivery`, `engops`, `intelligence`.
- **POLICY** — что разрешено и что проверяется (Governance / Security / Quality / Autonomy):
  `gates`, `governance`, `security`, `checks`, `validation`.
- **ADAPTERS** — мосты к внешним поверхностям (CLI / GitHub / Claude / Codex / Qwen / CI):
  `cli`, `integrations`, `providers`, `ui`, `devtools`.

Число top-level пакетов — **потолок** (`package_ceiling`, сейчас 19): новая capability живёт в
существующем домене, а рост числа пакетов требует архитектурного решения (ADR/DP), а не привычки
«каждая capability — свой пакет». Ратчет ходит вниз.

## 6. Orchestration

Продуктовая задача ведётся процессом `specify → plan → run` (intent-CLI). Прогон изолируется в
worktree, фиксируется на точном коммите (SHA) и собирает evidence на нём. Стадии workflow ссылаются
только на существующие agent id и gate id; стадия `review_mode: read-only` не может быть writer'ом
(writer ≠ judge). Гейты закрываются валидатором, судьёй, писателем или человеком — и отчёт называет,
кто закрыл (`closed_by`).

## 7. Data Flows

Источник истины — реестры (`registry/`, `manifest/ai-ops-manifest.yaml`); код их читает и краснеет
на расхождении. Установка в дочку: managed-слой `.ai/managed/` перезаписывается целиком, зоны
`.ai/project/` и `.ai/custom/` не трогаются; обязательные артефакты сеются черновиками (`status:
draft`), существующие файлы владельца не перезаписываются никогда.

## 8. API Architecture

Внешние контракты — `schemas/` (JSON Schema, публичная поверхность: breaking — только major).
Интерфейс кита — CLI (`installer/ai_ops.py` для дочки; intent-CLI движка). Незаявленной проверки не
существует, объявленной без реализации — тоже (сверяется тестами публичной поверхности).

## 9. Data Architecture

Состояние — файлы в репозитории: реестры (yaml), managed-слой дочки (`.ai/`), журналы отчётов
(`.ai/project/report-history/*.jsonl`, сводятся при слиянии дописыванием), провенанс и контрольные
суммы установки (`.provenance.json`, `.checksums.json`). Отдельной СУБД нет.

## 10. Authentication & Authorization

Не применимо в классическом смысле: кит — инструмент разработки, а не сетевой сервис. Права на
изменение управляются через зоны репозитория (managed vs project vs custom) и защиту веток форджа.

## 11. Security Boundaries

Эталонный контейнер изоляции движка — `containers/` (jail: Dockerfile + run-sandboxed.sh, сверяется
`validate_container_assets.py`). Инструменты не тянут сеть и живут на stdlib + pyyaml.
Capability-декларации честные: нельзя объявить возможность, не реализованную в коде.

## 12. External Dependencies

- **Python stdlib + pyyaml** — инструменты и валидаторы. Critical: без pyyaml реестры не читаются.
- **git** — движок работает через worktree/коммит и собирает evidence на SHA. Critical.
- **AI-runtime** (Claude Code / Codex / Qwen) — исполнитель writer/judge-стадий. High: без него
  прогон не идёт; кит остаётся фордж- и runtime-нейтральным (политика в реестре, адаптер в CLAUDE.md).

## 13. Deployment Architecture

Кит доставляется в дочку установщиком; обновление приходит как PR (`ai-ops-update.yml`), отставание
ловит `check-update`. Версионирование — SemVer (`VERSION`, `CHANGELOG.md`); `package_version` меняется
только при релизе. Инварианты и тесты гоняет CI (`.github/workflows/`).

## 14. Scalability

Масштаб — по числу подключённых дочек и объёму тестов пакета. Стена скорости CI — ОБЪЁМ тестов, а не
число файлов. Горизонтального сервиса нет: кит — пакет, не рантайм-сервис.

## 15. Reliability

Прогон изолирован в worktree и повторяем на точном SHA. Доставка ре-верифицируется против текущей
цели перед слиянием (фордж-нейтрально, через `git merge-tree`). Managed-слой целостен (checksums),
дрейф детектируется и блокирует, а не молчит.

## 16. Observability

Журналы отчётов прогонов (`report-history/*.jsonl`), провенанс установки, машиночитаемые отчёты
governance и own-medicine. Что НЕ сделано честно: сквозной трассировки OpenTelemetry в самом ките нет.

## 17. Failure Modes

- Реестр не читается / нет pyyaml → инструменты честно останавливаются, а не молчат.
- Managed-слой правлен вручную (drift) → обновление БЛОКИРУЕТ, не затирает молча.
- installed-версия вне allowed-диапазона → doctor обязан назвать (иначе тихая заморозка — известный
  класс, за которым следят).
- Ревьюер не рождает вердикт в среде → гейт закрывается handoff'ом оркестратору (не бесконечная петля).

## 18. Architecture Decisions

Ключевые инварианты и решения задокументированы в [AGENTS.md](AGENTS.md) и `.research/decisions/`
(DP-*). Среди них: registry — источник истины; writer ≠ judge; честные capability-декларации;
built ≠ wired (дормант заморожен потолком-ратчетом); фордж-нейтральный инвариант «против итога
слияния»; блокирующих гейтов MVP ≤ 8; язык документации русский, идентификаторы английские.

## 19. Known Limitations

- Взаимные связи ВНУТРИ ядра пакетов пока разрешены осознанно (замер как потолок; строгий DAG — позже).
- Разбор импортов JS/TS в анализе дочки — регулярными выражениями (даёт пропуски, не ложные тревоги);
  инварианты поверх такого графа рождаются `advisory`.
- Governance на PR дочки проверяет здоровье УСТАНОВКИ, полноценная проверка продукта дочки — в
  работе (инженерный стандарт, SR-17..20).
- OpenTelemetry не подключён.

## 20. Architecture Evolution

Current: пакетный движок со слоями и ратчетами; registry-driven; managed-доставка с PR-обновлением;
контур Planning & Execution; artifact-registry Product Operating Layer. Next: инженерный стандарт как
версионируемый объект (SR-1..4), секционная валидация артефактов (SR-5/6), governance продукта на PR.
Future: строгий DAG пакетов, supply-chain/OpenSSF проверки, замкнутая петля outcome→insight→work.
Триггеры миграций записываются отдельными решениями (ADR/DP), а не молча.

## 21. AI Development Contract

AI-агенты, работающие с этим репозиторием, обязаны: читать [AGENTS.md](AGENTS.md) и этот документ
перед архитектурными изменениями; держать registry источником истины (файл без записи в реестре и
наоборот — ошибка); не объявлять нереализованные возможности; уважать слои `packages/layering.yaml`
(зависимость вверх запрещена, ратчет ходит вниз); не вводить новых зависимостей без решения; писать
документацию по-русски, идентификаторы — по-английски; новое архитектурное решение — новый ADR/DP,
изменение архитектуры — обновление этого документа; прогонять проверки перед завершением.
