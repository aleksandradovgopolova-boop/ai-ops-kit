## [4.9.0] — 2026-09-29 · первый час по находкам репетиции на «Нитях»: состояние проекта в первом результате, первым — продуктовый шаг, проверка типов в turbo, имя проекта и направление из ответов владельца; стиль кода дочки держит машина

### Новое

- Первый план открывается продуктовым шагом, если его назвал владелец (#1203). Когда в ответах онбординга владелец сам назвал следующий результат для пользователя, bootstrap ставит в план первой работу к этому результату — под целью первого приоритета, со словами владельца в названии, — а описания процессов остаются в плане следом: они важны там, где описания нет. Где описаний нет вовсе и кит закрывает их сам цепочкой, её голова по-прежнему может идти первой; где они ждут слова владельца (как на «Нитях»), `next` советует продуктовую работу. Догадку кита за слово владельца не выдаём: из предположения продуктовая работа не создаётся. Направление тоже берёт «Следующий результат» и подтверждённую главную цель из ответов владельца, а не пишет «нужно ваше слово». Попутно исправлено: если у выбранной работы нет области записи, `next` больше не обещает, что с ней «не пересекаются по файлам» другие — это было сравнение с пустотой. (first-plan-starts-with-product-step)
- Первый результат установки теперь говорит, в каком состоянии проект сейчас (#1200). В `.ai/generated/first-result.md` и на финальном экране `setup` появился раздел «Состояние проекта сейчас» с итогом одной фразой: «по коду и безопасности проект в порядке — срочно править нечего», «срочно править нечего; посмотреть стоит: …» или «стоит поправить: …». Под итогом — по строке на проверку: устройство кода (сверка с конституцией), безопасность (сканер кита, только код продукта, без обвязки) и какими командами проект проверяется. Это связка уже существующих проверок, а не новая. Честность сохранена: тесты и сборку установка не запускает, поэтому о них сказано «кит знает, чем проверять», а не «проходят»; чего кит не видит или не смог проверить — названо, и итог получает оговорку «проверено не всё». Нашла репетиция первого часа на «Нитях»: сверка с конституцией там прошла чисто, но вывод до владельца не дошёл. (first-result-project-health)
- Включённый в дочке профиль стиля кода теперь держат все три точки, а не одна ручная команда: правка
  агента с новым именем не латиницей или импортом через границу слоя возвращается ему сразу (хук —
  только по изменённому файлу, существующее замороженное не в счёт), шаг CI дочки краснеет той же
  проверкой, что `./ai-ops lint-profile check`, а прогон кита не выдаёт «линт пройден» при росте
  расхождений и называет их адреса. Профиль не включён — всё как прежде. (lint-profile-enforced-everywhere)
- Описание выпуска теперь пишется как сообщение человеку, а не журнал: русский шаблон с двумя слоями — короткое «что меняется для вас» (до 250 слов, обязательные «Известные ограничения» и «Что сделать после выпуска») и полный журнал — и правила данными в политике коммуникации; агент `release-manager` пишет по ним и ставит у каждого пункта ссылку на источник. Машинной проверки правил пока нет — она следующая работа. (release-notes-template-rules)

### Исправлено

- После установки в `.ai-ops.yaml` больше не остаётся заготовка `<project-name>` (#1205). `init` берёт имя проекта из репозитория: из адреса `origin` (`…/niti.git` → `niti`), иначе из манифеста (`pyproject.toml`, `package.json` без scope), иначе из имени каталога основного репозитория — не рабочей копии. Ничего пригодного нет — заготовка остаётся, и doctor честно о ней скажет: имя не выдумывается. Нашла репетиция первого часа на «Нитях», где имя вписывал помощник. (init-fills-project-name)
- Советы кита после установки больше не говорят о «безымянном направлении» и не печатают команд (#1204). Причина была не в тексте, а в установке: установщик кладёт `ROADMAP.md` с целями-заглушками, а сборка направления из ответов владельца видела «файл уже есть» и не трогала его — план в том же случае заменялся, направление нет. Теперь заготовка кита (все цели — заглушки) заменяется направлением из фактов, а направление, где есть хоть одно своё имя цели, по-прежнему не трогается. Подпись для настоящего безымянного направления тоже без команды: «у него пока нет имени — назови его своими словами». Нашла репетиция первого часа на «Нитях». (propose-no-unnamed-direction)
- Кит узнаёт проверку типов в turbo-монорепо и не теряет названную человеком команду (#1202). Скрипт `check-types` (соглашение create-turbo) и близкие имена (`check:types`, `types:check`) теперь распознаются как проверка типов — из `package.json`, шага CI и цели Makefile. На «Нитях» это снимает «не знаю команды для проверки типов» и оговорку «проверено не всё». Команду, которой кит не видит, человек объявляет в `.ai-ops.yaml` (`verification.commands`, при нескольких стеках — по языку): она сильнее выведенной, имеет файл-источник и переживает повторный onboard. Прежде ответ вписывали в `.ai/repository-profile.yaml` — а это кеш в .gitignore, и следующий осмотр его стирал. (typecheck-detect-and-persist)

## [4.8.0] — 2026-09-29 · стиль кода в дочке держит машина: имена латиницей, линт при правке агента и в CI дочки, ревьюер по конституции

### Новое

- Архитектурная конституция получила две статьи о стиле кода в дочке: `CODE-011` — идентификаторы и имена файлов только латиницей и одна конвенция имён на стек (по умолчанию для каждой дочки, отказ — только ключом `standard.identifiers: any` в `.ai-ops.yaml`) и `CODE-012` — линтер и форматтер обязаны исполняться при правке, в CI и в прогоне кита. Гейтов у них пока нет, и это сказано прямо (#1183); заодно `ARCH-006` перестал числиться защитой дочки: его проверка размера видит только код кита. (identifier-and-lint-articles)
- Линт продукта теперь исполняется в самой дочке, а не только внутри `ai-ops run`: агент в Claude Code получает замечания линтера проекта сразу после записи файла (хук в `.claude/settings.json`, ваши настройки не трогаются, выключается `standard.lint_hook: off`), а новый workflow `ai-ops-lint` гоняет команды линта и формата дочки в её CI и может стать обязательной проверкой. Нет линтера или его нечем запустить — об этом сказано прямо, пропуск не выдаётся за пройденную проверку. (lint-at-edit-and-in-child-ci)
- Новая команда `./ai-ops lint-profile`: стиль кода в дочке держит машина, а не внимательность (#1183). Кит собирает профиль линтеров ПОВЕРХ её собственных конфигов — ESLint (имена латиницей, имена типов TypeScript, границы слоёв встроенным `no-restricted-imports` под своим именем `ai-ops/…`, новых пакетов не требуется), Ruff (`PLC2401`, `PLC2403`, `N`) и import-linter, golangci-lint (`asciicheck`, `revive`, `depguard`), ast-grep для прочих языков. Границы слоёв берутся из уже объявленной архитектуры (`architecture-invariants.yaml` или `standard.architecture`); правило зоны самой в себя запрещает соседние срезы (FSD). Латиница — по умолчанию, отказ — `standard.identifiers: any`. Включение не ломает текущий код: `--apply` замораживает существующие расхождения (для ESLint ≥ 9.24 — родными подавлениями), `check` краснеет только на новом, исправленное ужимает заморозку. На ии-среде заморожено 4781 имя не латиницей, 57 импортов через границу слоя и 7 имён типов; новый файл с кириллическим именем и импортом соседней фичи даёт код 1. (lint-profile-per-stack)
- Независимый ревьюер кода теперь судит по Архитектурной конституции: в его критерии (и в запрос внешнему ревьюеру) уходят статьи об архитектуре и коде — ID, уровень, заголовок, в ограниченном объёме, из той версии реестра, что стоит в репозитории (в дочке — `.ai/managed/`), и машинные находки конституции по изменённым в правке файлам. Смысловые статьи вроде «имена раскрывают намерение» и «логика живёт в своём слое» машина не ловит — их проверяет ревьюер; если реестра нет или проверка упала, он видит это прямо, а ревью не прерывается. (reviewer-gets-constitution-criteria)

### Исправлено

- Если в проекте нет линтера, кит больше не молчит об этом. В отчёте прогона и на онбординге владелец читает «Стиль кода в проекте никто не проверяет…» и совет, какой набор правил поставить под язык проекта. Раньше было «освобождено (нет инструмента в стеке)». Детектор теперь находит ESLint, Biome и Prettier по файлам настроек даже без скрипта в `package.json`, а ещё заполняет новый слот «проверка оформления»: prettier / biome / ruff format / black, и только когда в репозитории есть доказательство. Настройка `.ai-ops.yaml -> standard.lint: required` делает отсутствие линтера причиной отказа в приёмке. Незнакомое значение тоже блокирует приёмку. (child-without-linter-is-a-finding)

- Кит говорит о себе в одном роде. Раньше в части сообщений он был «он» («я не нашёл»), а в части — «она»: «Поняла: «…»», «независимую проверку я не провела», «дальше я работаю сама», а в ночном обзоре — разделы «Что я проверила» и «Чего я не стала делать». Теперь везде мужской род, как в остальных сообщениях кита. (kit-voice-masculine-form)

### Механизмы и проверки

- Кит сам следует правилу «идентификаторы — английские», которое требует от дочки: новое кириллическое имя в коде кита теперь краснит линтер или сторож в CI. Уже написанные 630 таких имён в 18 файлах заморожены поштучно, и заморозка может только сокращаться — и по числу файлов, и по числу имён в каждом файле: дописать кириллическое имя в замороженный файл нельзя, а исправленный файл обязан из заморозки уйти (#1183). (kit-identifier-baseline)

### Служебное

- Новое направление «стиль кода в дочке держит машина»: латиница в идентификаторах по умолчанию, линт исполняется при правке агента и в CI дочки, существующие нарушения фиксируются базой (#1183). (child-code-style-direction)
- Первая волна «стиль кода держит машина» закрыта в историю: шесть работ влиты, кит сам держит правило «имена латиницей»; в плане — стык профиля с хуком, CI и прогоном (#1183). (child-code-style-first-wave)
- В историю закрыты две работы: десять вопросов жизни фичи доказаны на реальной фиче ии-среды (10 из 10 после исправления кита и записи аудитории в паспорте фичи; разбор — `qualification/TEN-QUESTIONS-FIELD-RUN-2026-09-29.md`) и фраза об отличии продукта в README.
  Направление «продукт помнит свою историю» объявлено достигнутым решением владельца: обе половины приёмки взяты на реальной фиче ии-среды. (close-ten-questions-and-readme)


### Честно: что ещё не сделано

- Профиль `./ai-ops lint-profile` пока исполняется только своей командой `check`: хук при правке, workflow `ai-ops-lint` и приёмка прогона гоняют собственный линт дочки и профиль не видят. Стык — следующая работа направления (#1183). Если в дочке правила о латинице и слоях уже стоят в её собственном конфиге линтера, хук и CI держат их уже сейчас.

## [4.7.0] — 2026-09-29 · сканер безопасности меряет продукт, а не шум + установка ведёт к первому результату + десять вопросов жизни фичи

### Новое

- В карте продукта появилась строка «доля работ кита с доказательством улучшения дочки» — стрелка «работа кита → исход дочки», видимая числом (#1141, направление prove-the-loop #1116). Знаменатель — все работы кита (активный `planning/plan.yaml` плюс закрытые `history/plan-history.yaml`), числитель — работы, несущие ЗАПИСАННОЕ доказательство: названный дочерний продукт и ссылку на evidence, где улучшение зафиксировано. Голое самолюбование (`child_value: true` без источника) в числитель не попадает — ровно тот риск, против которого заведено направление. Честность обязательна: нет ни одной работы — «не измерено» с причиной; работы есть, доказательств нет — честный НОЛЬ, а не приукрашенная доля. Сегодня на самом ките это 0% (0 из 267 работ): loop построен, но ещё не доказан, и карта говорит об этом прямо. Показатель стоит РЯДОМ с пятёркой метрик отдельной строкой (не шестым пунктом карты и не блокирующей проверкой — гейт был бы ростом вширь, ровно тем, что независимое ревью запрещает). (child-value-share-in-product-scorecard)
- Конец установки — теперь первый РЕЗУЛЬТАТ, а не строка «кит установлен» (#1140). Первый час (`ai-ops model --flow --apply`, а значит и `ai-ops setup`) при apply оставляет открываемый файл `.ai/generated/first-result.md`: что кит понял о репозитории и — по стадии — собранные направление и план с первой работой, либо какие ответы нужны (командой `ai-ops model --answer`, без ручной правки YAML), либо честное «результата пока нет, репозиторий не прочитался». Финальный экран `setup` теперь ВЕДЁТ этим результатом и ссылается на файл, а не заголовком «AI Ops установлен одной командой». Дерево, которое не прочиталось, файла-обманки не создаёт — недоказанное остаётся недоказанным. (install-leads-to-first-result)
- Карта продукта перестала отвечать заглушкой на два последних вопроса. «Доля фич с реальным результатом после релиза» и «доля решений, опирающихся на прошлые результаты» были каркасом: обе функции не принимали данных и всегда говорили «не измерено — у самого кита нет живой аналитики». Эта фраза ехала в КАЖДЫЙ подключённый репозиторий: на ии-среде, где петля замкнута на реальных числах, кит рассказывал о себе там, где спрашивали о продукте. Теперь четвёртая считается из отчётов о результате (`features/<id>/outcome-readout.yaml`), пятая — из уроков, выведенных ИЗ измеренного результата и подшитых к следующему шагу. Честность сохранена с обеих сторон: нет фич — «не измерено»; фичи есть, замеров нет — честный НОЛЬ, потому что «ни у одной результат не замерен» это знание, а не его отсутствие; `target_met: unknown` замером не считается. Итоговая строка карты больше не называет метрики по памяти, а перечисляет то, что не измерено в этом проекте. (scorecard-tail-reads-real-outcomes)
- Кит отвечает на десять вопросов жизни фичи одним связным ответом. `./ai-ops graph questions <feature>` (новый модуль `intelligence/feature_life_history`) собирает поверх графа знаний ответ на дословные десять вопросов приёмки — зачем функция возникла, какую проблему решает, для кого, какая была гипотеза, почему такое решение, что построили и где, что доказано и кто проверял, что произошло после релиза, чему научились и что дальше. Связь доказывает граф (рёбра `motivates`/`contains`/`builds`/`reviewed`/`targets`/`feeds`), а детали читаются из СВЯЗАННОГО первоисточника (паспорт функции, `product-learning/FL-*.yaml`) — не расширяя граф вширь. У каждого ответа видно, чем он подтверждён; чего в связанной истории нет, то называется честным «неизвестно» с указанием, какого именно звена не хватает, а не заменяется догадкой. Полная история фичи читается как один ответ «почему мы вообще сделали эту функцию и что с ней стало», который раньше собирался вручную из пяти разных файлов. (ten-questions-feature-life-history)
- PR обновления кита, который открывает CI-джоба дочки (`ai-ops-update.yml`), теперь тоже показывает,
  что выпуск привозит по безопасности: новые адреса сканера поимённо, прежние числом, явное «ничего»
  или «проверить НЕ УДАЛОСЬ». Данные раздела лежат в отчёте обновления (`security_surface` в
  `last-update-report.json`), и шаблон выводит их текстом, не подставляя в shell. (update-pr-security-section-via-ci)

### Исправлено

  «правило + текст строки» переживает сдвиг строк). Кит перестал молча привозить в чужой репозиторий
  injection-поверхность, за которую отвечает сам. Секретов это не касается — пароль в поставленной
  копии лежит в репозитории дочки и по-прежнему роняет гейт. (vendor-flags-separate-section)
- На вопрос «почему выбрали именно такое решение» кит теперь отвечает и тогда, когда обоснование записано не в уроке фичи, а в самом решении, из которого она появилась (поле `reason` эпизода в `decisions/registry.yaml`, связанного ребром `decision -motivates-> feature`). Уликой ответа указано это решение, а не урок. Урок с выбранным вариантом по-прежнему главнее; если обоснования нет ни там, ни там — честное «неизвестно». Нашёл полевой прогон десяти вопросов на реальной фиче ии-среды: ответ лежал в уже связанной записи, но кит его не читал (8 → 9 из 10). (why-this-solution-from-decision)

### Механизмы и проверки

- Ограничитель на размер функций теперь накрывает весь кит, а не шесть выбранных каталогов. Повод конкретный: вне его охвата выросла самая длинная функция репозитория — длиннее любого объявленного потолка, — и каждая работа добавляла ей десяток строк, не встречая сопротивления. Заодно нашлись ещё семь таких же неохраняемых мест. Потолки заведены по факту: они останавливают рост, а не требуют бросать дела и переписывать. И добавлена проверка, которая сама ловит отставание списка — раньше он пополнялся вручную и отставал от кода. (func-size-covers-the-whole-package)
- Сборка графа истории читает диск в одном месте: все четыре прохода получают уже прочитанные данные
  и проверяются на синтетике без файлов, а проход паспортов разрезан на именованные подшаги. Сам граф
  не изменился — побайтно тот же на ките и на всех тестовых дочках. (graph-build-passes-take-data)
- Security-скан теперь показывает адреса рискованных мест и в Node/TS, а не только в Python: SQL,
  собранный склейкой в шаблонном литерале (`db.query(...${id}...)`), динамическое исполнение через
  `new Function` и `vm.runIn*Context`, запись в DOM помимо `innerHTML` (`outerHTML`,
  `insertAdjacentHTML`, `document.write`, `v-html`). В секретах добавились строка подключения к базе
  с паролем внутри, npm-токен, JWT и ключи LLM-провайдеров. Раньше по этим местам человек, решающий
  про безопасность выпуска, получал пустой список и мог принять его за «чисто».

  Вердикт про injection-поверхность по-прежнему выносит человек или независимый ревьюер: скан
  поставляет адреса, а не доказательство отсутствия уязвимостей. Замер на дереве самого кита:
  ни одно новое правило не подняло ни одного флага на собственном коде — список остался коротким и
  пригодным для чтения. (security-scan-sees-node-ts)
- Сборка истории продукта перестала быть одной функцией на 275 строк — самой длинной в ките. Теперь это четыре названных прохода по источникам: план продукта, паспорта функций, выводы из данных и вердикты проверок. Для человека ничего не изменилось: граф на реальных данных после разреза совпал с прежним побайтно. Ограничитель размера опущен со 275 до 137 строк — он ходит только вниз, и это его первое снижение в этой области. (split-build-graph-by-sources)
- Разбор манифестов зависимостей вынесен из фасада `security_scan` в сателлит `scan_deps`: фасад
  подошёл к порогу монолита вплотную (699 при пороге 700), и следующая правка сканера упёрлась бы в
  ратчет. Перенос дословный — отчёт сканера на 2192 файлах совпал с прежним побайтно в обоих режимах
  запуска (как модуль пакета и как скрипт). Публичная поверхность не переезжает: `new_dependencies`,
  `new_dependencies_detailed` и `DEP_MANIFESTS` остаются именами `security_scan`. (split-security-scan-deps)

  Canvas) — правят редко и он тихо отстаёт. В брифинге «Ревью фундамента» (`ai-ops propose`) кит
  сравнивает свежесть документов фундамента со свежестью нижнего слоя и с датами фич и, когда есть
  измеримое основание, говорит по-человечески: «возможно, стоит пересмотреть фундамент: „Vision“,
  скорее всего, устарел — N нижних документов и M фич новее». Свежесть берётся из git-даты последнего
  изменения файла; какой контур/какие документы считаются фундаментом, объявлено в
  `registry/product-operating-model.yaml` (секция `foundation`), а дочка вправе задать фундамент
  тоньше — списком файлов. Честность превыше полноты: нет git-даты у документа — состояние «не знаю»,
  а не «свежо»; не с чем сравнить (ни нижних документов с датой, ни фич) — кит молчит и устаревание не
  выдумывает. Сигнал ADVISORY: он советует пересмотреть, а не валит сборку. (foundation-freshness-advisory)

- Мёртвая заявка active-work с ЧУЖОЙ машины больше не блокирует `ai-ops next` навечно. У возраста заявки появился жёсткий потолок (по умолчанию 14 дней, настраивается через `AI_OPS_CLAIM_HARD_TTL_DAYS`): старше него заявку снимает reap НЕЗАВИСИМО от машины. Раньше session-заявку с другой машины кит не трогал вовсе («вдруг сессия жива»), а 12-часовой порог применялся только к своей машине — и заявка `derived-counts` с чужого MacBook провисела 24 дня, блокируя `next`, хотя работа давно в истории. Защита от кражи ЖИВОЙ работы сохранена: свежие чужие заявки (моложе потолка) по-прежнему уважаются как авторитет координации; поведение своей машины (мёртвый pid, порог 12ч) не изменилось. Меняется судьба только очень старых заявок. (claim-hard-ttl-releases-foreign-dead-claim)
- Критический тест fs-guard больше не зависит от привилегий среды: проба «откат физически
  невозможен» опиралась на то, что r-x каталог не даёт unlink (EACCES), а под root это правило
  обходится и тест молча зеленел мимо дефекта. Теперь под root он честно пропускается, а под обычным
  пользователем (как в CI) исполняется по-настоящему — ассерты не ослаблены. (fix-root-dependent-critical-test)
- Когда граф знаний нельзя построить из-за того, что установленный реестр типов
  (`registry/entities.yaml`) отстал от сборщика — тот порождает типы и связи, которых старый реестр
  ещё не знает, — кит теперь называет причину и советует обновиться (`ai-ops update`), вместо голого
  отказа с сырой ошибкой валидатора. Подсказка честная: она допускает и второй вариант (граф правили
  вручную мимо реестра), появляется только для ошибок словаря типов и не подменяет собой отказ — гейт
  по-прежнему не отвечает по несошедшемуся графу. Для настоящей порчи данных (ссылка на несуществующий
  узел) совет «обнови кит» НЕ показывается: это был бы ложный диагноз. (graph-gate-names-stale-type-registry)
- README больше не расходится с реальным числом команд владельца: писал «32 команды», а фактически (реестр INTENTS) и в capability-map — 34 (P1 №11 продуктового ревью). Число исправлено и помечено машинно-проверяемым маркером `claim:commands-total`; тест-замок сверяет README ↔ INTENTS ↔ capability-map, чтобы расхождение больше не появилось незаметно.   `features/<id>/delivery-outbox/<delivery_id>.receipt.yaml` — она не смотрела. Из-за этого функция,
  доставленная с проверенным по remote SHA, всё равно помечалась как «нет доказательства поставки».
  Теперь проверка читает приёмник ПЕРВЫМ (тот же порядок, что и остальной кит), а прежние запасные
  пути остаются как fallback. Условие приёмки не изменилось (нужна `DeliveryReceipt` с
  `sha_verified=true`), и поведение при полном отсутствии расписки прежнее. (released-check-reads-delivery-outbox)
- Кит больше не требует доказательство доставки (DeliveryReceipt) от выпущенной функции, чей процесс не включал стадию поставки. Раньше выпущенной считалась любая функция обязанной приложить расписку — и лёгкие, веденные вручную функции получали ложную жалобу «докажи доставку», которую никогда не заявляли. Теперь расписку спрашивают только у функций, чей заявленный профиль действительно проходит стадию delivery; функция, реально прошедшая поставку, доказательство приносит как прежде. (released-receipt-only-if-delivery-staged)
- Предпусковое превью исследовательского вопроса больше не обещает pull request. Раньше `run` любого типа показывал владельцу «проверю изменение и открою черновой pull request» — даже когда роутер выбрал RESEARCH-workflow, чей итог не изменение кода, а доказательства и пакет для решения. Теперь для research превью говорит языком исследования: «запущу исследование: превращу вопрос в доказательства и пакет для решения (материалы соберу в .research/)». (research-preview-speaks-research-not-pr)
- Доставка переживает перенос/переименование репозитория на GitHub. Раньше при org-transfer старый
  адрес отдавал 301-редирект: `git push` его следовал, но создание PR и API-вызовы били по СТАРОМУ
  слагу, распарсенному из origin-URL, — PR уходил не туда либо доставка зависала в `outcome_unknown`.
  Теперь перед PR кит резолвит ТЕКУЩИЙ канонический слаг через GitHub API (`GET /repos/{owner}/{name}`
  следует редиректу и отдаёт актуальный `full_name`) и ведёт по нему все последующие вызовы —
  определение дефолт-ветки, проверку идемпотентности и сам POST создания PR, а также сверку
  (reconciliation). Резолв — улучшение, а не новая точка отказа: если он не удался (репо не найден или
  API недоступен), доставка идёт по исходному слагу ровно как раньше, слаг не выдумывается. (delivery-follows-repo-transfer-301)

## [3.38.0] — 2026-08-31 · Product Operating System замкнута (5/5)

Этот релиз закрывает пять целей продуктовой ОС и выпускает работу, накопившуюся на `main` после

### Капстоун: автономное перепланирование — `ai-ops replan`

Цикл сам сводит приоритеты плана к реальности **без человеческого `--replan`**, замыкая Фазу 5

4-классовой модели ночного обзора на план): переприоритизация (класс A) обратима, детерминированна,
**СОСТАВ РАБОТ НЕ МЕНЯЕТ**, каждый сдвиг подписан «почему» — применяется сама (`--apply` пишет
машинный артефакт `.ai/project/replan/latest.yaml` дочки, авторский `planning/plan.yaml` и main не
трогает); структурные изменения — только предложением. Автономное удаление работ невозможно по
механизму (`_check_same_work_set`) — прямой ответ полевому провалу ии-среды. Детерминизм, `budget=0`,
kill-switch, policy-гейт. Второй правды не заводит: сводит `next_work.compute` /
`delivery_plan.resolve`+`git_disagreements` / `risk_register` / `backlog_prioritize`.

### Approval-gated слияние дублей — `ai-ops backlog merge`

Вторая половина исхода `duplicates_detected_and_merged`. Детектор как и прежде ПРЕДЛАГАЕТ; кит СЛИВАЕТ
дубли только по явно одобренным человеком парам (`--approved` файл), никогда сам. GitHub не «сливает»
Issue — закрывает ДУБЛЬ с кросс-ссылкой на канонический (`state=closed`, `reason=not_planned`),
канонический оставляет открытым; обратимо. Без `--apply` — dry-run; провал комментария не закрывает
дубль; все мутации GitHub через единственный шов `GitHubClient._gh_mutate` (только `gh`).
