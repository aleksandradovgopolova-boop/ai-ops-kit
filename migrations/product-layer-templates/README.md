# migrations/product-layer-templates/ — миграции версий шаблонов Product Operating Layer

Отдельная ось от миграций пакета (`migrations/<from>-to-<to>/`). Здесь — миграции ВЕРСИЙ ШАБЛОНОВ
артефактов слоя (PR-5): когда официальный шаблон артефакта поднимается с версии N до N+1, экземпляр
артефакта в дочке (`.ai-ops/<ARTIFACT>`) на версии N нужно привести к N+1, не потеряв содержимое.

Раскладка:

```
migrations/product-layer-templates/<artifact_id>/v<N>-to-v<N+1>/
  up.py     # применение: аргумент — путь экземпляра артефакта в дочке; exit 0 = успех
  down.py   # rollback (или честная ошибка для необратимой миграции)
```

`artifact_id` — id из `registry/artifact-registry.yaml` (`product_passport`, `roadmap`, …).

ГЛАВНОЕ ПРАВИЛО, КОТОРОЕ ПРОВЕРЯЕТ МАШИНА (`ai_ops_kit/planning/product_templates.py -> check`):
**нельзя поднять версию шаблона в реестре, не положив сюда миграцию на каждый шаг.** Артефакт в
реестре объявлен версией V — значит для него обязаны существовать шаги `v1-to-v2 … v(V-1)-to-vV`,
каждый с `up.py` и `down.py`. Иначе дочка на старой версии не сможет догнать новую, и «обратная
совместимость либо миграция» (PR-5) окажется словом без исполнения.

Пока все шаблоны версии 1 — миграций нет, и это законно: шаг 1 не требует перехода. Первый же
подъём версии обязан прийти вместе со своей папкой здесь, иначе `check` покраснеет.

Миграции идемпотентны, не читают и не пишут секреты (то же правило, что у миграций пакета).
Каталог `migrations/` в дочку НЕ поставляется (не входит в `managed_set`) — миграции применяет кит.
