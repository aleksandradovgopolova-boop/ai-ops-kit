# Предоставленное владельцем продуктовое ревью

Содержимое исходного снимка сохранено без изменения.

```text
Да. Я посмотрела текущее состояние репозитория на 5 октября 2026 как продукт, а не как «набор хорошего кода».

Мой главный вывод такой: **AI Ops Kit уже перерос стадию “собираем возможности”. Сейчас его главная проблема не нехватка функциональности, а нехватка доказанного пользовательского продукта вокруг этой функциональности.**

То есть внутри уже довольно мощная машина. А следующий скачок должен быть не «ещё умнее», а **проще войти → быстрее получить пользу → увидеть измеримый эффект → захотеть оставить кит в проекте**.

Сейчас версия — **4.9.3**, но честный `stable` по-прежнему остаётся на ветке 4.3.x: более новые миноры находятся в `qualification`, потому что для них не хватает полевой проверки. Это, кстати, очень правильная продуктовая честность. [VERSION](https://github.com/aleksandradovgopolova-boop/ai-ops-kit/blob/main/VERSION) · [README](https://github.com/aleksandradovgopolova-boop/ai-ops-kit/blob/main/README.md)

### Что уже очень хорошо

Первое — у продукта наконец появилось довольно ясное позиционирование:

> пользователь говорит, что нужно сделать; кит понимает контекст продукта, организует работу, проверяет результат и не говорит «готово» без доказательства.

Это сильно лучше, чем позиционировать продукт через 42 роли, 36 гейтов или архитектуру. В README уже появился нормальный human-level promise.

Второе — зрелость инженерного фундамента очень высокая. Сейчас есть 38 пользовательских команд, 36 quality gates, 42 роли; причём карта сама различает `built`, `partial`, `built≠wired` и `planned`. И на данный момент `built≠wired` остался всего один намеренно изолированный security-модуль. [Capability map](https://github.com/aleksandradovgopolova-boop/ai-ops-kit/blob/main/docs/capability-map.md)

Третье — мне очень нравится изменение способа измерения самого кита. Вы перестали считать главным KPI количество возможностей и ввели пять продуктовых метрик:

1. доля фич от идеи до релиза;
2. доля утверждений с evidence;
3. доля выпущенных фич с полной историей;
4. доля фич с измеренным пострелизным результатом;
5. доля новых решений, использующих прошлые результаты.

Вот это уже выглядит как зарождение настоящей **Product Operating System**, а не workflow framework.

Четвёртое — появляется реальная полевая квалификация. Например, 5 октября правила code style реально прогнаны на `ии-среде`: плохой commit был остановлен настоящим CI, исправленный прошёл, независимый reviewer нашёл нарушения. При этом документ честно фиксирует, что живая Claude-сессия не была проверена. [Field run](https://github.com/aleksandradovgopolova-boop/ai-ops-kit/blob/main/qualification/CODE-STYLE-FIELD-RUN-2026-10-05.md)

И ещё важный момент: последние релизы преимущественно уже не добавляют случайные «фичечки», а чинят первый час, verification, installer, release communication. Это правильное направление. Последний релиз — [v4.9.3](https://github.com/aleksandradovgopolova-boop/ai-ops-kit/commit/ad16611cec1ca65a659f597f7b3b0436df8e78b8).

## Где сейчас настоящие проблемы

### 1. Продукт всё ещё начинается слишком рано с внутренней сложности

38 команд — впечатляет разработчика кита. Пользователю 38 команд не нужны.

В идеале обычный пользователь вообще не должен знать, что существуют:

`model`, `bootstrap`, `plan`, `propose`, `next`, `run`, `do`, `review`, `readout`, `graph`, `contract`, `health`...

Это отличный underlying API. Но **плохая основная UX-модель**.

Основной продукт должен ощущаться примерно так:

> «Вот мой репозиторий. Помоги сделать X».

И дальше Кит сам делает `model → plan → run → review → evidence → result`.

То есть тебе сейчас надо очень жёстко разделить:

**Product surface** — 5–7 намерений пользователя.

**Power-user surface** — все 38 команд.

Пока они слишком близко находятся друг к другу.

---

### 2. Первый час незнакомого человека всё ещё главный незакрытый риск

Это даже сам roadmap признаёт как №2 текущей работы: `first-hour-for-a-stranger`.

Причём acceptance сформулирован правильно:

> от репозитория без кита до первого результата ≤5 минут, причём результат — не «кит установлен».

Вот это сейчас, на мой взгляд, **приоритет №1 вообще**.

Не code style.

Не новая intelligence-фича.

Не ещё один validator.

Пока посторонний человек без твоего участия не сможет поставить kit и получить первый полезный результат, у нас есть очень крутой внутренний продукт, но ещё нет доказанного внешнего продукта.

Issue уже существует: [#1115](https://github.com/aleksandradovgopolova-boop/ai-ops-kit/issues/1115).

Я бы сделал его абсолютным P0.

---

### 3. Недостаточно доказана причинно-следственная связь «Kit → стало лучше»

Сейчас есть доказательства формата:

- Kit нашёл проблему;
- Kit заблокировал неправильный commit;
- Kit сохранил историю;
- Kit построил решение;
- Kit правильно предложил next.

Это хорошие **functional outcome**.

Но пока мало доказательств:

> команда с Kit стала работать лучше, чем без Kit.

Например:

- PR проходит меньше циклов переделки;
- меньше regressions;
- быстрее time-to-first-PR;
- меньше времени PM/tech lead уходит на сопровождение AI;
- повышается доля фич с измеренным outcome;
- меньше забытых требований;
- сокращается lead time idea → release;
- новым участникам проще войти в проект.

Это и есть ваша цель `prove-the-loop-not-add-capabilities`. [#1116](https://github.com/aleksandradovgopolova-boop/ai-ops-kit/issues/1116)

И я бы её поставила рядом с первым часом.

---

### 4. Есть риск построить ERP для разработки вместо помощника

Это сейчас самая опасная долгосрочная развилка.

У тебя уже есть:

- feature registry;
- evidence;
- plan;
- roadmap;
- history;
- knowledge graph;
- governance;
- scorecard;
- portfolio;
- products;
- delivery;
- inbox;
- team;
- health;
- work;
- readout;
- candidates;
- model;
- contract.

По отдельности всё оправдано.

Вместе начинает появляться риск:

> чтобы Kit управлял работой, человек должен начать управлять Kit.

Вот этого нельзя допустить.

Главный принцип следующего этапа я бы сформулировала так:

**не добавлять человеку новые сущности, если Kit может вывести их сам.**

Если `WorkItem`, feature, evidence, plan, outcome-readout нужны машине — отлично.

Но пользователь не должен заниматься поддержкой этих сущностей как администратор Jira из ада.

---

### 5. Product dashboard пока просится сильнее, чем новые CLI-команды

Issue #1201 про «пульт продукта» очень своевременный. [#1201](https://github.com/aleksandradovgopolova-boop/ai-ops-kit/issues/1201)

Сейчас у продукта есть огромное количество знания, но оно размазано между командами.

Я бы сделал единый ответ на пять вопросов:

**Где мы?**

Что делаем сейчас.

**Почему это делаем?**

Какой исход ожидаем.

**Что мешает?**

Риски / решения человека / непроверенные утверждения.

**Что изменилось?**

Последний release / PR / outcome.

**Что делать дальше?**

Одна основная рекомендация + максимум 2 альтернативы.

Это и должен быть cockpit.

Не dashboard ради dashboard, а **главный интерфейс между человеком и операционной системой**.

### 6. Runtime-agnostic пока заявлен сильнее, чем доказан

В README правильно написано, что роли не должны зависеть от конкретного исполнителя. Архитектурно это разумно.

Но открытым остаётся [#611 runtime-agnostic-core](https://github.com/aleksandradovgopolova-boop/ai-ops-kit/issues/611).

И здесь я бы не торопился с лозунгом «Claude / Codex / Qwen одинаково».

Правильнее продуктово:

> Kit хранит процесс и контекст независимо от модели; степень автоматизации зависит от подключённого runtime.

Потом уже делать qualification matrix:

| Runtime | Install | Execute | Review | Hooks | Parallel | Stable |
|---|---|---|---|---|---|---|
| Claude Code | ✓ | ✓ | ✓ | ✓ | … | qualification |
| Codex | ✓ | ✓ | ✓ | … | … | experimental |
| Generic API | … | … | … | — | — | partial |

Это будет честнее и понятнее.

## Что я бы сейчас вообще НЕ делала

Вот тут я бы довольно жёстко тормознула.

Не нужны в ближайшем цикле ещё 10 ролей.

Не нужны ещё 15 quality gates.

Не нужны новые lifecycle stages.

Не нужна сложнее orchestration architecture.

Не нужно расширять knowledge graph просто потому, что можно.

Не надо сейчас оптимизировать Kit под enterprise governance.

Не надо доказывать, что он способен покрыть вообще всё.

У вас уже достаточно функциональности, чтобы несколько месяцев заниматься только превращением всего этого в продукт.

# Какой дальше план

Я бы сделал четыре последовательных этапа.

### Этап 1. Productize the first hour

Это ближайший P0.

Берём **3 незнакомых репозитория**, желательно разных:

- маленький;
- обычный frontend/backend;
- монорепо или сложный существующий продукт.

И **3 человека, которые Kit раньше не использовали**.

Сценарий один:

> «Вот repo. Сделай небольшую реальную задачу».

Не рассказываем им про устройство кита.

Замеряем:

`repo → first useful result`

`repo → first accepted PR`

Количество вопросов Kit → человек.

Количество технических решений, которые пришлось принимать человеку.

Количество ручных CLI-команд.

Количество тупиков / retry.

Количество случаев, когда понадобилась твоя помощь.

И отдельно:

**сколько новых понятий человеку пришлось понять?**

Моя целевая планка:

- ≤5 минут до первого осмысленного результата;
- ≤15 минут до первой исполнимой работы;
- 0 знаний архитектуры Kit;
- 0 ручного редактирования его внутренних YAML;
- 0 необходимости выбирать агента / workflow / gate.

---

### Этап 2. Сжать пользовательскую модель продукта

Из 38 команд сделать примерно шесть пользовательских намерений:

`Ask` — что происходит / почему.

`Do` — сделай задачу.

`Plan` — помоги решить, что делать дальше.

`Review` — проверь результат.

`Status` — где мы сейчас.

`Improve` — что продукту нужно улучшить.

А всё остальное оставить advanced API.

Фактически Kit должен научиться сам преобразовывать:

> «Добавь экспорт PDF»

в:

intake → context → requirements → plan → implementation → verification → review → PR → evidence.

Без пользователя, решающего, какой pipeline запускать.

---

### Этап 3. Доказать outcome

Выбираем 2 реальные дочки.

Например `ии-среда` + ещё один существенно другой продукт.

На протяжении 20–30 настоящих работ снимаем baseline.

Я бы взяла всего пять KPI:

**Time to usable result**

от запроса до рабочего результата.

**Human interventions / work**

сколько раз Kit пришлось спасать.

**Rework rate**

сколько работ потребовали возврата после review/CI.

**Evidence completeness**

доля существенных утверждений, реально подтверждённых.

**Outcome closure**

доля выпущенных фич, где позже измерили результат.

А потом сравниваем работу **с Kit против исторического baseline**.

Вот после этого уже появляется материал:

> Kit сократил ручное сопровождение AI-разработки на X%.

или

> В 83% работ PM не принимал технических решений.

Вот это уже начало коммерческого/организационного value proposition.

---

### Этап 4. Только после этого — масштабирование

И дальше уже становится понятно, что реально масштабировать.

Мой предполагаемый порядок:

1. первый час / onboarding;
2. естественный language-first UX;
3. cockpit;
4. product measurement;
5. multi-runtime qualification;
6. portfolio/team layer;
7. организационное обучение.

А не наоборот.

## Как я сейчас вижу зрелость продукта

Если грубо оценить по 10-балльной шкале:

| Область | Сейчас |
|---|---:|
| Product vision | **9/10** |
| Архитектура | **9/10** |
| Инженерная надёжность | **9/10** |
| Evidence / honesty model | **10/10** |
| Покрытие lifecycle | **9/10** |
| Первый опыт пользователя | **6/10** |
| Простота продукта | **5/10** |
| Доказанная внешняя ценность | **5/10** |
| Adoption readiness | **5/10** |
| PMF evidence | **3–4/10** |

И это не плохая оценка.

Это означает, что **ядро продукта уже построено раньше, чем его adoption layer**.

На ранних версиях у меня было ощущение: «тут много правильных процессов, но продукт ещё ищет себя».

Сейчас уже другое ощущение:

**продукт нашёл себя. Теперь его надо перестать достраивать вширь и заставить выигрывать реальные пользовательские сценарии.**

Самый важный следующий milestone я бы вообще назвала не `v5.0`.

Я бы назвала его:

> **“Someone else can use it.”**

Критерий выпуска: незнакомый человек приходит с незнакомым repo, говорит одну реальную задачу и без тебя доходит до результата.

Когда это заработает — вот тогда AI Ops Kit перейдёт из категории «очень продвинутая авторская система» в категорию **реального продукта, который можно масштабировать на команды**.
```
