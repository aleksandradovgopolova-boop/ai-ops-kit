# Code Review

## Вердикт

**FAIL.** Модуль, чей заявленный смысл — «совет, который нельзя выполнить, ХУЖЕ отсутствия», сам утверждает пройденными проверки, которых не делает. Два блокера: фиктивный selftest и selftest в продакшн-модуле вопреки AGENTS.md. Сверх того, основная проверка флагов невыполнима по построению (тавтология), а проверка traceback гарантированно падает на собственном репозитории.

## Blockers

**BLOCKER-1. `--selftest` ничего не проверяет — печатает «PASSED» безусловно.**
`ai_ops_kit/engops/refusal_paths.py:96-101`

```python
if args.selftest:
    print("SELFTEST: refusal_paths.py")
    print("  - check_refusal_paths: OK")
    print("  - format_report: OK")
    print("SELFTEST PASSED")
    return 0
```

Ни `check_refusal_paths`, ни `format_report` не вызываются. Нет ни одного assert, нет фикстуры, нет ветки возврата ненулевого кода. Это не слабый тест — это отчёт о проверке, которой не было: строка «check_refusal_paths: OK» ложна при любом состоянии кода, включая синтаксически валидный, но полностью нерабочий модуль. Прямое нарушение правила «объявленная проверка обязана исполняться». Отдельно отмечу иронию: модуль ловит ложные обещания кита пользователю и сам является таким обещанием.

**BLOCKER-2. Selftest живёт в продакшн-модуле; тестового файла в diff нет вовсе.**
`ai_ops_kit/engops/refusal_paths.py:14, 63, 96-101`

AGENTS.md: «Selftest не живёт в продакшн-модуле. Модули `ai_ops_kit/` едут в child-репозиторий; тест модуля — в `tests/unit/test_<module>_selftest.py`». Требуется `tests/unit/test_refusal_paths_selftest.py`; в diff его нет. Флаг `--selftest`, строка usage в docstring и ветка в `main()` подлежат удалению из модуля, а проверки — переносу в tests/unit с реальными фикстурами (временный `root` с заведомо битым и заведомо чистым CLI).

## Major

**MAJOR-1. Проверка флагов не может обнаружить нарушение — множества совпадают по построению.**
`refusal_paths.py:33-53`

`defined_flags` собирается регуляркой `--([a-z0-9-]+)` по **всему тексту** `ai_ops_cli.py`, включая строковые литералы сообщений об ошибках. Затем те же сообщения ищутся в том же `content` шаблонами `unrecognized arguments: --(...)` и `unknown flag: --(...)`. Любой флаг, пойманный этими шаблонами, по определению уже попал в `defined_flags` — тот же текст, надмножество той же регулярки. Ветка `if flag not in defined_flags` недостижима. Проверка возвращает `pass` всегда, независимо от того, есть ли в CLI совет с несуществующим флагом.

Чтобы проверка имела смысл, «определённые» флаги нужно извлекать структурно (AST: аргументы `add_argument`/`add_parser`) либо запуском `--help`, а «упомянутые» — из литералов подсказок; сейчас оба множества берутся из одного плоского текста.

**MAJOR-2. Шаблоны ищут рантайм-вывод argparse в исходнике — совпадений не будет никогда.**
`refusal_paths.py:38-42`

`unrecognized arguments:` и `invalid choice:` — форматные строки, которые argparse печатает **во время исполнения**; в исходнике `ai_ops_cli.py` они не встречаются. Заявленная в docstring проблема — «кит печатает советы с флагами/командами, которых нет», то есть подсказки вида `Попробуйте: ai_ops_cli.py run --execute` внутри собственных сообщений кита. Именно эти строки и не сканируются. Проверка нацелена не на тот класс текста, что описан в шапке.

Дополнительно: `invalid choice: '([a-z0-9-]+)'` захватывает **имя подкоманды** (без `--`) и сравнивает его с множеством имён **флагов** — разные пространства имён, сравнение некорректно даже гипотетически.

**MAJOR-3. Заявленная проверка команд не реализована.**
`refusal_paths.py:11`

Docstring: «Все упомянутые команды существуют». В коде нет ничего, что извлекало бы или валидировало команды/подкоманды. Объявленная возможность с нулевой реализацией — тот же дефект, что и BLOCKER-1, только на уровне контракта модуля.

**MAJOR-4. Проверка traceback самосрабатывает: модуль помечает сам себя и падает на своём репозитории.**
`refusal_paths.py:55-68`

Скан идёт по `ai_ops_kit/engops/*.py` — включая сам `refusal_paths.py`, в исходнике которого присутствует литерал `"Traceback (most recent call last)"` (строка 61, сам шаблон поиска). Первое условие истинно. Второе, `re.search(r'["\'].*Traceback.*["\']', content, re.DOTALL)`, тоже истинно — литерал обрамлён кавычками прямо в этой же строке. Результат: `issues` непуст → `status: fail` → `main()` возвращает 1. Если модуль включат в гейт или CI, гейт красный сразу после мержа, причём с ложной причиной.

Сама регулярка как способ определить «внутри ли строкового литерала» несостоятельна: с `re.DOTALL` `.*` перекрывает произвольные участки файла, так что паттерн вырождается в «где-то есть кавычка, где-то Traceback, где-то ещё кавычка». Нужен AST-обход строковых литералов, а сам модуль — исключать из скана.

**MAJOR-5. Отсутствие цели проверки трактуется как успех — молчаливый no-op.**
`refusal_paths.py:31-32, 57`

`if cli_path.exists():` без `else`: если `ai_ops_kit/cli/ai_ops_cli.py` не найден, проверка CLI просто не выполняется, `issues` остаётся пустым и модуль рапортует `pass`. То же для `engops_path`. При этом путь вызывает сомнение: установленный кит, судя по конвенции репозитория, живёт по `.ai/managed/tools/ai_ops_cli.py`, а не по `ai_ops_kit/cli/`. Достаточно неверного `root` или переезда файла — и инструмент вечно зелёный. Отсутствие артефакта должно давать явный `skip`/`fail` с указанием пути, а не `pass`.

## Scope violations

Явного scope creep нет — diff добавляет ровно один новый файл и не трогает существующий код. Но обратное: **объём недобран**. Модуль ни к чему не подключён (нет регистрации в гейтах/CI, нет упоминания в конфиге), и без этого не влияет ни на что, кроме ручного запуска. Если подключение планировалось этим же изменением — оно отсутствует; если следующим — это следует зафиксировать явно, иначе модуль остаётся мёртвым кодом.
