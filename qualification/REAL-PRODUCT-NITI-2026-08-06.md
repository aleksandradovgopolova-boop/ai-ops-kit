## F-012. Mock-провайдер: прогон «завершается», не сказав, что писателя не было

**Наблюдалось:** `ai-ops run … --execute` с провайдером mock печатает
`tool-loop: bad-proposal: no-json · шагов 0 · правок 0`, гейты
`intake_completeness`/`implementation_verification` не закрыты, WorkItem
`NOT_READY` — при этом active-work сразу помечается `done`, а run-report не
говорит главного: «код в этом режиме должен написать внешний агент в worktree
X». Агент-исполнитель (Claude Code) понял это только по косвенным признакам
(созданный worktree + `not_yet: живой предложитель`).

**Почему важно:** «harness-executor» — де-факто основной режим работы кита под
Claude Code (см. CLAUDE.md-протокол). Сейчас его контракт неявный: непонятно,
что считается завершением, кто закрывает гейты и почему lifecycle получает
`done` при `NOT_READY`.

**Задача:**
- run-report при mock/absent-провайдере обязан явно печатать режим
  (`executor: external-agent`) и инструкцию: рабочий каталог, ветка, что
  сделать, чем закрыть гейты;
- active-work не помечать `done` при `NOT_READY` — либо статус
  `awaiting-external-executor`, либо done только после появления коммита в
  ветке работы;
- (опц.) команда `ai-ops finish <wid>` — переоценка гейтов по факту коммитов
  внешнего исполнителя.

**Acceptance:** прогон с mock печатает режим и инструкцию; `status` показывает
работу как ожидающую исполнителя, а не done; после реального коммита гейты
переоцениваются и работа закрывается честно.

## F-013. Spec-first: невалидный статус раздела превращается в молчаливое «не заполнено»

**Наблюдалось:** разделы спеки были заполнены содержимым, но со статусом
`filled` (угадан по смыслу). `spec_levels.assess` не знает такого статуса →
все разделы стали `missing`, блокер напечатал «не заполнено: goal, scope, …»
— хотя содержимое есть, а причина в неизвестном слове. Допустимый словарь
(`complete/not_applicable/declined/needs_human/missing`) нашёлся только чтением
исходника `spec_levels.py`.

**Почему важно:** спеку заполняет либо человек, либо агент без контекста
исходников кита; сообщение блокера — единственный канал обратной связи.
Диагноз «не заполнено» при фактической причине «нераспознанный статус» — это
ложный след, стоивший лишней итерации.

**Задача:**
- в форм-ошибке перечислять допустимые статусы (`{sid}: неизвестный статус
  'filled' — допустимо: complete/not_applicable/declined/needs_human`);
- различать в выводе блокера «раздел пуст» и «раздел заполнен, но статус
  нераспознан»;
- (опц.) шаблон spec.yaml, который создаёт `specify`, снабжать комментарием со
  словарём статусов прямо в файле.

**Acceptance:** спека со статусом `filled` даёт блокер, из текста которого
понятно, что исправить, без чтения исходников; шаблон spec.yaml содержит
словарь статусов.

## F-014. Worktree создаётся не от текущего HEAD — последовательные задачи не строятся друг на друге

**Наблюдалось:** рабочая ветка сессии — `ai-ops-main` (свежий origin/main +
установка кита + принятые задачи). Каждый `run --execute` создавал worktree от
старой базы (origin/main без принятых задач): вторая задача не видела результат
первой и правила бы те же файлы от старой версии (гарантированный конфликт при
слиянии). Исполнителю пришлось вручную делать `git reset --hard <HEAD ветки>`
в каждом worktree.

**Почему важно:** последовательная работа «задача за задачей» — базовый сценарий
кита; ручной reset в managed-worktree — это обход механики, который у
неопытного исполнителя закончится потерянными изменениями.

**Задача:**
- база worktree по умолчанию — текущий HEAD репозитория (ветка, на которой
  стоит пользователь), а не remote-default;
- явный `--base <ref>` для переопределения;
- run-report печатает выбранную базу (`worktree base: <ref> <sha>`), чтобы
  расхождение было видно сразу.

**Acceptance:** два последовательных `run --execute` на одной ветке — второй
worktree содержит результат первого без ручных действий; база отражена в
run-report.
