## Что это и чего это не

- Это CI-половина сквозного baseline **только для самого Кита**.
- Это **не заявление об ускорении** и не сравнение «до/после».
- Это **не про CI дочерних продуктов** — он измеряется отдельным срезом.
- Недоказанное помечено `null`, а не нулём. Параллельные jobs **не складываются** в стену.

## Как считаем (чтобы не смешивать)

- **wall** — `updatedAt − createdAt` всего прогона (часы на стене).
- **queue** — `startedAt первого реального job − createdAt` прогона.
- **execution** (job) — `completedAt − startedAt` конкретного job.
- **критический путь** — самый длинный job в прогоне. Jobs внутри одного прогона идут
  параллельно, явных межзадачных зависимостей в данных нет, поэтому критический путь = самый
  длинный job, **а не сумма** параллельных.
- `sum_parallel` (сумма всех параллельных jobs) приведена в `report.json` только затем, чтобы
  показать: это **не** стена (она завышает в ~3,5 раза).

**Чтение.** Три контура PR параллельны, поэтому стена пути PR ≈ стена самого медленного из них —
`package-quality`. Для успешных PR это **290 с и 522 с** (разброс велик при n = 2 успешных PR).
`docs` отдаёт feedback за ~16–20 с, `pr-smoke` — за ~87–91 с; оба заметно короче `package-quality`
и его не удлиняют.

**Очередь ничтожна** (1–4 с): раннеры GitHub-hosted поднимаются почти мгновенно. Очередь здесь
не узкое место; узкое место — исполнение внутри `package-quality`.

### Что внутри `package-quality` (критический путь)

Во всех пяти прогонах самый длинный job — `quality (selftests-m, .github/ci-groups/selftests-m.sh)`:
критический путь **285 / 519 / 432 / 510 / 360 с**. Для сравнения, арифметическая сумма всех 13
параллельных jobs = 1565–1941 с — **её нельзя** выдавать за стену (завышает ~3,5×). За selftests-m
по длительности следуют группы `selftests-a`, `fast-1`, `fast-2` и `smoke-macos`
(`.github/ci-groups/*.sh`). Поэтапный (step-level) тайминг внутри jobs не снимался — лог намеренно
не тянули, чтобы не конкурировать за общий тестовый слот.

## Причины повторов

Терминология — по таксономии #1321. Разделено «что видно из метаданных» и «что из них не выводимо».

| Наблюдение | Повтор? | Причина по таксономии | Выводимо из метаданных? |
|---|---|---|---|
| `package-quality` идёт на `pull_request` (голова PR) **и** на `push` (merge-коммит) того же изменения: #1370 `22a6cdd9` (519 с) → merge `f5adcab5` (432 с); #1369 `1a321e9d` (290 с) → merge `4fed5eae` (513 с) | **да, ~2× обязательного набора на одно влитое изменение** | дубль PR↔merge (повтор обязательного набора при изменении базы — merge в `main`) | **да** — по полю `event` и связи PR→mergeCommit |
| PR #1371 `f28fc143`: прогон `package-quality` упал — job `quality (contracts)` = failure (99 с), остальные 12 jobs прошли; `run_attempt = 1` (перезапуска ещё не было) | падение зафиксировано; повтора пока нет | причина падения contracts — **не выводима** из метаданных run (нужен лог, который не тянули) | факт падения — да; его причина — нет |
| Ручные перезапуски того же run | не наблюдались | — | да — `run_attempt = 1` у всех прогонов выборки |
| cache miss / повторная установка / прерывание сети / flaky | **не определимо** из метаданных run | — | нет — требуется cache/step-level слой, не снятый в этом проходе |

Вывод: единственный **доказуемый** из `gh` повтор — дубль обязательного набора `package-quality`
между прогоном PR и прогоном на merge-коммите (≈2 исполнения обязательного набора на одно влитое
изменение). Остальные категории повторов из метаданных run не выводятся и не выдаются за ноль.

## Условная применимость (не повтор, но важно для честности)

На событии `push` (merge) jobs `security-scan` и `delivered-footprint` помечены `skipped` — они
запускаются только на PR. Это **не** «прошло»: «не запускалась ≠ прошла». В `report.json` у таких
jobs `execution_s = null`, а не 0.

## Не измерено (`null`, не ноль)

- **cold vs warm cache** — попадания/промахи `actions/cache` в этом проходе не разделены.
- **CPU / RAM / число workers раннера на прогон** — `gh` отдаёт только класс (`ubuntu-latest` /
  `macos-latest`), не фактическое выделение.
- **ожидания внешних сервисов** — не вычленены.
- **ожидания человека** (латентность ревью, время до merge) — вне этого замера.
- **p95** — n на один контур+SHA слишком мал; только точечные наблюдения, без распределения.
- **step-level тайминг** внутри jobs — лог намеренно не тянули (общий тестовый слот был занят).
- **стена дубля локального↔CI** — локальная половина в baseline от 21.10.2026.

## Рамка честности

Это CI-половина сквозного baseline **для Кита**. Он не заявляет никакого ускорения, не сравнивает
«до/после», не покрывает CI дочек и не меняет ни одной проверки. Разброс стены `package-quality`
(290 с против 522 с на успешных PR) при n = 2 — это разброс, а не тренд; p95 недоступен. Названы
только те причины повторов, что выводимы из метаданных прогонов; всё прочее помечено «не
определимо» и `null`. Числа пригодны как опора для политики объёма проверки и бюджетов
последующих срезов #1321, но сами по себе ничего не оптимизируют.
