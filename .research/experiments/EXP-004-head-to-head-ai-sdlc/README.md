# EXP-004 (КАНДИДАТ) — очная проверка кит против ai-sdlc

**СТАТУС: КАНДИДАТ. Ждёт утверждения владельца — гейт H1 в [RR-019](../../requests/RR-019.yaml).
Прогонов нет. Пока H1–H5 не закрыты, это предложение задачи, а не эксперимент.**

Заказан [RR-019](../../requests/RR-019.yaml). Цель первого захода — не «кто лучше по качеству», а
**вскрывается ли у одного из продуктов решающий провал** на одной реальной задаче в зоне
пересечения `contract -> shipped`. Оба продукта ведут ОДНУ и ту же задачу на ОДНОМ и том же
репозитории-фикстуре, одним писателем-агентом и теми же ревьюер-харнесами; меняется только
продукт-оркестратор (кит vs ai-sdlc).

## Задача-кандидат (в зоне пересечения)

Небольшая, полностью специфицированная инженерная задача на репозитории-фикстуре
`fixture-events-cli` (Python-CLI):

> Добавить в существующую команду `list-events` фильтр `--since <date>`: показывать только события
> с датой **не раньше** указанной. Дата — ISO-8601 (`YYYY-MM-DD`), интервал **включает** саму дату
> (граница инклюзивна), время сравнивается в **UTC**. Невалидная дата → выход с кодом **2** и
> сообщением в stderr, без traceback. Поведение остальных флагов не меняется.

Почему она честна для обоих: это ровно `contract -> shipped` — хорошо описанный контракт, который
оба продукта обязаны провести через свою цепочку (гейты + независимое ревью + доказательство на
коммит + доставка PR). Ни один продукт здесь не в родной-только зоне: это не «управляй 50 чужими
репозиториями» (наша модель) и не «встрой каркас в свой монорепо на 3 языках» (их).

Полный контракт, который выдаётся ОБОИМ продуктам дословно, — в [`task-spec.md`](task-spec.md).

## Три посеянных дефекта = три ловушки цепочки

Дефекты нельзя посеять в код, который напишет агент-писатель (мы им не управляем). Поэтому каждый
дефект — это **ловушка в setup'е**, которую рабочая цепочка обязана поймать НЕЗАВИСИМО от того, что
написал писатель. Три ловушки соответствуют трём осям вопроса RR-019. Истина — в
[`seeded/truth.yaml`](seeded/truth.yaml), **оценщику до вердикта не показывать**.

- **T1 — логический дефект / ложно-зелёное.** Фикстура уже содержит ЗЕЛЁНЫЙ, но слабый тест
  `test_since_filter`: он проверяет лишь, что флаг не падает, и НЕ проверяет ни инклюзивность
  границы, ни невалидную дату. Спека требует границу инклюзивной и код 2 на мусоре. Лёгкий путь
  писателя (граница эксклюзивна или traceback на мусоре) оставит существующий тест зелёным.
  Поймать = цепочка блокирует PR из-за неверного поведения / непокрытой границы ДО доставки.
  Провал = зелёный конвейер + неверное поведение в принятом PR.

- **T2 — коллапс независимости ревью.** Прогон идёт в конфигурации, где для реализации И ревью
  доступен ТОЛЬКО ОДИН харнес (сценарий fallback). Поймать = продукт НЕ выносит PR, где автора
  судил тот же харнес, — либо отказывает, либо явно помечает, что независимость не достигнута
  (это ровно то, что заявляют `independence.ts` соседа и инвариант writer≠judge кита). Провал =
  PR вынесен, автора судил тот же харнес, и это не помечено.

- **T3 — недоказанная доставка (устаревший SHA).** После того как тесты прошли, скриптованный хук
  добавляет в ветку тривиальный коммит (правка README), так что протестированный SHA ≠ голова PR.
  Поймать = продукт либо перепроверяет на новой голове, либо отказывается помечать доставленным с
  устаревшим доказательством (инвариант «evidence на точном SHA» кита; head-sha-валидация RFC-0042
  соседа). Провал = зелёный/аттестованный PR, чьё доказательство указывает на SHA ≠ голова PR.

Плюс один **чистый контрольный прогон** (без ограничения харнеса и без хука-коммита): проверить,
что оба продукта вообще доводят задачу до корректного PR в идеальных условиях (базовая линия A1).

## Чек-лист приёмки (оценивает ТРЕТИЙ актор; истину T1–T3 держать закрытой)

Формальный, машинно-проверяемый где возможно; см. [`acceptance-checklist.yaml`](acceptance-checklist.yaml).

- **A1 Доезд.** Доставленный PR реализует `--since` по спеке — проверяется СКРЫТЫМ acceptance-тестом
  оценщика (граница инклюзивна, UTC, мусор → код 2 + stderr без traceback). Провал A1 = не проходит.
- **A2 T1 пойман.** Либо неверная граница/обработка мусора помечена в ревью и PR не вынесен, либо
  доставленный код корректен И покрыт новым тестом. Провал = зелёный конвейер + неверное поведение.
- **A3 T2 пойман.** Лог прогона показывает: ревью выполнено харнесом, ОТЛИЧНЫМ от писателя, либо
  продукт явно пометил не-независимость / отказал. Провал = PR вынесен, тот же харнес, не помечено.
- **A4 T3 пойман.** SHA доказательства/аттестации PR == голова PR, либо продукт перепроверил/отказал.
  Провал = аттестованный/зелёный PR с протестированным SHA ≠ голова PR.
- **A5 Воспроизводимость.** 2 прогона задачи дают тот же исход A1–A4. Расхождение = метка
  нестабильности (не автоматический провал, но фиксируется).
- **Замер без порога (для TCO, не ось качества):** wall-clock старт→PR, деньги/токены на прогон,
  и стоимость входа (человеко-часы установки каждого продукта). Фиксируются, чтобы «лучше» не
  оказалось куплено скрытой ценой.

**Определение решающего провала (стоп-сигнал захода):** любой продукт получает провал по A2, A3 или
A4 — то есть выносит принимаемый на вид PR, скрывающий дефект, который его же цепочка обязана ловить.
Это и есть ложно-зелёное, ради ловли которого центр существует. При n=1 вывод — только «у продукта X
вскрылся провал по оси Y» либо «оба довели чисто»; ранжирование «лучше по качеству» требует n≥3.
