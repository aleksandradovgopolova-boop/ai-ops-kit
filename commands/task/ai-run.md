# Команда: ai-run

> **Канонический вход (3.0-срез 1).** `ai-run` — основной путь запуска задачи. `ai-start-task`
> сохраняется как совместимый алиас той же спины и не удаляется (снятие — не раньше 4.0).

## Назначение

Единый вход «задача → контролируемое исполнение → отчёт» одной транзакцией:
классификация/маршрут → RunPlan (base_workflow + треки + агрегированные гейты) →
WorkItem → регистрация в реестре активных работ → исполнение → компактный отчёт.
Собирает то, что раньше было отдельными шагами `ai-start-task`. Инструмент —
`ai_ops_kit/engine/ai_ops_run.py`.

## Вход от человека

Принимай задачу обычными словами. Роли, workflow, сигналы и внутренние YAML
собирает исполнитель из запроса и источников проекта; не выдавай технический
шаблон ниже за обязательную форму для владельца.

Сначала установи границы задачи: явно названный пользователем репозиторий имеет
приоритет над прежним контекстом дочки. «Все открытые issues» относится к этой
очереди; сними её актуальный список, различай задачи, эпики и требования полевых
доказательств. Не подменяй реализацию parent задачами продукта-дочки.

Прочитай существующие сведения до вопроса: известные объём, цель, репозиторий
и разрешённые действия не спрашиваются повторно. Неразрешимый бизнес-пробел
назови простыми словами; параллельно делай независимую разрешённую работу.
Неполный runtime или отказ инструмента сохраняй как ограничение с источником.
`planned` не означает выполненную стадию; в итог попадают реальные проверки и эффекты.

## Порядок выполнения

```
PYTHONPATH=.ai/managed python3 -m ai_ops_kit.engine.ai_ops_run run "<задача>" <child_root> \
    --signals '<json сигналов>' \
    --engine controller --runtime <native-runtime-id>
```

Это вход для рантайма со своим tool loop: `native-runtime-id` — `claude-code`,
`codex` или `qwen-code` по фактическому исполнителю. Для автоматического
provider-пайплайна явно выбери `--engine pipeline --execute` и провайдера;
флаг runtime сам по себе native CLI не запускает.

1. Построить RunPlan по сигналам (ui_changed, measurable_behavior, security_surface_changed,
   events_changed, ai_component, deploy_touched, user_facing_change, affected_areas).
2. Создать WorkItem и записать RunPlan (`features/<id>/run-plan.yaml`).
3. Зарегистрировать активную работу (ветка/зоны/сессия) — для conflict forecast.
4. Исполнение:
   - **Рантайм со своим tool loop** (`--engine controller`): контроллер готовит план и каркас
     состояния; стадии/патчи/тесты исполняет **рантайм**, следуя плану. status = `planned`.
   - **generic-orchestrator** (`--engine controller`): контроллер реально прогоняет стадии
     и гейты; status = `done`/`blocked` по evidence, без delivery-гарантий pipeline.
5. Записать компактный `features/<id>/run-report.json` и показать резюме.

## Границы (честно)

Флаг runtime этого технического контроллера сам не запускает native Codex CLI
или его bounded stage adapter. Внешний runtime со своим tool loop читает план
и исполняет стадии самостоятельно; генерация каркаса не доказывает выполнение.


Кит не притворяется, что исполнил за рантайм: для внешнего рантайма «сделал» = evidence
(commit SHA, exit codes, структурный reviewer-result), а не факт вызова. `ai-run` —
канонический вход (3.0-срез 1); сплит на пакеты — оставшиеся срезы 3.0 (см.
`docs/3.0-design.md`).

## Результат

WorkItem + RunPlan + запись в реестре активных работ + run-report; для
generic-orchestrator — прогон стадий с вердиктом гейтов.

## После первого полезного результата: пульт продукта

Первый результат может предложить обычный запрос «Создай пульт продукта».
Само предложение не запускает создание, публикацию или изменение плана и не
мешает продолжать основную работу. Это существующий вход ai-run, не новый CLI.

Когда такой запрос поступил, сначала проверь существующий пульт/экран состояния:
дополни его, если он уже есть. Источники — цели, канонический план, паспорт,
реальные метрики и история **этой дочки**. Не копируй числа/тексты Кита и не
заводи второй план. Пульт отвечает где/зачем/что мешает/что изменилось/что дальше;
одна рекомендация и максимум две альтернативы идут из существующего next_work.
Отсутствующие/неизмеренные данные обозначь unknown/degraded; snapshot назови снимком.
Создание и доставка проходят обычный Kit-путь задачи с проверкой реального результата.
